# 构建与模块布局

当 Lua 与蓝图 API 无法满足需求、需要新增原生 UI Adapter，或需要面向 iOS、HarmonyOS、Android 或 Web 平台构建时，请使用 C++ Source 项目。原生运行时基于 C++20、CMake 与声明驱动绑定机制构建。

## 环境要求与构建模型

构建 C++ Source 项目需要满足以下条件：

- 安装 CMake、C++20 工具链及对应目标平台的构建依赖。
- 目标平台处于受支持范围内：

| 目标平台 | 最低系统／API 版本 | 架构／图形接口 |
|---|---|---|
| Windows | Windows 10 | x64 |
| macOS | macOS 13.3 | Apple Silicon |
| iOS | iOS 16.3 | arm64 |
| HarmonyOS | HarmonyOS 6.0.2 / API 22 | arm64-v8a |
| Android | Android 7.0 / API 24 | arm64-v8a |
| Web | 现代浏览器 | WebGL 2 |

公开头文件包含常规 C++ 声明以及在编译期展开为空的 `BIND_*` 标记。Core bindgen 会读取模块声明根目录与共享 Runtime 声明根目录，为每个类生成一份稳定的 LuaGlue 源码，并生成一份模块聚合与 Stub 源码、一份 LuaLS Stub 以及编辑器元数据。

### 可复现的 Windows Release 构建

Windows Release 构建在 Ludork、SFML、Lua 以及独立构建的 FFmpeg 上均采用可复现的编译与链接配置：

- **编译器与链接器**：MSVC 启用确定性编译；LLVM Clang 启用 `/Brepro` 并映射源码与构建目录路径。两者在链接时均使用 `/Brepro` 且禁用增量链接；MinGW 会抑制 PE 时间戳。
- **哈希稳定性**：当源码、依赖、编译器、SDK、构建配置与路径完全一致时，干净重建可保持 EXE 与 DLL 的哈希值不变，便于更新 Standalone 项目的 `Binaries`。
- **适用边界**：上述任一输入发生变化都可能改变输出产物。可复现性不保证跨不同编译器或不同项目路径生成完全一致的二进制文件，也不保证安装包字节完全一致。发行包不包含 PDB 文件。

### 可选服务器集成

可通过[服务器构建设置](<../简易服务器/部署与编辑器设置.md>)启用可选的 [`Global.Net` 快照／RPC API 与健康检测](<../简易服务器/原生客户端 API.md>)。修改开发环境 URL 或密钥后必须重新构建 Debug。未启用服务器集成的构建仍保留这些 API，但调用服务器交互接口时仅输出诊断信息并直接返回；详见[禁用服务器集成](<../简易服务器/原生客户端 API.md#禁用服务器集成>)。

## 模块架构

| 模块 | 职责 | 原生依赖方向 |
|---|---|---|
| `LudorkRuntime` | 值类型、VM 与绑定服务、蓝图执行、类型与组件数据、JSON、Asset/Data/Script 存储，以及 GPU 粒子模拟与绘制 | Standard、SFML 与私有 zlib；完整模式另加 LuaSF；不得依赖 Core 模块 |
| `Engine` | Engine 类型、服务、状态与玩法基础 | LudorkRuntime 与 SFML |
| `GlobalCore` | 全局游戏类与服务 | Engine、Standard、SFML 与 LudorkVideo；启用服务器传输时依赖 IXWebSocket；可选平台库 |
| `GlobalFunctions` | `Components`、`UI`、`NodeGraph` 与 `Manager` 四组自由函数 | GlobalCore 与 SFML |
| `LudorkVideo` | 位于 `Engine/Source/Media` 的共享视频解码、定位与音频提取 | LudorkRuntime、SFML，以及启用时的 FFmpeg |

`LudorkVideo`（`Ludork::Video`）是用于视频播放的静态库，不暴露 Lua 根模块。`LudorkRuntime` 在桌面端为共享库，在移动端为静态库，同样不暴露 Lua 根模块，其绑定归属于 `Engine`。各玩法模块按固定顺序加载，不反向链接 `GlobalFunctions`，并携带完整的跨模块声明。

### 资源存储与 `.ldpak` 归档

`AssetStore`、`DataStore` 与 `ScriptStore` 定义了只读的 Asset、Data 与 Lua 模块边界，同时支持未归档目录与 `.ldpak` 归档，并叠加用户目录覆盖层。Core 在 `setAppName` 之后提供用户根目录，由 Runtime 负责路径查找，绝不反向调用 Core 来决定目录。优先级与格式规则见[运行时资源查找](<../编辑器用户指南/项目设置与资产布局.md#运行时资源查找>)。

Standard 仅获得 `DataStore` 的文件访问权限，因此脚本归档不会暴露给文件系统 API。私有 zlib 负责归档解压与 CRC32 校验。

`.ldpak` v1 采用小端字节序布局：

- **文件头**：`LDPK` 头记录格式版本、分组、条目数量、索引范围与 CRC32 校验值。
- **索引**：按 UTF-8 字节顺序排列，记录路径、目录标志、64 位数据偏移、原始大小、存储大小、文件 CRC32 与分块数量。每条路径后紧跟分块描述符，记录存储大小、压缩标志与原始数据 CRC32。
- **数据块**：文件数据按 8 字节边界对齐起始，各块连续存放，原始块大小根据 1 MiB 块大小与文件总长度推导；空文件不含数据块。写入器对每个块使用独立的 zlib 等级 6 压缩流，仅在压缩后体积更小时保存压缩数据。
- **解码与校验**：归档读取与流读取共用同一套块解码逻辑。每条流仅缓存当前已解码的块，按原始字节偏移定位，并在加载块时校验块 CRC32；完整文件读取还会校验文件级 CRC32。遇到非法块范围、无效长度、压缩数据截断或尾随字节以及校验失败时一律拒绝：流返回对应的失败结果，完整文件读取则抛出错误。

### 蓝图运行时与宿主边界

- **蓝图执行**：Runtime 负责蓝图类生成、Script Mixin、图执行与 Latent 调度；Engine 提供 Actor 图查询、EventBus 与帧循环接入。`RuntimeProviders.installBlueprint(classDataByPath, compileGraph, instantiateGraphTemplate)` 用于安装三个蓝图回调，`ClassDict` 委托给 VM 解析器。缓存与定义身份遵循[执行流、事件与变量](<../Lua 与蓝图脚本/蓝图脚本/执行流、事件与变量.md#类定义与会话生命周期>)。
- **批量 Actor 事件检查**：`BlueprintRuntimeFacade::hasEvents(objects, eventNames)` 返回按对象与事件排列的布尔矩阵，使 Actor 更新批次在同一次同步内复用类级事件检查。实例图与实例自有方法仍单独检查；类缓存仅在单次调用期间有效，后续同步会及时感知方法与图的变化。关闭 Tick 的 Actor 会推迟事件检查，直到重新启用 Tick；其事件掩码在原生更新之后、事件分发之前解析，并保持至下次同步。所有 Actor 都会执行原生更新。
- **Provider 门面**：Engine 持有 `RuntimeProviders` 绑定门面。具名类型的 `Curve` 与 `PlainTextConfig` 回调驻留在 Core，蓝图与配置安装则委托给 Runtime。固定签名 Provider 在调用边界校验单个返回值，Graph 结果采用共享原生所有权；Runtime 不包含 Core 数据类型。缺失安装、重复安装、返回错误结果或在会话已停止时调用均会触发错误。
- **引导模块**：仅在启动阶段使用的原生模块归宿主持有。应用负责注册 `cjson` 与 `cjson.safe`，Standard 负责注册 `Class`，Engine 直接使用已初始化的原生表与 API，而不引入反向模块链接。动态模块解析仍由资产与元数据驱动。

### 应用宿主与构建选项

- **宿主目录布局**：游戏应用宿主位于 `Application/`（包含 `include/` 与 `src/`），Android 与 HarmonyOS 应用外壳位于 `Engine/PlatformHosts/Android` 与 `Engine/PlatformHosts/Harmony`。构建脚本位于 `Engine/cmake/`，其中 FFmpeg 构建位于 `Engine/cmake/FFmpeg/`。
- **窗口样式**：游戏窗口样式统一定义在 `GlobalRuntime.cpp` 的 `runtimeWindowStyle()` 中。其固定窗口策略会传递至 SFML 窗口创建与重建、原生工作区尺寸测量以及 HarmonyOS ArkTS 宿主。各平台 Adapter 仅将传入样式映射为窗口控件与边框尺寸，不自行决定缩放策略。显示倍率与全屏属于运行时设置。
- **存档加密选项**：`LUDORK_SAVE_AS_LDC` 为 CMake 选项，默认值为 `OFF`，由 Standard 在 Entry 执行前暴露为 `SAVE_AS_LDC`。C++ Source 打包通过**加密存档内容**设置该默认值；Entry 覆盖规则见[运行时数据、配置与存档](<../Lua 与蓝图脚本/默认玩法/运行时数据、配置与存档.md#存档>)。
- **Lua 开关**：`LUDORK_WITH_LUA` 默认为 `ON`，游戏构建必须保持启用。
- **UI 生成边界**：游戏构建会生成原生绑定并通过项目注册表校验 UI 资产，但不会生成 UI Lua View 或类型声明。生成 UI View 时，请执行编辑器**导出**或运行 `ludork-assets ui-assets generate <project-root>`（无需桌面预览环境）。文件归属规则见[声明式 UI 编写工作流](<../Lua 与蓝图脚本/声明式 UI/编写工作流.md>)。
- **PreviewHost**：预览构建目标、产物与交叉构建注册表详见 [PreviewHost：构建、发布与排错](<../PreviewHost/构建、发布与排错.md>)与[架构与数据流](<../PreviewHost/架构与数据流.md>)。

## 共享格式与渲染常数

`Toolchain/runtime_formats.py` 统一定义 `.ldpak` 与加密载荷的布局、版本、二进制数据标记及编解码上限；`Toolchain/resource_constants.py` 统一定义资源分组、路径与后缀。CMake 会调用 `ludork-codegen runtime-constants cpp <project-root> <output-directory>`，在 `Intermediate/<build-name>-<hash>/RuntimeConstants/LudorkGenerated` 下生成中立的 C++ 头文件。

原生使用方应链接 `Ludork::RuntimeConstants`，而不要包含父级宿主的私有头文件。Engine 通过 [`ResourceFileConstants`](<../Lua 与蓝图脚本/全局与 Core 模块/Core Modules/Engine/事件与模块根.md#resourcefileconstants>) 向脚本暴露脚本、数据与动画文件后缀。

`Assets/Shaders/Global/UnoccludedLightPass.frag` 是 `LUDORK_MAX_SHADER_LIGHTS` 的唯一定义位置，必须为 `1–256` 之间的十进制整数（当前为 `64`）。代码生成器会拒绝缺失、重复或无效的定义。修改此上限后必须重新构建原生项目，以确保着色器、原生渲染器与只读的 `GlobalCore.Light.MAX_SHADER_LIGHTS` 保持一致；常规的着色器重载不会更新编译期上限。

游戏构建、桌面预览构建与 `LUDORK_WITH_LUA=OFF` 构建都会运行常数生成。C++ Source 模板保留着色器源码与构建配置，正常构建会自动重新生成这些头文件。生成的头文件属于构建产物，不得手工编辑，也不应作为模板源码分发。

## LDC 二进制数据

`Runtime/Data.hpp` 提供 `loadData`、`saveData`、`dataExists`、`decodeData` 以及二进制载荷读取器 `parseBinaryData`；文件接口接受 `std::filesystem::path` 或 UTF-8 字符串。Lua 在 `Engine` 模块上暴露前四个数据文件 API，而 `parseBinaryData` 为 C++ 载荷层 API。`Runtime/Json.hpp` 提供针对精确路径的 JSON 文本操作。Standard 负责文件访问、路径解析以及载荷压缩与混淆，既不依赖 Runtime，也不解析二进制值树。

LDC 采用 `LDDC` 封装格式（版本 `1`），包含 zlib 压缩、流混淆与校验和，其中原始长度与校验和覆盖未压缩的二进制载荷。每个值均以 1 字节标记开头：

| 标记 | 值与载荷 |
|---|---|
| `0`、`1`、`2` | 分别表示 null、false、true，无后续载荷 |
| `3` | 小端有符号 64 位整数 |
| `4` | 小端有限 IEEE 754 binary64 浮点数 |
| `5` | 小端 `uint32` 字节长度，后跟字符串字节 |
| `6` | 小端 `uint32` 元素数量，后跟带标记的数组值 |
| `7` | 小端 `uint32` 条目数量，后跟字符串键与带标记的值；键采用无标记的长度／字节编码，并按 UTF-8 字节顺序写入 |

- **限制与区分**：空数组与空映射严格区分。解码后的载荷上限为 512 MiB，嵌套深度上限为 256 层。
- **解码校验**：遇到非法标记、数据截断、无效长度、重复键、非有限数值或尾随字节时解码失败。作为纯数据格式，LDC 不支持函数、对象、循环结构或引用恢复。
- **旧版载荷**：内含 JSON 文本的旧版 LDC 载荷会被直接拒绝，不提供回退或迁移，请从源数据重新生成。着色器载荷使用独立格式。

## MRB 渲染

渲染模块采用 `versions.conf` 指定的 SFML MRB 源码树及匹配的重新生成的 LuaSF 绑定。如需使用外部源码目录，请在现有 CMake 构建中设置 `LUDORK_SFML_SOURCE_DIR`、`LUDORK_LUASF_SOURCE_DIR` 与 `LUDORK_LUAGLUE_SOURCE_DIR`。依赖初始化按固定来源拉取源码，无法用于更新本地提供的 SFML 副本。

| 目标平台 | 游戏后端 | 编辑器预览后端 |
|---|---|---|
| Windows | Direct3D 11 | OpenGL 3.2 Core |
| macOS | Metal | OpenGL 3.2 Core |
| iOS | Metal | 无本地 PreviewHost |
| Android 与 HarmonyOS（含二合一设备） | OpenGL ES 3 | 无本地 PreviewHost |
| Web | WebGL 2 | 无本地 PreviewHost |

桌面构建除原生游戏后端外同时包含 OpenGL。游戏会在创建 GPU 资源前选定平台后端；若选定后端初始化失败，不会回退到 OpenGL。PreviewHost 作为独立进程运行，显式创建 OpenGL Core 上下文，在内存中直接从 GLSL 编译着色器程序，不会写入游戏的持久化着色器缓存。

### `ContextSettings` 与 LuaSF

SFML MRB 使用 `ContextSettings.backend` 替代原有的 `ContextSettings.majorVersion`、`minorVersion`、`attributeFlags` 与 `Attribute`：

- 将 `backend` 设为 `nil`／`std::monostate` 可继承设备配置；也可指定 `OpenGLSettings`、`OpenGLESSettings`、`VulkanSettings`、`DirectXSettings` 或 `MetalSettings`。
- OpenGL 版本、profile 与 debug 标志配置在 `OpenGLSettings` 上；帧缓冲的深度、模板、抗锯齿与 sRGB 设置仍位于 `ContextSettings`。
- `Engine.ContextSettings` 构造函数接受 `(depth, stencil, antiAliasing, sRgb, backend)`，或包含这些字段的字典。
- LuaSF 必须基于匹配的公开头文件重新生成；生成器会排除 `sf::rhi` 与 RHI 头文件子树，同时保留常规 SFML 公开 API。

### 着色器转换与缓存准备

着色器资产与生成材质均使用 GLSL 编写。[初始化场景](<../Lua 与蓝图脚本/默认玩法/默认模板概述.md#入口与模块>)会在运行依赖着色器的过渡效果前完成两者的准备；资产程序、生成材质 Pass 以及内置光源和 GPU 粒子程序的详细流程见[着色器准备](<../Lua 与蓝图脚本/全局与 Core 模块/Core Modules/Engine/地图与材质.md#mrb-着色器准备>)。源码缺失、阶段不受支持或编译失败都会中止初始化；执行绘制前程序必须已就绪。

- **转换管线**：C++ 转换器分别为 Direct3D 11 生成 HLSL、为 Metal 生成 MSL、为 OpenGL ES／WebGL 生成 ESSL，完整保留阶段接口、uniform 名称与类型、纹理绑定及引擎坐标约定。在原生平台上，待转换程序与材质、着色器缓存检查共用同一工作线程池，每个任务处理完整程序以确保各阶段协同链接。WebGL 运行于单线程，在批次间让出执行权，并在向浏览器存储写入缓存期间继续保留最后一帧完整的加载画面。GPU 对象创建与管线预热在准备线程上按程序顺序执行。
- **派生缓存布局**：派生文件按源文件相对路径存放在用户数据目录下，必要时追加目标语言与程序身份后缀。GLSL 源码与翻译文本遵循着色器加密设置，缓存记录遵循数据加密设置。即使游戏使用 `.ldpak` 归档，派生缓存也始终以未归档文件形式存储。
- **校验与增量恢复**：每次 `Init` 均由 C++ 校验源码内容、阶段组合与缓存产物。缓存命中时直接恢复 GPU 对象，跳过重复转换与编译，且不改写未变动文件。GLSL 或转换配置变更仅影响对应的程序组合。转换器与平台编译器分别追踪身份：有效 HLSL 可在不重新转换 GLSL 的前提下修复缺失或失效的 DXBC；调整加密设置仅更新存储形态并复用有效 DXBC；重新导出材质时若生成 GLSL 未变，则保留已校验的派生着色器。
- **Windows 文件锁重试**：在 Windows 上，缓存重命名或回滚文件删除如因临时访问拒绝或共享冲突受阻，会持续重试最长 10 秒。取消操作可立即中断等待；回滚阶段享有独立的重试窗口以恢复原缓存。

### 后端二进制缓存与 GPU 粒子

- **Direct3D 11（Windows）**：初始化阶段会在 HLSL 内容、阶段类型、入口点与编译器指纹均相同的着色器阶段间复用已验证的 DXBC，对其余不重复输入并行编译各一次，并将原始 DXBC 写入对应阶段的缓存路径。运行时直接读取原始字节，不套用着色器加密封装。驱动升级时重新创建并校验 GPU 对象，同时保留有效 DXBC。DXBC 属于 Direct3D 字节码而非 GPU 机器码，最终缓存由操作系统与驱动管理。
- **Metal（macOS 与 iOS）**：保留 MSL 以及绑定到设备与驱动的 `MTLBinaryArchive`。归档命中时直接复用管线而无需重新录制；归档未变化时不重新序列化或发布。缺失或失效条目按需增量恢复，仍可用的归档内容保持不变。会话准备阶段仍通过 Metal 的 MSL 前端创建着色器库。
- **OpenGL ES 与 WebGL**：保留 ESSL 并跳过持久化 GPU 二进制生成，GPU 程序在运行时编译与链接。
- **MRB GPU 粒子**：模拟与绘制均通过 SFML RHI 在 GPU 端执行，涵盖顶点变换、实例化绘制与浮点曲线纹理。存活粒子数先在 GPU 端归约，仅异步回读最终的 4 字节计数。后端缺少统计能力时计数与计时结果作为可选值处理；若后端缺少模拟能力则直接报告错误，不提供 CPU 回退。

## GPU 粒子归属

GPU 粒子的配置与执行在 Core 与 Runtime 之间清晰分层：

- **Core 公开接口**：Core 持有 `Emitter`、`EmitterComponent`、`EmitterView`、Scene 调度接口以及既有的 `ParticleSystem`。`EmitterConfiguration` 包含多个 `EmitterTrack` 值，每条轨道组合了 Runtime 的 `EmitterTrackParameters` 与 Core 的八通道具名 `EmitterCurves`（`Curve::CurveData`）。`setConfiguration` 集中校验参数，为每条轨道将各条 `Curve` 采样烘焙为 256 × 8 浮点查找表，并重新开始播放；`getConfiguration` 返回独立的值副本。
- **资源解码**：在 Emitter 路径中，`RuntimeData` 仅限用于 Core 的 `EmitterResource.hpp/.cpp` 读取资源 JSON，将创作期字符串选项、0–255 颜色、数组与曲线引用映射为固定配置字段。`Emitter` 持有该配置值，后端持有编译后的配置。
- **曲线布局与配置**：`Runtime/Graphics/GpuEmitterCurveLayout.hpp` 定义 256 × 8 曲线布局及其打包为两行 RGBA 的方式，确保 CPU 烘焙、GPU 纹理分配与生成着色器坐标共用一致的采样数与索引规则。`Runtime/Graphics/GpuEmitterConfiguration.hpp` 传递 Runtime 轨道参数与烘焙曲线采样，不含 Core 类型。
- **未绑定的 GPU 后端**：`GpuEmitterBackend`（`Runtime/Graphics/GpuEmitterBackend.hpp`）通过私有实现管理播放状态、固定步长模拟、GPU 轨道、绘制、异步统计与延迟 GPU 释放。它仅接收已解析的配置，既不解析 `Data/Particles` 键，也不依赖 Core 的 Curve、Actor 或 UI 类。
- **统计与绑定**：`EmitterStatistics` 为 Runtime 值记录，包含必填的 `capacity` 与 `time` 字段，以及可选的渲染器、计数与计时字段。Core 直接返回该结构；Lua 绑定输出包含全部声明字段的快照表，不可用的可选值以 `nil` 表示。公开的 `Emitter` 将播放调用转发至后端。配置、轨道、曲线、爆发与统计记录各自独立成同名头文件，其 Lua 注册与声明由常规绑定构建生成至 `Engine` 下（Runtime 不暴露 Lua 根模块）。
- **实现与 GPU 生命周期**：GPU 源码、程序、缓冲区与私有头文件位于 `Runtime/src/Graphics/Emitters`，构建于 SFML RHI 之上。纹理读取复用 Runtime 的 `AssetStore` 与 `AssetInputStream`，统一支持未归档目录与 `.ldpak` 归档布局。Runtime 依赖 Standard 与 SFML，Core 仅包含 Runtime 的公开 graphics 头文件。Runtime Graphics 的 CMake 子目录在完整构建与 `LUDORK_WITH_LUA=OFF` 构建中均只编译一份后端。
- **延迟 GPU 释放**：共享 GPU 资源按活动 SFML RHI 设备索引。关闭阶段将退役 GPU 对象加入队列，不要求调用线程持有上下文；实际回收在对应资源上下文激活时执行。Scene 与预览宿主持有窗口和渲染目标，并在销毁上下文前完成回收。GPU 资源生命周期独立于 Lua VM 生命周期。

## 会话与模块生命周期

- **会话所有权**：Standard 持有 Lua 会话。`runtime::initialize` 要求 Standard 会话处于运行状态，重复调用会保留已挂载的 Runtime 状态。一旦 `runtime::shutdown` 卸载 Runtime，重新启动必须建立新的 Standard 会话与 Lua VM。
- **关闭顺序**：Standard 按依赖逆序依次关闭各模块（`Global`、`Engine`、`Runtime`），随后释放自身状态。Lua VM 归宿主所有，宿主必须在发起关闭的线程上等待关闭完成后，方可调用 `lua_close`。如果 LuaSF 初始化或绑定注册在 Standard 启动前失败，宿主仍须先调用 `LuaSF_quiesce_state` 与 `LuaSF_shutdown_state`，再调用 `lua_close`，以释放可能已部分初始化的胶水会话。
- **独立于会话的存储**：`AssetStore`、`DataStore`、`ScriptStore` 以及 Standard 只读文件 Provider 属于宿主配置，独立于 VM 会话并在会话关闭后保持有效。
- **执行范围与 VM 锁**：Standard 在每个宿主 Lua 入口建立 LuaGlue 执行范围。只有当宿主确认当前线程持有 VM 锁且执行 Hook 未变化时，嵌套胶水操作才能复用该范围。`LuaExecutionPause` 会暂停该所有权，暂停期间的操作必须重新获取锁；未提供所有权探针的宿主使用常规的 enter/leave Hook。
- **栈检查（`LuaInvocation.hpp`）**：在 VM 所有权范围内，调用 `ludork::standard::ensureLuaStack(state, count, context)` 可为额外的 `count` 个值预留栈空间；计数超过 `INT_MAX` 时抛出 `std::length_error`，扩栈失败时抛出 `std::runtime_error`。
- **受保护 Lua 调用**：`invokeLuaFunction(state, callable, arguments, context)` 接收 `lua_glue::Object` 可调用对象与 `std::vector<lua_glue::Object>` 参数列表，检查栈容量、压栈并执行受保护调用。成功时将全部返回值保留在入口栈顶之上并返回结果数量；发生任何异常时先恢复入口栈顶再向外传播。独立的 `class_runtime::invoke(state, callable, argumentCount)` 则直接消费已压入 Lua 栈的参数。

## 宿主与实现源码

每个独立类或绑定类型均在 `include` 下放置同名头文件，必要时在 `src` 下放置同名源文件。宿主专用的数据类型可内嵌于宿主；共享数据与辅助工具集合可集中存放。

### 实现分层与共享内部模块

- **宿主私有 `Impl` 布局**：宿主私有实现置于 `src` 下并以 `Impl` 命名后缀（如定义 `Host::Impl` 的 `HostImpl.hpp`）。规模较大的实现可建立同名子目录并通过 `target_sources` 贡献源码。依赖方向严格由宿主流向实现：子目录不得包含父目录私有头文件（包括通过 include 搜索路径绕过），公开头文件不得包含私有头文件。
- **Core 与 Runtime 共享内部模块**：Core 通过 `src/Shared/include/CoreShared`（实现位于 `src/Shared/src`）共享 `SpriteVisuals`、摇杆设备追踪与文本配置编解码器；使用方仅包含接口头文件，宿主配套头文件保留在宿主源码旁。Runtime 的共享 Lua 服务位于 `Runtime/src/LuaServices`，纯 ConfigVars 解析位于 `Runtime/src/Metadata`。
- **Application 平台接口**：各平台实现通过 `Application/src/Platform/include` 共享中立接口。应用宿主将平台返回结果应用到运行时启动选项；平台实现既不包含宿主私有头文件，也不负责启动错误报告。
- **Windows 启动器**：Windows 编辑器与游戏启动器共用 `Engine/PlatformHosts/Common` 下的源码，由 `WindowsLauncher.hpp` 暴露 `RunLauncher`，接收可执行文件相对路径与 `LauncherWorkingDirectory` 策略。编辑器启动 `Binaries\Ludork.exe` 并以启动器目录为工作目录；游戏启动 `Binaries\Main.exe` 并继承调用方工作目录。两者均透传参数、标准流与子进程退出码。C++ Source 模板保留该共享源码。

### Standard `ClassRuntime` 分层

Standard 的 `ClassRuntime` 依赖方向为 `Class → Composite → Instance → Native → Detail`，允许跨层向下调用：

- **Detail**：中立状态与查询。
- **Native**：原生槽位成员与属性。
- **Instance**：原生构造与销毁。
- **Composite**：索引与元表。
- **Class**：分配、终结与 `super`。

### 边界检查（`ImplBoundaryValidate`）

边界检查器负责核查 Engine 与 Application 的私有头文件（包括经由 include 搜索路径触及的父级私有头），验证 Standard 分层方向与无环性，并拒绝在第一方 Engine C++ 字符串与绑定注解中静态引用 `Source.*` 项目 Lua 模块路径或类型。静态检查不追踪动态拼接路径；通用原生服务所需的项目模块名由调用方传入。

CMake 的 `ImplBoundaryValidate` 目标会在构建目录记录检查通过标记，输入未变更时直接复用：

- **监视输入**：Source、Runtime、Standard 与 Application 源码树、Lua 运行时文件、LuaSF 头文件、编译后的 Toolchain 套件、检查构建规则，以及文件或目录的增删。
- **Lua Stub 与元数据**：增删 Lua Stub 会使缓存失效，仅刷新 Stub 内容不会；生成的 `*_meta.lua` 内容不计入输入。
- **失败与直接运行**：检查失败会清除成功标记并阻断构建，直至后续检查通过。直接执行 `ludork-check impl-boundary-check <project-root>`（包括原生 CI 中的调用）始终运行全量检查。修改检查器源码后，请先重新构建 Toolchain，再调用其编译产物。

### System 组合、线程与 `CellSize`

- **System 组件**：`System` 私有组合了 `Display`（窗口）、`FramePipeline`（画布、特效与转场目标）、`SceneStack`（排队操作与退役场景）以及 `Lifecycle`（关闭状态）。各组件对外暴露操作接口而非可变状态聚合。帧呈现执行在场景逻辑锁之外，渲染目标在帧间重建。
- **场景逻辑工作线程上下文**：在启用独立场景逻辑工作线程的宿主上，OpenGL 与 OpenGL ES 会为该线程创建与逻辑循环同生命周期的共享图形上下文。游戏线程重建摄像机渲染纹理时，工作线程上下文仍保持激活状态，场景逻辑锁负责串行化对共享渲染纹理的访问。详见 [SceneBase 线程规则](<../Lua 与蓝图脚本/全局与 Core 模块/Core Modules/GlobalCore/场景与系统.md#scenebase>)。
- **跨线程视频播放**：游戏循环运行期间，其他线程发起的同步视频播放请求会被排入游戏线程队列，调用线程等待直至播放完成或失败。
- **`EngineState::CellSize`**：为正整数 C++ 编译期常量，不支持项目级或运行时覆盖。修改此值需要重新构建引擎、编辑器与项目模板。

## 原生文本输入边界

Engine 通过 `Input/TextInputService.hpp` 管理编辑会话，平台宿主实现 `Input/TextInputHost.hpp`。双方契约采用 UTF-8 文本、位于字素边界上的字节偏移，以及以窗口客户区像素为单位的光标矩形。

宿主通过线程安全的 sink 上报带会话标识的事件。服务操作仅在游戏线程上或游戏线程启动前执行。Standard 借助 `utf8proc` 提供 Unicode 分段与空白字符处理。

## 原生 WebView 边界

Runtime 持有原生网页服务与 `Engine.OpenWebView(url)` 绑定。`Runtime/WebViewHost.hpp` 定义平台宿主工厂、窗口挂接与带会话标识的完成回调；`Runtime/WebViewService.hpp` 提供输入阻断能力。

- **生命周期**：工厂可在 VM 初始化前安装。`Display` 将宿主挂接到当前活动原生窗口，并在窗口替换或销毁前解除挂接。每次打开请求分配唯一 ID，宿主在现有图层上执行导航，因此旧请求的延迟完成不会关闭当前会话。被拒绝的请求保留既有页面与会话。
- **平台后端**：宿主异步执行 UI 操作，不阻塞游戏循环，也不在完成回调中调用 Lua。macOS 与 iOS 使用 `WKWebView`，Android 使用系统 WebView，HarmonyOS 使用 ArkWeb，Windows 使用系统安装的 Evergreen WebView2 Runtime。
- **HarmonyOS 输入隔离**：HarmonyOS 覆盖层根容器配置 `HitTestMode.BLOCK_HIERARCHY`，使内部的 Web 组件与关闭按钮接收触摸事件，同时阻止下层兄弟节点与祖先节点参与命中测试。游戏 `XComponent` 保持挂载在覆盖层下方。

## Core 头文件与 Runtime 边界

Core 的 Lua 绑定头文件从 `Engine/Runtime/include` 引入 `<CoreMinimal.hpp>`，以获取注解宏、运行时类型、常用 C++ 类型以及 SFML 的 Graphics、Window 与 System 模块。模块导出与直接类型依赖须显式包含，且每个公开头文件都必须可独立编译。

手写 Core 代码（包括私有源文件）只能通过 Runtime API 访问 VM 与绑定服务。LuaGlue API 调用仅限 Runtime 内部与生成绑定使用，预编译 LuaGlue 头文件不改变该源码边界。Runtime 同时负责隔离的音频执行，Core 保留玩法与播放策略。Runtime 内部在活动 `RuntimeScope` 中执行私有操作，由 Facade 构成对外入口边界。

关于 API 类型选择、容器所有权与 Lua 引用操作，请参阅[运行时值边界](<运行时值边界.md>)。

## 原生指针转换

`<CoreMinimal.hpp>` 已包含 `<Cast.hpp>`，底层头文件也可直接包含。[声明转换协议](<宏参考.md#原生转换声明>)后，使用 `ludork::Cast<T>(pointer)` 执行带检查的原生向下转换与横向转换，其中 `T` 为目标类名（不带 `*`）。静态可确定的向上转换可直接使用隐式转换或 `static_cast`；禁止用未经检查的 `static_cast` 替代动态类型检查。

- **指针语义**：支持裸指针与 `std::shared_ptr`，不提供引用转换或 `void` 目标重载。空输入或类型不匹配时返回空结果，完整保留 const 限定符与多重继承子对象偏移。`std::shared_ptr` 转换成功时与原指针共享控制块，右值重载仅在转换成功时转移所有权。
- **类型键**：动态类型查询在跨模块范围内按内容比对编译器生成的类型签名字符串。此类类型键仅用于同一工具链完整构建的内部识别，既非持久化 ID，也不构成跨工具链 ABI。

### 工具链套件与命令行入口

仓库初始化会将共享工具链准备至 `.tools/Toolchain`；已安装的编辑器与解压后的 BuildTools 包则位于 `BuildTools/Toolchain`。该目录包含六个命令族可执行文件（`ludork-build`、`ludork-codegen`、`ludork-assets`、`ludork-pack`、`ludork-editor` 与 `ludork-check`，Windows 平台带 `.exe` 后缀），共用同一运行时目录——复制或分发时必须保留完整目录。已发布工具无需系统 Python；从源码重建工具链需要 Python 3.12。

- **构建命令**：源码仓库与安装版中的 `build_cpp` 脚本均调用 `ludork-build native-build <project> <Debug|Release> --tools-directory <tools>`，统一负责配置、编译与发布成功构建记录。`build_preview_host` 调用同一命令并附带 `--target PreviewHost`，同时校验发布后的预览程序。共享的编辑器启动器与宿主 Lua 编译器任务见[共享构建任务](https://github.com/JasonLeon01/Ludork/blob/main/tools/README.md#shared-build-tasks)。
- **直接调用 CMake 与准备依赖**：平台脚本会自动定位 Toolchain。直接集成 CMake 时请传入 `-DLUDORK_TOOLCHAIN_DIRECTORY=/path/to/Toolchain`，IDE 配置生成入口同样支持 `--toolchain-directory`。如需单独准备某项原生依赖，可运行 `ludork-build dependencies <project-root> --repository-root <repository-root> --only <name>`（省略 `--only` 则准备全部依赖）；详见[工具链维护命令](https://github.com/JasonLeon01/Ludork/blob/main/tools/README.md#toolchain-maintenance-commands)。
- **编辑器工作流**：在编辑器中，**编译**会为 C++ Source 项目执行 Debug 构建。直接通过 CMake 构建后，需增量执行一次 `build_cpp` 以刷新**运行**所依赖的构建记录。修改第三方源码或外部 CMake 配置后同样需要执行**编译**或 `build_cpp`；详见[运行、调试与打包](<../编辑器用户指南/运行、调试与打包.md>)。
- **CI 运行器**：从对应版本 Release 下载 `Ludork-BuildTools-<version>-<platform>.tar.gz`，解压后在 `BuildTools/` 下运行构建或打包入口，并在构建机上安装项目所需的编译器与 SDK。

### Windows 编译器

Windows x64 游戏构建支持 MSVC、MinGW-w64 GCC 与 LLVM Clang（`clang-cl.exe`），完整覆盖 PreviewHost、启用 FFmpeg 的构建、Source 转 Standalone 以及游戏打包。涉及 GNU Make 与 Git Bash 的依赖构建环节（含 FFmpeg）仍需这两个工具；已安装编辑器在 `BuildTools/` 下自带 Toolchain 与 GNU Make。工具准备与编辑器打包沿用各自的标准工具链。

- **LLVM Clang 要求**：需要来自同一 LLVM 安装的 `clang-cl.exe`、`lld-link.exe` 与 `llvm-lib.exe`，以及 Visual Studio 2022 C++ 生成工具、Windows SDK 和位于 `PATH` 中的 Ninja。它借助 Ninja 目标 MSVC ABI 与运行库，无需安装 Visual Studio 的 ClangCL 集成组件。
- **显式选择编译器**：`build_cpp`、`build_preview_host`、`pack_standalone` 与 `pack_project` 会读取项目的[编译器设置](<../编辑器用户指南/项目设置与资产布局.md#mainproj>)，显式配置选定的 MSVC、MinGW 或 LLVM 工具链，而非从 `PATH` 继承其他编译器。若指定编译器缺失，构建直接失败且不会静默替换为其他安装。
- **切换编译器**：三种编译器均将 CMake 产物写入 `build`，运行时产物写入 `bin/<configuration>`。切换前请先在编辑器中使用[更改项目编译器](<../编辑器用户指南/运行、调试与打包.md#windows-项目编译器>)确认清理旧原生产物。若现有 CMake 缓存或构建记录属于另一编译器，命令行构建会直接失败且不删除任何文件；切勿在同一缓存中预先配置不同生成器或编译器。
- **MinGW 运行时文件**：MinGW 构建会将 `WebView2Loader.dll` 与所需的 GCC 运行库 DLL 一同发布至 `bin/<configuration>` 中的游戏与 PreviewHost 旁。可编辑 Standalone 项目与游戏包均在 `Binaries` 中携带这些文件，因此目标机器无需安装 MinGW（网页功能仍依赖系统已安装的 Evergreen WebView2 Runtime）。分发 MinGW 构建的游戏时，请随附运行库声明并按 `Licenses/NativeDependencies/MinGW-RUNTIME-NOTICE.md` 的说明提供编译器运行库源码分发材料。

> **注意**：当完整路径超过 Windows 传统路径长度上限时，即便父目录已存在，WinLibs GCC 14.2 仍可能无法创建生成的 `.obj.d` 文件。建议将 MinGW 项目创建在较短的根路径下，为生成的绑定文件名预留长度余量。

### 编译选项、RTTI、IPO 与预编译头

- **Debug 优化**：`LUDORK_OPTIMIZE_DEBUG` 默认为 `ON`，控制 Debug 优化，包括对 LuaSF 绑定对象与共享 LuaGlue 运行时启用 Debug IPO。LuaGlue 在所有构建配置中均执行参数类型与边界检查。
- **禁用 RTTI**：第一方 C++ 代码禁止使用 `dynamic_cast`、`std::dynamic_pointer_cast` 与 `typeid`。`Engine/cmake/LudorkCppOptions.cmake` 在所有配置中为 C++ 与 Objective-C++ 禁用 RTTI（MSVC 与 `clang-cl` 使用 `/GR-`，GCC、GNU 风格 Clang 与 AppleClang 使用 `-fno-rtti`），涵盖游戏、预览、关闭 Lua 的构建及源码编译依赖。LuaGlue 不依赖 RTTI 即可完成类型识别，异常处理保持启用。调整该策略后须整体重建所有原生模块；外部导入库与系统框架保留各自配置。
- **Release IPO 与符号可见性**：Release 构建为 Standard、其 `ClassRuntime` OBJECT 目标、移动端最终应用目标、Runtime 与 Core 启用 IPO/LTO（MinGW 保持禁用 IPO）。`ClassRuntime` 隐藏普通与内联符号，仅保留显式公共导出。
- **Release 链接与调试符号**：Apple 平台 Release 链接启用 `-dead_strip`；MSVC 与 LLVM Clang 通过 `/OPT:REF /OPT:ICF` 生成独立 PDB 文件；Android 与 HarmonyOS 启用工具链未引用节回收。诊断发布版本时请妥善保留未剥离的构建产物与调试符号——[打包](<../编辑器用户指南/运行、调试与打包.md#打包>)仅剥离最终发行产物。
- **预编译头（PCH）**：`LudorkStandard`、`LudorkStandardClassRuntime`、`LudorkRuntime`、`Engine`、`GlobalCore`、`GlobalFunctions`、`PreviewHostRuntime` 与 `PreviewHostExecutable` 默认启用 PCH。各目标按编译器、配置、架构与编译宏独立生成 PCH，严禁跨目标或跨构建变体复用。
- **PCH 内容与排除项**：启用 Lua 的构建预编译 `LuaSF.hpp` 与 `LuaGlue/LuaGlue.hpp`；`LUDORK_WITH_LUA=OFF` 构建预编译标准库头文件。Objective-C/Objective-C++ 源文件以及设置了单文件级 MSVC 或 `clang-cl` Debug 优化覆盖的文件均跳过 PCH。每个源文件仍须直接包含所需头文件，公开头文件也必须能独立编译。
- **生成绑定目标**：生成的 Core 绑定在内部 `EngineBindings`、`GlobalCoreBindings` 与 `GlobalFunctionsBindings` OBJECT 目标中编译，其 PCH 优先包含所属模块生成的转换特征。对象文件直接合入既有宿主库，不新增额外运行时库或 Lua 模块。在 macOS 上，单 arm64 架构的 AppleClang Release 构建对各绑定目标的 PCH 与生成源码使用 `-Os` 优化。
- **禁用 PCH**：执行 `cmake -S Game -B Game/build -DCMAKE_DISABLE_PRECOMPILE_HEADERS=ON`（替换为项目的实际源码与构建路径），随后运行 `build_cpp` 刷新**运行**所需的构建记录。关闭 PCH 后，生成绑定单元改为通过强制包含引入转换特征。将同一选项设回 `OFF` 即可重新启用 PCH。

### 第三方源码依赖

- **LuaSF 与 Lua**：LuaSF 仅作为绑定层，不持有 Lua VM 或其依赖。游戏运行时通过 `luaL_newstate` 与 `luaL_openlibs` 创建 `lua_State`，经 `LuaSF_initialize_state` 与 `LuaSF_register` 移交 LuaSF，并在结束时经由 `ludork::standard::shutdown` 与 `lua_close` 销毁。LuaSF 与 SFML 共用同一个 Lua 5.5 运行时；桌面构建共享 LuaGlue，移动端与 Web 目标静态链接。
- **源码目录覆盖**：CMake 默认从 `Game/Engine/ThirdParty` 读取 LuaSF、LuaGlue、SFML 与 Lua。可通过 `-DLUDORK_LUASF_SOURCE_DIR`、`-DLUDORK_LUAGLUE_SOURCE_DIR`、`-DLUDORK_SFML_SOURCE_DIR` 与 `-DLUDORK_LUA_SOURCE_DIR` 覆盖路径。LuaGlue 默认定位至所选 LuaSF 目录的同级目录（例如 `-DLUDORK_LUASF_SOURCE_DIR=/path/to/LuaSF-AutoGenerator/output/LuaSF`）。依赖初始化从同一压缩包安装 LuaSF 与 LuaGlue，并写入匹配的 `.ludork-version` 标记。
- **本地源码归档**：运行依赖初始化前，可设置 `LUASF_SOURCE_ARCHIVE`（Unix Shell 使用 `.tar.gz`，Windows 使用 `.zip`，且必须直接解压出 `LuaSF/` 与 `LuaGlue/`，旧版目录布局将被拒绝）或 `SFML_SOURCE_ARCHIVE`（`.zip` 或 `.tar.gz`，根目录须为 `SFML/` 且包含 `CMakeLists.txt` 与 `include/SFML/Config.hpp`）。显式导入会替换已安装源码，打包流程本身不会替换依赖。
- **SFML**：SFML 为必需的源码项目，其生成的 `sfml-*` 目标由 LuaSF 复用。移动端使用静态 SFML，桌面端遵循 `LUASF_BUILD_SHARED_SFML`（默认共享库）。`versions.conf` 指定 SFML 仓库与标签（当前为 SFML-ME `MRB3100`）。HarmonyOS GPU 粒子要求 SFML 源码保留 GLES 3 上下文请求，详见[通用粒子](<../编辑器用户指南/通用粒子.md>)。
- **IXWebSocket**：依赖初始化将 IXWebSocket 12.1.0 安装至 `Engine/ThirdParty/IXWebSocket`（在 `versions.conf` 中固定至提交 `bf7ad53c02612643e1cf72e37c8749491798d33d`）。`Engine/cmake/LudorkIXWebSocket.cmake` 为 GlobalCore 的可选 WebSocket 传输提供静态 `ixwebsocket::ixwebsocket` 目标，并在其作用域内关闭 TLS、消息压缩、示例、测试与安装步骤。
- **IXWebSocket 打包与传输**：C++ Source 模板与移动端打包保留 IXWebSocket 源码，发行包随附 `Licenses/IXWebSocket/LICENSE.txt` 与 `THIRD-PARTY.txt`。原生客户端接受 `http://` 配置并自动派生 `ws://`；Web 构建使用浏览器原生 HTTP/WebSocket 传输。详见[配置发行客户端](<../简易服务器/部署与编辑器设置.md#配置发行客户端>)。
- **Bindgen 与输出目录**：CMake 自动运行 `ludork-codegen core-bindgen`，详见[生成元数据与 Stub](<生成元数据与 Stub.md>)。模板不包含 `Intermediate/`，常规构建会自动重建该目录；`bin/` 与 `build/` 保留在项目根目录。

### 移动端与 Web 构建

- **Web（WebGL 2）**：使用 Emscripten 的 CMake 工具链配合 Ninja 构建，产物单独输出至 `build-web` 以区别于原生预览构建。运行时、Lua 模块与可选 FFmpeg 静态链接为单个 Wasm 模块，并复用 OpenGL ES 3 着色器转换路径。游戏借助 Asyncify 在浏览器主线程以协作方式推进后台任务，无需 pthreads 或跨源隔离响应头；自定义原生代码在耗时任务期间必须主动让出执行权，不得启动原生线程或依赖操作系统 socket。宿主会先恢复浏览器存储并准备音频，再在收到开始手势后进入 Lua。
- **Web FFmpeg**：`Engine/cmake/FFmpeg/build_web.sh` 将 MOV/H.264/AAC 软件解码器连同 `swscale` 与 `swresample` 编译为静态 Wasm 库，排除多线程、硬件加速、网络协议、编码器与命令行工具（Windows 平台需要 Git Bash 与 GNU Make）。详见 [WebGL 打包](<../编辑器用户指南/运行、调试与打包.md#webgl>)。
- **iOS**：采用单窗口 `UIScene` 宿主，由应用的 scene manifest 指定 scene delegate。宿主将窗口关联至 `UIWindowScene` 并在场景激活后启动运行时。场景临时断开时暂停活动运行时并保留窗口，供同一会话重新连接。应用与可选 FFmpeg 均以 iOS 16.3 为最低部署目标。
- **HarmonyOS 工具链**：在 Apple Silicon macOS 上通过 DevEco Studio 的 OpenHarmony 原生 SDK 进行交叉构建，每次打包均会重建 Stage 与原生构建目录。HAP 目标与兼容 SDK 均为 `6.0.2(22)`（`OHOS_COMPATIBLE_SDK_VERSION=22`），面向 `aarch64-linux-ohos22.0.0` 编译 Ludork、Lua、LuaSF、LuaGlue 与 SFML 并启用 API 可用性诊断（安装更新的编译 SDK 不会抬高最低部署目标）。
- **HarmonyOS 运行时与 FFmpeg**：应用在创建 GPU 资源前选择 OpenGL ES 3，在 Stage 清单中声明 `phone`、`tablet` 与 `2in1` 设备类型并请求 `ohos.permission.LOCK_WINDOW_CURSOR`。手机与平板默认横屏启动，二合一设备支持全屏与浮动窗口。启用 FFmpeg 的构建沿用同一带版本号的目标三元组、OpenHarmony sysroot、MUSL 选择与 API 可用性检查。
- **Android**：在 Apple Silicon macOS 上使用宿主机 CMake 3.28+ 与 `Unix Makefiles` 交叉构建，从本地 SDK 的 `ndk` 目录自动选取版本号最高的完整稳定 NDK 工具链（r27 及以上），并传入 `ANDROID_PLATFORM=android-24`、`ANDROID_ABI=arm64-v8a` 与 `ANDROID_STL=c++_static`。项目绝不自带 SDK 或 NDK，也不使用 Android Studio 自带的 SDK CMake 与 Ninja。Lua、LuaSF、LuaGlue、Runtime、Core、`cjson`、SFML 与可选 FFmpeg 全部静态链接进唯一的共享库输出 `libludork.so`，由 Gradle 作为预构建 `jniLibs` 条目打包。

## 加载运行时模块

```lua
local Engine = require("Engine")
local GlobalCore = require("GlobalCore")
local GlobalFunctions = require("GlobalFunctions")

local Components = GlobalFunctions.Components
local UI = GlobalFunctions.UI
local NodeGraph = GlobalFunctions.NodeGraph
local Manager = GlobalFunctions.Manager
```

请严格按照上述顺序加载这三个根模块。`GlobalFunctions` 的各个分组通过对应的表访问，不会泄漏至模块根。Standard 全局变量已由运行时预先安装；`CoreSystem` 不是运行时模块。
