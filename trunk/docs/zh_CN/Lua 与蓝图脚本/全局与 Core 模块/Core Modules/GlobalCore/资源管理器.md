# GlobalCore：资源管理器

通用管理器要求大小写精确的 `/Game/Assets/...` 路径，既能读取松散文件，也能读取 `.ldpak` 归档。原生绝对路径、`Assets/...` 路径和类别相对路径均无效。

归档压缩对这些 API 透明。可 seek 的流逐块解压，文件大小与字节位置均以原始数据为准。每个读取的块都校验 CRC32，完整读取还会校验文件 CRC32。

`AudioManager.setEffect(audioType, effect)` 接受 `Sound`、`Voice` 或 `Music`，为该类别后续的播放保存回调；传入 `nil` 清除回调，不影响已经播放的声源。回调签名为 `fun(source: sf.SoundSource, control: GlobalCore.AudioEffectControl, sampleRate: integer)`，其中 source 和 control 均不为 nil。每个新声源在播放前调用一次回调，传入当前播放设备的采样率。回调必须安装且只安装一个非空处理器；未安装或重复安装都会同步报错。

使用 Lua 处理器时，调用 `control:attachLuaProcessor(source, moduleName, resolverName, effectName, sampleRate)`。三个名称都是项目必须提供的字符串，原生层没有默认项目模块或解析函数。每次挂接都会创建独立 Lua 状态，通过 `require(moduleName)` 取得模块表，用 `effectName` 调用其中名为 `resolverName` 的函数，再以 `(nil, control, sampleRate)` 调用返回的 attacher，得到 `sf.SoundSource.EffectProcessor`。隔离状态中的 control 只暴露 `isCancelled()`、`beginTail()` 和 `finishTail()`，不能再次挂接处理器。模块加载、解析和处理器创建失败均同步向外传播，不会退回无处理器播放；后续音频回调中的错误通过 Manager 更新传播。

隔离状态使用 AudioManager 初始化时捕获的模块搜索路径，因此额外路径应在加载 `GlobalCore` 前配置。主状态中的闭包和对象不会传入音频状态。模块名称、解析函数和预设注册表由项目管理；内置预设、播放生命周期与取消规则见[默认玩法音频](<../../../Game 玩法/资源、音频、视频与特效.md#音频>)。

## TextureManager

`load` 同步返回已就绪的纹理。`request` 立即返回 `TextureLoadRequest`，文件读取、归档解压和图像解码在后台执行。运行中的 System 主循环将已解码图像上传到 GPU 后，才发布 Ready 状态。发出请求不代表纹理已经可以绘制；应在后续更新中检查句柄，不要用阻塞当前帧的循环等待。

### 函数与事件

| 名称 | 种类 | 参数 | 返回 | 执行语义与 metadata |
|---|---|---|---|---|
| `load` | `function` | filePath: string; sRGB: bool = false; area: sf.IntRect = nil; smooth: bool = false | return: sf.Texture | — |
| `request` | `function` | filePath: string; sRGB: bool = false; area: sf.IntRect = nil; smooth: bool = false; priority: int = 0 | return: GlobalCore.TextureLoadRequest | 仅 Lua；`metadata = false` |
| `getPath` | `function` | texture: sf.Texture | return: string or nil | 仅 Lua；`metadata = false` |
| `getMemory` | `function` | — | return: int | — |

`TextureManager.getPath(texture)` 按实际贴图实例查询管理器的当前缓存，返回原始资源路径。它不读取或加载文件，也不持有该贴图。管理器之外创建的贴图，或清理缓存后已不在其中的贴图，返回 `nil`。返回路径不包含 `load` 的 `area` 裁剪、sRGB 或平滑选项。

两种加载方式共享缓存和在途工作。精确路径、sRGB、area 与平滑选项共同区分缓存项，优先级不参与区分。同一缓存项的多个请求共用解码和上传，但各自获得独立的订阅句柄。缓存命中时立即为 Ready。同步 `load` 可以完成匹配的待加载请求，无需等待下一帧，因此也可以在 System 主循环启动前使用。失败结果不会被复用，新请求可以重新尝试加载。

### TextureLoadRequest

句柄在取消或释放前持有已就绪的纹理；其他调用者已取得的纹理引用仍有效。普通平台的管理器缓存使用弱引用，iOS 则保留强引用，直到缓存被清理。

| API | 约定 |
|---|---|
| `getStatus()` | 返回只读常量 `TextureLoadRequest.PENDING`（`"pending"`）、`READY`（`"ready"`）、`FAILED`（`"failed"`）或 `CANCELLED`（`"cancelled"`）。不等待，也不抛出已保存的加载错误。 |
| `getTexture()` | Ready 时返回 `sf.Texture`，Failed 时抛出保存的加载错误。Pending 与 Cancelled 抛出状态错误；此方法不会等待。 |
| `setPriority(priority)` | 修改当前 Pending 订阅的整数优先级。数值越大越优先，相同优先级按请求顺序处理。已完成、失败或取消的句柄不受影响。 |
| `cancel()` | 释放当前订阅，并将句柄设为 Cancelled；Ready 或 Failed 句柄也可取消。重复调用无副作用，之前取得的纹理仍有效。 |

这些方法和常量仅供 Lua 使用，不生成蓝图节点。纹理请求不是 `Engine.AsyncOperation`，不能传给 `asyncio.await`。在普通更新中查询状态；Ready 或 Failed 时调用 `getTexture()`，让必需资源的加载错误正常向外传播。

共用工作的优先级取当前 Pending 订阅中的最高值。取消或释放一个句柄不影响其他订阅者。最后一个订阅者离开后，排队工作会取消，在途结果会被丢弃；已经开始的解码或上传不会中断。运行时退出时，会取消未完成请求并等待解码线程退出，再关闭图形上下文。

服务使用两个解码线程。待上传的已解码像素积压达到 64 MiB 后，暂停启动新的后台解码，已经运行的解码仍可完成。每帧最多启动两次上传，同时采用 8 MiB 字节预算与 1 ms 时间预算。若本帧第一张纹理超过字节预算，仍允许上传以保证进度；已经开始的上传无法中断。这些是调度限制，不是帧耗时或总内存的硬上限：解码过程中还可能存在额外像素副本和编解码缓冲。即使 `area` 只选取较小的 GPU 纹理区域，积压仍按完整解码图像计算。移动端应用暂停时也暂停上传。
