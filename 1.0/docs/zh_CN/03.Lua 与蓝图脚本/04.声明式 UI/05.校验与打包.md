# 声明式 UI 校验与打包

## 目标

校验基于路径的 UI 声明，把原生 Preview 与运行时作对比，并在打包资产时去掉编辑器专用的预览数据。

## 外部修改后校验

UI JSON 在编辑器之外发生变更时，运行：

```text
ScriptTools ui-assets generate <project-root>
ScriptTools ui-assets validate <project-root>
ScriptTools ui-adapter-check <project-root>
```

`ui-assets generate` 同步生成的 View 与声明，并删除废弃的输出，不需要 Preview Host 或 Registry。改用 `--check` 则只报告缺失、过期或废弃的输出，不写入文件。生成文件的位置见[声明式 UI 编写工作流](<01.编写工作流.md#文件布局>)。

`ui-assets validate` 依据项目 Registry 校验资产。`ui-adapter-check` 与 `ui-preview validate` 都是只读检查。Adapter 校验把项目 JSON 与配套 Host 的编译描述作比较。

C++ Source 项目首次预览构建之前，以及在编译之前保存时，只检查与控件描述无关的结构，原生校验仍处于待定状态。这类检查使用 `ScriptTools ui-assets validate <project-root> --structure-only`。构建先产出预览产物，再执行完整的 UI 校验。资产无效会让构建失败，但已生成的预览仍可继续编辑。已有 Registry 的普通保存执行完整校验。

Standalone 通过 `ScriptTools ui-preview ensure <project-root>`、常规 UI 校验或 `ui-preview registry`，从随附的 Host 恢复缺失的预览 JSON。元数据损坏或不匹配、二进制缺失仍属错误。C++ Source 项目的预览产物不可用时必须重新构建，因为未完成或失败的原生构建无法自动恢复。

## 导出与生成文件

使用编辑器的 **导出** 操作，保存并校验项目、执行 Export Hook，再同步生成 UI View 与声明。运行会检查上次导出是否仍有效，内容变化时先询问再导出；编辑器每次打包都会完整导出一次。导出记录、按钮可用性与失败处理见[编译、导出与运行](<../../02.编辑器用户指南/08.运行、调试与打包.md#编译导出与运行>)。

普通保存、编译、直接命令行运行或打包，以及模板创建，都不生成 UI 文件。显式 `ui-assets generate` 命令仍可用于 UI 生成与检查，但不执行插件 Hook，也不发布完整的编辑器导出记录。直接命令行运行与打包要求预先导出文件，并保留原有校验。移动端打包配合 `--check` 时只执行预检。

三个 UI 生成目录均按整个目录忽略，并与生成的语言文件、导出记录一起排除在所有模板之外。模板保留其他声明，包括手写声明、通用数据声明与原生绑定声明，游戏包则排除整个 `Scripts/stub`；见[项目模板](<../../01.快速入门/02.项目模板.md>)。

## 校验层

保存、导出、原生预览、运行与打包都依据 [UI 资产 Schema 与 Control Registry](<04.资产 Schema 与 Control Registry.md>) 校验资产，并拒绝未知字段、资产内重复的节点名与别名路径。

## 原生预览与打包

Preview 需要兼容的协议、系统 adapter fingerprint 和完整的 Registry 摘要。移动端打包会为本机原生校验构建桌面 Preview，该 Preview 不会放进设备包。

打包校验 staging 副本，移除 `editor` 数据，再按配置编译、加密或归档，全程不改动项目的游戏资产。JSON、`.ldc` 与打包后的 Data 保持相同的无扩展名 UI key，打包后的 Controller 保持原有逻辑模块路径。

staging 校验通过 `--registry <source-project>/EditorCache/UiPreview.registry.json` 使用源项目的 Registry。Registry 属于开发产物，不进入玩家包。
