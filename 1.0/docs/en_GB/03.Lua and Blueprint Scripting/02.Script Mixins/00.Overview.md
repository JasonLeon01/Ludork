# Script Mixins Overview

A Script Mixin attaches a Lua behaviour table directly to a Blueprint class, so the Blueprint keeps editor-authored defaults and inheritance while its event logic stays in Lua. The runtime loads the selected module as `Mixins.<path-with-dots>` and turns its functions into methods on the generated Blueprint class. Mixin sources live beneath `Scripts/Mixins` as one runtime file plus a same-name `_meta.lua`, mirrored by `.d.lua` declarations under `Scripts/stub/Mixins` for Lua tooling.

## Recommended reading order

For a first mixin:

1. Read [Script Mixin Authoring Workflow](<01.Authoring Workflow.md>) to create the file pair beneath `Scripts/Mixins` and attach it to a Blueprint.
2. Read [Script Mixin Metadata](<04.Metadata.md>) to declare the editable fields that Blueprint instances expose.
3. Read [Script Mixin Runtime Contract](<02.Runtime Contract.md>) before writing methods, so the returned table stays within the reserved-name and `super()` rules.
4. Compare the result against [Game Script Mixins](<03.Game Mixins.md>).
5. Finish with [Script Mixin Validation and Packaging](<05.Validation and Packaging.md>), then place an instance on a map and verify the behaviour in a running game.

When something fails validation, start at [Script Mixin Validation and Packaging](<05.Validation and Packaging.md>). It describes the path, mode-chain and same-name metadata checks in the order the editor reports them, and asks you to resolve the first reported path or metadata error before examining downstream field errors. A reported metadata rule continues into [Script Mixin Metadata](<04.Metadata.md>).
