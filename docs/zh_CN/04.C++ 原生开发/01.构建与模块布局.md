# 构建与模块布局

当 Lua 与 Blueprint API 不足、需要新的原生 UI adapter，或需要生成 iOS/HarmonyOS/Android 构建时，使用 C++ Source 项目。运行时使用 C++20、CMake 与声明驱动绑定。

一份公开声明必须同时驱动 C++ 注册、LuaLS stub 与编辑器 metadata。不得修改生成输出，也不得在生成器内新增以玩法模块、类型或成员名为条件的分支。

## 目标

选择正确的原生模块，构建其生成绑定，并按受支持顺序加载生成的 Lua 模块。

## 前置条件

- 已安装 CMake、C++20 工具链及目标平台依赖的 C++ Source 项目。
- 面向目标平台的干净构建配置。
- 受支持的目标：Windows 10 或更高版本（x64）、macOS 13.3 或更高版本（Apple Silicon）、iOS 15.0 或更高版本（arm64）、HarmonyOS 6.0.2 / API 22 或更高版本（arm64-v8a），或 Android 7.0 / API 24 或更高版本（arm64-v8a）。

公开头文件包含普通 C++ 声明和编译期为空的 `BIND_*` 标记。构建时 Core bindgen 读取头文件，并生成按原生类稳定拆分的 sol2 注册源码、一个模块聚合/stub 源码、模块级 LuaLS stub 和编辑器 metadata。

## 步骤

### 1. 选择模块

| 模块 | 职责 | 原生依赖方向 |
|---|---|---|
| `CoreSystem` | 低层系统与工具函数 | 独立模块 target；使用 zlib |
| `Engine` | Engine 类型、服务、状态和玩法基础 | Core binding/Standard、SFML 与 zlib |
| `GlobalCore` | Global 游戏类与服务 | Engine、Standard 与 SFML；可选平台/FFmpeg 库 |
| `GlobalFunctions` | `Components`、`UI`、`NodeGraph`、`Manager` 自由函数组 | GlobalCore 与 SFML |

三个根玩法模块具有固定 Lua 加载顺序。`CoreSystem` 是独立模块，仅由确实需要它的代码加载；这并不表示 Engine 原生链接 CoreSystem target。`Engine` 与 `GlobalCore` 不反向链接 `GlobalFunctions`。公开签名跨模块时，应直接包含完整声明。

仅用于启动的原生模块由宿主负责：应用注册 `cjson` 与 `cjson.safe`，Standard 负责注册 `Class`，Engine 使用已初始化的原生 table 和 API，不建立反向模块链接。由资产和 metadata 驱动的动态模块解析保持不变。

完整的平台应用外壳位于 `PlatformHosts/Android` 与 `PlatformHosts/Harmony`。打包器在生成移动端包时复制这些 Gradle 与 Hvigor 宿主工程；`cmake` 目录仅保留项目 CMake 辅助逻辑与可选 FFmpeg 构建接线。

`UiPreviewHost` 与专用的 `UiPreviewHostRuntime` 动态库一起发布，不加载完整 Engine Lua 模块；C++ Source 工程仍构建和打包完整 Engine 模块。

### 2. 构建项目

```sh
./tools/build_cpp.sh Sample Debug
./tools/build_cpp.sh Sample Release
```

```bat
tools\build_cpp.bat Sample Debug
tools\build_cpp.bat Sample Release
```

CMake 会针对变化的公开头调用独立 `ScriptTools` 可执行文件的 `core-bindgen` 命令，其实现位于 `ScriptTools/core_bindgen`。Bindgen 会为每个绑定原生类在 build 目录写入稳定的 `<Module>.<NativeClass>.auto.cpp`；新增或删除类不会给无关类单元重新编号或改名。每个模块还只有一个 `<Module>.stub.auto.cpp`。这个文件同时承担模块聚合与生成 stub 写入职责：它负责模块级注册，并按绑定顺序调用各类单元。不会另外生成 `<Module>.auto.cpp`。

Bindgen 只在内容变化时写入各生成文件。因此，修改带注解头文件后，无关类源码保持不变，构建可复用它们的目标文件。模块级 LuaLS stub 与根 metadata 仍分别以单文件输出到 `Scripts`。

Android 打包是从 Apple Silicon macOS 执行的交叉构建。打包器使用本机 CMake 3.28 或更高版本与 `Unix Makefiles`，从本机 SDK 的 `ndk` 目录选择完整稳定版 NDK r27 或更高版本中的最高版本，并传入 `ANDROID_PLATFORM=android-24`、`ANDROID_ABI=arm64-v8a` 和 `ANDROID_STL=c++_static`。项目不会自带 SDK 或 NDK。Lua、LuaSF、Core、cjson、SFML 与可选 FFmpeg target 均为静态库；唯一共享输出为 `libludork.so`，Gradle 将其作为预构建 `jniLibs` 使用。此流程不使用 Android Studio SDK CMake 或 Ninja。

### 3. 加载运行时模块

```lua
local Engine = require("Engine")
local GlobalCore = require("GlobalCore")
local GlobalFunctions = require("GlobalFunctions")

local Components = GlobalFunctions.Components
local UI = GlobalFunctions.UI
local NodeGraph = GlobalFunctions.NodeGraph
local Manager = GlobalFunctions.Manager
```

以上三个根模块必须按所示顺序加载。`GlobalFunctions` 分组通过对应 table 访问，不得泄漏到模块根。需要独立系统模块的代码可以在这条三模块序列之外使用 `local CoreSystem = require("CoreSystem")`。

## 限制

成功构建模块不会使反向依赖合法。跨模块公开签名仍需完整声明，`CoreSystem` 仍位于固定玩法根加载序列之外。

按类稳定命名源码不会消除普通 C++ 头文件依赖。如果一个公开头声明了多个绑定类，修改该头可能会重新编译所有包含它的生成类单元；来自无关头文件的类仍保持稳定源码和目标文件。
