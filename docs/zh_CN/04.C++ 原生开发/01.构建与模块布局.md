# 构建与模块布局

Lua 与蓝图 API 无法满足需求、需要新增原生 UI adapter，或需要产出 iOS、HarmonyOS、Android 构建时，选择 C++ Source 项目。运行时使用 C++20、CMake 与声明驱动绑定。

## 目标

选对原生模块，构建其生成的绑定，并按受支持的顺序加载生成的 Lua 模块。

## 前置条件

- 已创建 C++ Source 项目，并安装 CMake、C++20 工具链及目标平台依赖。
- 面向目标平台准备一份干净的构建配置。
- 目标平台在支持范围内：Windows 10 或更高版本（x64）、macOS 13.3 或更高版本（Apple Silicon）、iOS 15.0 或更高版本（arm64）、HarmonyOS 6.0.2 / API 22 或更高版本（arm64-v8a）、Android 7.0 / API 24 或更高版本（arm64-v8a）。

公开头文件写普通 C++ 声明，另加编译期展开为空的 `BIND_*` 标记。Core bindgen 读取模块声明根与共享 Runtime 声明根，为每个类生成一份稳定的 LuaGlue 源码，再生成一份模块聚合与 stub 源码、一份 LuaLS stub 与编辑器 metadata。

`LUDORK_OPTIMIZE_DEBUG` 同时控制 LuaSF 绑定对象与共享 LuaGlue 运行时的 Debug 跨过程优化。

## 步骤

### 1. 选择模块

| 模块 | 职责 | 原生依赖方向 |
|---|---|---|
| `LudorkRuntime` | 值、VM/绑定服务、蓝图执行、类型与组件数据、JSON、Asset/Data/Script 存储，以及 GPU 粒子模拟与绘制 | Standard、SFML 与私有 zlib；完整模式另加 LuaSF；不得依赖 Core 模块 |
| `Engine` | Engine 类型、服务、状态与玩法基础 | LudorkRuntime 与 SFML |
| `GlobalCore` | 全局游戏类与服务 | Engine、Standard 与 SFML；可选平台库/FFmpeg |
| `GlobalFunctions` | `Components`、`UI`、`NodeGraph`、`Manager` 四组自由函数 | GlobalCore 与 SFML |

`LudorkRuntime` 在桌面端为共享库，在移动端为静态库，不暴露 Lua 根；绑定仍留在 `Engine` 下。AssetStore、DataStore 与 ScriptStore 划出只读的 Asset、Data 与 Lua 模块边界，松散目录布局与 `.ldpak` 布局都适用。Standard 只取得 DataStore 的文件访问权限，因此脚本归档不会出现在文件系统 API 中。私有 zlib 仅用于归档 CRC32。玩法模块的加载顺序固定，不反向链接 `GlobalFunctions`，并自带完整的跨模块声明。

`.ldpak` v1 为小端格式。`LDPK` header 保存版本、分组、条目数、索引范围与 CRC32。文件与目录索引按 UTF-8 字节排序，保存 64 位偏移、长度与数据 CRC32。原始正文按 8 字节对齐。

Runtime 负责蓝图类生成、脚本 Mixin、图执行与 latent 调度。Engine 提供 Actor 图查询、EventBus 与帧循环接入。`RuntimeProviders.installBlueprint(classDataByPath, compileGraph, instantiateGraphTemplate)` 安装三个蓝图回调。ClassDict 转发到 VM resolver。缓存与定义身份遵循[事件、公共函数与蓝图流程](<../03.Lua 与蓝图脚本/03.蓝图脚本/01.执行流、事件与变量.md#类定义与会话生命周期>)。

仅在启动阶段使用的原生模块归宿主所有：应用注册 `cjson` 与 `cjson.safe`，Standard 负责注册 `Class`，Engine 直接使用已初始化的原生 table 与 API，不建立反向模块链接。由资产与 metadata 驱动的动态模块解析保持不变。

`LUDORK_SAVE_AS_LDC` 是 CMake 选项，默认 `OFF`。Standard 在 Entry 运行前将其暴露为 `SAVE_AS_LDC`。C++ Source 打包通过**加密存档内容**设置该默认值。Entry 的覆盖方式遵循[运行时数据、配置与存档](<../03.Lua 与蓝图脚本/05.Game 玩法/06.运行时数据、配置与存档.md#存档>)。

游戏宿主位于 `Application/`（`include/` 与 `src/`）。Android 与 HarmonyOS 的应用外壳位于 `Engine/PlatformHosts/Android` 与 `Engine/PlatformHosts/Harmony`。构建支持位于 `Engine/cmake/`，`Engine/cmake/FFmpeg/` 下是 FFmpeg 构建。

游戏窗口样式统一定义在 `GlobalRuntime.cpp` 的 `runtimeWindowStyle()` 中。固定窗口策略传递给 SFML 窗口创建与重建、原生工作区尺寸计算以及 HarmonyOS ArkTS 宿主。平台适配层只将传入样式转换为窗口控件和边框尺寸，不再自行决定是否允许缩放。显示倍率与全屏仍属于运行时设置。

`LUDORK_WITH_LUA` 默认 `ON`，构建游戏时必须启用。项目的桌面预览目标不改动该设置。专用的 `UiPreviewHostRuntime` 用预览资源加载方式编译项目的 UI 实现。Host 不启动游戏，也不创建 Lua Controller。

游戏构建生成原生绑定，并通过项目 registry 校验 UI 资产。UI Lua View 与声明由编辑器 **导出** 或显式 `ScriptTools ui-assets generate <project-root>` 单独生成，构建不会生成它们。UI 生成器本身不要求桌面 Preview。[声明式 UI 编写工作流](<../03.Lua 与蓝图脚本/04.声明式 UI/01.编写工作流.md>)说明了生成代码与手写代码的归属。

源码预览与游戏二进制共用 `bin/<configuration>`。桌面构建产出[原生 UI Adapter](<08.原生 UI Adapter.md#项目预览产物>)中说明的项目预览产物。移动交叉构建使用显式提供的桌面 registry。

### 共享格式与渲染常数

`ScriptTools/runtime_formats.py` 统一声明 `.ldpak` 与加密载荷的布局、版本和编解码常数；`ScriptTools/resource_constants.py` 统一声明资源分组、路径和后缀。CMake 运行 `ScriptTools runtime-constants cpp <project-root> <output-directory>`，在 `Intermediate/<build-name>-<hash>/RuntimeConstants/LudorkGenerated` 生成中性的 C++ 头。原生使用方链接 `Ludork::RuntimeConstants`；实现层不通过包含父级 host 的私有头获取这些值。Engine 通过 `ResourceFileConstants` 暴露四个数据与动画后缀。

`Assets/Shaders/Global/UnoccludedLightPass.frag` 包含唯一的 `LUDORK_MAX_SHADER_LIGHTS` 定义，必须是 `1..256` 范围内的十进制整数，当前为 `64`。该上限来自合批灯光通道把每盏灯的索引放在顶点色 alpha 中，而该分量只占一个字节。生成器拒绝缺失、重复或无效的定义。改变该上限后，需要重新构建原生项目，使 shader、原生渲染器和只读的 `GlobalCore.Light.MAX_SHADER_LIGHTS` 保持一致。单独重新加载 shader 不会更新编译期上限。

游戏、桌面 Preview 和 `LUDORK_WITH_LUA=OFF` 构建都会执行生成。C++ Source 模板保留 shader 源码和构建配置，正常构建会重新生成这些头。生成头属于构建产物，不手工编辑，也不作为模板源码分发。

### GPU 粒子归属

Core 保留公开的 `Emitter`、`EmitterComponent`、`EmitterView` 和 Scene 调度接口。其 `EmitterConfiguration` 包含 `EmitterTrack` 值；每条轨道将 Runtime 的 `EmitterTrackParameters` 与 Core 的 `EmitterCurves` 组合，后者包含八个具名的 `Curve::CurveData` 通道。`setConfiguration` 集中校验这些值，通过现有 `Curve` 实现为每条轨道烘焙 256 × 8 个 float 的查找表，并重播。`Runtime/Graphics/GpuEmitterCurveLayout.hpp` 统一定义该布局：八个通道各有 256 个采样，打包为两行 RGBA。CPU 烘焙、GPU 纹理分配和生成的 shader 坐标共用这些采样数量与索引规则。`getConfiguration` 返回独立值副本。原有 ParticleSystem 仍留在 Core。

在 Emitter 路径中，`RuntimeData` 仅用于 Core 的 `EmitterResource.hpp/.cpp` 资源 JSON 输入和预览 JSON 消息边界。资源适配器将文件中的字符串选项、0–255 颜色、数组与曲线引用转换为固定配置字段。Emitter 保存该配置值，后端保存编译后的配置，两者都不以动态字典持有资源。资源文件与预览消息沿用已有 JSON Schema。

`Runtime/Graphics/GpuEmitterConfiguration.hpp` 传递 Runtime 轨道参数与烘焙后的曲线采样，不包含 Core 类型；`Runtime/Graphics/GpuEmitterBackend.hpp` 中未绑定的 `GpuEmitterBackend` 通过私有实现持有播放状态、固定模拟步、GPU 轨道、绘制、异步统计与 GPU 延迟释放。后端接收已解析的配置，不解释 `Data/Particles` 资源键，也不依赖 Core Curve、Actor 或 UI 类。`EmitterStatistics` 是 Runtime 值记录，`capacity`、`time` 必有，渲染器、存活数和计时结果为可选值。Core 直接返回该结构；Lua 绑定输出声明字段组成的快照表，不可用的可选值保留为 `nil`。

Core 的公开 `Emitter` 将播放操作转发给该后端。配置、轨道、曲线、爆发与统计记录各有独立同名头文件，Lua 注册与类型声明由正常绑定构建生成到 `Engine` 下。Runtime 不增加 Lua 根。

GPU 实现位于 `Runtime/src/Graphics/Emitters`；原始 OpenGL 函数、着色器、缓冲区/查询标识和 GPU 私有头都留在该目录。纹理读取复用 Runtime AssetStore 与 AssetInputStream，继续支持已有的松散目录与归档布局。Runtime 依赖 Standard 和 SFML，Core 只包含 Runtime 的公开 graphics 头。

Runtime 的 Graphics CMake 子目录在完整构建和 `LUDORK_WITH_LUA=OFF` 构建中各编译一次后端。UiPreviewHostRuntime 编译 Core 的资源适配与 UI 代码，链接同一个 Runtime 后端，不另编译一套 GPU 实现；继续使用既有 Runtime 库导出和预览打包规则。

共享 GPU 资源按活动的 SFML context ID 区分。Shutdown 将 GPU 对象加入延迟释放队列，不要求调用线程拥有上下文；回收在对应资源上下文激活时执行。Scene 和预览宿主继续持有窗口/渲染目标，并在销毁上下文前回收资源。该 GPU 生命周期独立于 Lua VM 生命周期。

### 会话与模块生命周期

Standard 持有 Lua 会话。`runtime::initialize` 要求 Standard 会话正在运行，重复调用会保留已挂接的 Runtime 状态。`runtime::shutdown` 卸载 Runtime 之后，重新启动需要新的 Standard 会话与 Lua VM。

Standard 按依赖逆序关闭各模块（Global、Engine、Runtime），再释放自身状态。Lua VM 归宿主所有，宿主必须在发起关闭的线程上等待 shutdown 结束，之后才能调用 `lua_close`。

AssetStore、DataStore、ScriptStore 与 Standard 的只读文件 provider 属于宿主配置。它们独立于 VM 会话，会话关闭后依然保留。

Standard 在每个宿主 Lua 入口建立 LuaGlue 执行范围。只有宿主确认当前线程仍持有 VM 锁、且执行 hooks 未变化时，嵌套胶水操作才可复用该范围。`LuaExecutionPause` 会暂停这份所有权；暂停期间的操作必须重新获取锁。未提供所有权探针的宿主继续使用普通 enter/leave hooks。

### 宿主与实现源码

每个独立类或绑定类型使用同名头文件，必要时再加同名源文件。公开声明放在 `include` 下，成员定义放在 `src` 下。宿主专用的数据类型可以内嵌。共享数据与辅助集合可以集中存放。

宿主私有实现放在 `src` 下，使用 `Impl` 后缀，例如定义 `Host::Impl` 的 `HostImpl.hpp`。较大的实现可以改用同名子目录，通过 `target_sources` 贡献源码。依赖由宿主流向它的实现。子目录不得包含父目录的私有头，也不能借 include 搜索路径绕过；公开头文件不得包含私有头文件。

Runtime 的共享 Lua 服务位于 `Runtime/src/LuaServices`。纯 ConfigVars 解析位于 `Runtime/src/Metadata`。

Standard 的 ClassRuntime 依赖方向为 `Class → Composite → Instance → Native → Detail`，允许跨层向下跳转。每一层各管一件事：

- Detail 管中立状态与查询。
- Native 管 native 成员与属性。
- Instance 管 native 构造与析构。
- Composite 管索引与元表。
- Class 统筹分配、终结与 super。

边界检查覆盖 Standard，拒绝向上层包含、父目录私有头包含，以及由这些边形成的循环。

System 私有组合 Display、FramePipeline、SceneStack 与 Lifecycle。Display 持有窗口。FramePipeline 持有画布、特效与转场目标。SceneStack 持有排队操作与已退役场景。Lifecycle 持有关闭状态。组件对外暴露操作，而不是可写状态聚合。帧呈现仍在场景逻辑锁之外完成，渲染目标逐帧重建。

每个 Scene 逻辑线程都在自身线程上创建并释放独立的共享图形上下文。该上下文覆盖整个逻辑循环的生命周期，因此渲染线程重建 Camera 渲染纹理时，不会销毁逻辑线程当前使用的上下文。共享渲染纹理的访问仍由场景逻辑锁串行化。

`EngineState::CellSize` 是正的 C++ 编译期常量。编辑器构建通过 ScriptTools 由该声明生成对应的 `EngineConstants.CellSize`。改动它需要重建引擎、编辑器与模板。不存在项目级或运行时覆盖入口。

### 编辑器桥接边界

Standard 持有由 `LUDORK_COMMAND_PORT` 选择的 localhost TCP 编辑器桥接。协议使用换行分隔的 JSON 与 `v` 字段，编辑器和运行时的版本必须一致。控制台命令、注入输入、关闭、控制开关、文本输入与 `liveDebug` 共用这条连接；性能遥测和 UiPreviewHost 保留各自独立的协议。

`Engine.EditorLiveDebug` 是 Lua 入口，见 [EditorLiveDebug](<../03.Lua 与蓝图脚本/08.全局与 Core 模块/02.Core Modules/01.Engine/12.事件与模块根.md#editorlivedebug>)。Standard 在既有 `System::updateRuntime()` 帧边界、持有场景逻辑锁时调用已安装的 handler。网络线程不调用 Lua，也不修改地图对象。窗口焦点不影响该执行边界。

`liveDebug` 请求包含 `v = 1`、`type = "liveDebug"`，以及非空字符串 `requestId` 和 `run`。其他字段原样传给 Lua handler。handler 返回一个响应 table；受保护分发将请求或编码错误转成失败响应。地图上下文与 Actor 实例校验由游戏 handler 负责。

较大的响应可以拆成多条线协议消息，接收方拼齐后再解码。断线丢弃待发数据。handler 注册仍属于当前 VM，直到替换、卸载或关闭。

### 原生文本输入边界

Engine 通过 `Input/TextInputService.hpp` 持有编辑会话。平台宿主实现 `Input/TextInputHost.hpp`。契约使用 UTF-8、字素边界上的字节偏移，以及以窗口客户区像素为单位的光标矩形。宿主通过线程安全的 sink 回传带会话标记的事件。服务操作在游戏线程上运行，或在游戏线程启动之前运行。Standard 通过 utf8proc 提供 Unicode 分段与空白处理。

Windows 嵌入式游玩时，HWND 与 IME 上下文留在编辑器进程内。嵌入式文本 Host 通过编辑器桥接协议交换带会话标记的文本、组合事件与客户区像素光标矩形，绝不从游戏进程去子类化编辑器的 HWND。编辑器与运行时的桥接版本必须一致。断开连接会关闭编辑会话，保留已提交文本，丢弃组合内容。重新连接不会重开会话。

### 原生 WebView 边界

Runtime 持有原生网页服务及 `Engine.OpenWebView(url)` 绑定。`Runtime/WebViewHost.hpp` 定义平台宿主工厂、窗口挂接与带会话标识的完成回调；`Runtime/WebViewService.hpp` 提供输入阻断。工厂可在 VM 初始化前安装。Display 将宿主挂到有效原生窗口，并在替换或销毁窗口前解除挂接。每次打开请求使用新 ID，宿主在已有层上导航；旧请求的延迟完成不会关闭当前会话。拒绝请求时保留原网页和会话。

平台宿主异步执行 UI 操作，不在游戏循环中等待网页，也不从完成回调调用 Lua。macOS 与 iOS 使用 WKWebView，Android 使用系统 WebView，HarmonyOS 使用 ArkWeb，Windows 使用系统已安装的 Evergreen WebView2 Runtime。

HarmonyOS 覆盖层根容器使用 `HitTestMode.BLOCK_HIERARCHY`：内部 Web 和 Close 按钮接收触摸事件，同时阻止较低层级的兄弟节点与祖先节点参与触摸测试。游戏 XComponent 在覆盖层下方保持挂载。

### Core 头文件与 Runtime 边界

Core 的 Lua 绑定头从 `Engine/Runtime/include` 引入 `<CoreMinimal.hpp>`，以获得注解、运行时类型、常用 C++ 类型以及 SFML 的 Graphics、Window、System 模块。模块导出与直接类型依赖须显式包含。每个公开头文件都必须能独立编译。

手写 Core（包括私有源码）通过 Runtime 访问 VM 与绑定服务，不直接或间接依赖 sol。Runtime 还负责隔离的音频执行，Core 保留玩法与播放策略。生成的绑定可以使用 sol。Runtime 内部在活动 `RuntimeScope` 中使用私有操作。Facade 构成对外入口边界。

API 类型、容器所有权与 Lua 引用操作的选择见[运行时值边界](<09.运行时值边界.md>)。

### 原生指针转换

`<CoreMinimal.hpp>` 已包含 `<Cast.hpp>`；底层头文件也可直接包含它。[声明转换协议](<04.宏参考.md#原生转换声明>)后，使用 `ludork::Cast<T>(pointer)` 执行带检查的原生向下或横向转换；`T` 是目标类，不带 `*`。静态可确定的向上转换可使用隐式转换或 `static_cast`；不得用未经检查的 `static_cast` 替代动态类型检查。

支持裸指针与共享指针。空输入或类型不匹配时返回空结果；保留 const，并正确处理多重继承的子对象地址偏移。共享指针转换成功时与原指针共用控制块，右值重载仅在成功时转移所有权。不提供引用转换或 `void` 目标重载。

查询与动态类型识别跨模块按内容比较编译器生成的类型签名字符串。这些类型键仅用于同一工具链完整构建的内部识别，不是持久化 ID 或跨工具链 ABI。

### 2. 构建项目

```bash
./tools/build_cpp.sh Game Debug
./tools/build_cpp.sh Game Release
```

```text
tools\build_cpp.bat Game Debug
tools\build_cpp.bat Game Release
```

编辑器的 **编译** 会对 C++ Source 项目执行这次 Debug 构建。**运行** 只在从未成功完成 Debug 构建时不可用；第一方原生输入过期时，会询问 **编译后运行**。修改 Lua、UI 或 locale 不要求 **编译**；`Main.proj` 的 FFmpeg 开关属于原生构建输入。编辑器的 **运行** 与 `build_cpp` 共享该按配置区分的记录；直接 CMake 构建不会发布记录，之后执行一次增量 `build_cpp` 即可。第三方目录和外部 CMake cache 设置不属于检查范围，修改后需主动执行 **编译** 或 `build_cpp`。编辑器流程见[运行、调试与打包](<../02.编辑器用户指南/08.运行、调试与打包.md>)。

`LUDORK_OPTIMIZE_DEBUG` 默认 `ON`，控制 Debug 优化。LuaGlue 在所有配置中检查参数类型和边界。

第一方 C++ 禁止使用 `dynamic_cast`、`std::dynamic_pointer_cast` 与 `typeid`。`Engine/cmake/LudorkCppOptions.cmake` 在所有配置中关闭 C++ 与 Objective-C++ 的 RTTI：MSVC 使用 `/GR-`，GCC、Clang 与 AppleClang 使用 `-fno-rtti`。该策略覆盖游戏、Preview、关闭 Lua 的构建、从源码编译的依赖与独立的 Windows 编辑器启动器。LuaGlue 的类型识别不依赖 RTTI，异常处理保持启用。修改该策略后须一起重建所有原生模块；导入的预编译库与系统框架保留自身设置。

Release 构建为 Standard、它独立的 ClassRuntime OBJECT target 与移动端最终应用 target 启用 IPO/LTO，与 Runtime、Core 保持一致；MinGW 仍禁用 IPO。ClassRuntime 隐藏普通符号与内联符号，同时保留显式的公共导出。Apple 平台的游戏应用、Standard、Runtime 与 Core 在最终 Release 链接时使用 `-dead_strip`；MSVC 保留独立 PDB 与 `/OPT:REF /OPT:ICF`，Android 和 HarmonyOS 使用工具链的未引用节回收。这些 Release 设置不改变 Debug 优化或公共 Lua API。诊断发布版本时，应保留匹配的未剥离构建产物及生成的调试符号文件；[打包](<../02.编辑器用户指南/08.运行、调试与打包.md#打包>)只剥离对应平台的最终发行产物。

macOS 单 arm64 架构的 AppleClang Release 构建对生成的 Core 绑定源码使用 `-Os`；手写运行时以及其他平台、架构和配置保留原有优化等级。

构建前先在本地验证宿主到实现的依赖方向：

```bash
.tools/ScriptTools/ScriptTools impl-boundary-check Game
```

```text
.tools\ScriptTools\ScriptTools.exe impl-boundary-check Game
```

开发命令使用 `.tools/ScriptTools` 下的完整运行时目录；已安装编辑器把它放在 `tools/ScriptTools`，入口为 macOS 的 `ScriptTools` 或 Windows 的 `ScriptTools.exe`。移动或复制时需保留整个目录，包括库文件和 `runtime-versions.txt`；安装后的工具不需要系统 Python。

该命令从宿主源码及其同名目录发现 C++ 边界。Lua 边界使用对应的宿主文件或模块目录约定；带有镜像 `.d.lua` 的子模块本身算作独立宿主。CMake 以 `ImplBoundaryValidate` target 暴露同一份验证，并让 Engine 依赖它。Windows 与 macOS CI 在原生输入验证期间也会直接运行该命令。违规会报告源文件与行号，因此不需要第二份边界清单。该检查还会拒绝手写 Core 中的 LuaGlue 用法以及解析出的间接 LuaGlue include。

仓库根目录的 `.clang-tidy` 用于检查手写 C++。执行 `clang-tidy <source.cpp> -p <build-directory>`，该构建目录须含 `compile_commands.json`，并记录实际目标的编译参数，包括 RTTI 开关。不要把生成文件或第三方文件选为待检查的主翻译单元。Visual Studio 生成器不导出该编译数据库。

LuaSF 只是绑定器：它既不持有 Lua VM，也不持有依赖。游戏运行时用 `luaL_newstate` 与 `luaL_openlibs` 创建 `lua_State`，通过 `LuaSF_initialize_state` 和 `LuaSF_register` 交给 LuaSF，并经由 `ludork::standard::shutdown` 与 `lua_close` 销毁。

CMake 从 `Game/Engine/ThirdParty` 下的对应目录读取 LuaSF、LuaGlue、SFML 与 Lua。可用 `-DLUDORK_LUASF_SOURCE_DIR`、`-DLUDORK_LUAGLUE_SOURCE_DIR`、`-DLUDORK_SFML_SOURCE_DIR`、`-DLUDORK_LUA_SOURCE_DIR` 覆盖。LuaGlue 默认使用所选 LuaSF 源码的兄弟目录，因此本地生成器联调可设置 `-DLUDORK_LUASF_SOURCE_DIR=/path/to/LuaSF-AutoGenerator/output/LuaSF`。依赖初始化从同一个源码包安装两个工程并写入一致的 `.ludork-version` 标记。

SFML 是必需的源码工程而不再是可选覆盖项，LuaSF 会复用 Ludork 由它构建出的 `sfml-*` target。移动平台使用静态 SFML，桌面跟随 `LUASF_BUILD_SHARED_SFML`，默认共享库。`versions.conf` 通过仓库与标签选择 SFML 变体，当前固定为 SFML-ME 的 `310-ME-OH-GLESVER` 标签。OHOS GPU 粒子要求 SFML 源码保留 GLES 3 上下文请求，详见 [通用粒子](<../02.编辑器用户指南/10.通用粒子.md#gpu-支持与性能验收>)。

依赖初始化前可设置 `LUASF_SOURCE_ARCHIVE` 选择本地源码包：shell 入口使用 `.tar.gz`，Windows 使用 `.zip`。源码包必须直接解压为 `LuaSF/` 与 `LuaGlue/`，旧源码布局会被拒绝。两个工程复用同一个 Lua 5.5 运行时；桌面共享 LuaGlue，移动目标静态链接。

CMake 自动运行 `ScriptTools core-bindgen`。生成的 C++ 文件放在顶层 `Intermediate/` 目录下，按构建目录与模块分组。LuaLS stub 与 metadata 写入 `Scripts`。输出与重新生成细节见[生成 Metadata 与 Stub](<05.生成 Metadata 与 Stub.md>)。

模板不包含 `Intermediate/`；目录缺失时，正常构建会重新创建。`bin/` 与 `build/` 仍留在项目根目录。

HarmonyOS 打包是通过 DevEco Studio OpenHarmony native SDK 从 Apple Silicon macOS 发起的交叉构建。每次打包都重建 Stage 与原生构建目录，因此 CMake cache 无法跨设备形态或图形后端复用。HAP target 与 compatible SDK 都是 `6.0.2(22)`，CMake 收到 `OHOS_COMPATIBLE_SDK_VERSION=22`。工具链据此为 `aarch64-linux-ohos22.0.0` 编译 Ludork、Lua、LuaSF、LuaGlue 与 SFML，并启用 API availability 诊断。安装了更新的 SDK 时，它只作 compile SDK 使用，不会抬高该 deployment target。

Mobile 变体配置 `SFML_HARMONY_DEVICE_FORM=MOBILE` 与 `SFML_OPENGL_ES=ON`，声明 `phone` 与 `tablet`，使用固定横屏移动宿主。2in1 变体配置 `SFML_HARMONY_DEVICE_FORM=2IN1`，只声明 `2in1`。它们支持 `fullscreen` 与 `floating` 窗口，发布 `NEED_OPENGL=1`，请求 `ohos.permission.LOCK_WINDOW_CURSOR`，并按后端设置 `SFML_OPENGL_ES=OFF`（OpenGL）或 `ON`（OpenGL ES）。启用 FFmpeg 的 HarmonyOS 构建在 C/C++ 编译与链接阶段使用同一个带版本 compiler target，同时保留 OpenHarmony sysroot、MUSL 选择与 availability 检查。

2in1 OpenGL 二进制硬依赖 `libGLv4.so`。镜像缺少该库时，动态加载器会在原生初始化之前拒绝 NAPI 模块。该二进制不会切换到 OpenGL ES。

Android 打包是从 Apple Silicon macOS 发起的交叉构建。打包器调用本机 CMake 3.28 或更高版本，使用 `Unix Makefiles`，从本机 SDK 的 `ndk` 目录中选取找到的最高完整稳定版 NDK r27 或更高版本，并传入 `ANDROID_PLATFORM=android-24`、`ANDROID_ABI=arm64-v8a` 与 `ANDROID_STL=c++_static`。项目从不自带 SDK 或 NDK。Lua、LuaSF、LuaGlue、Runtime、Core、cjson、SFML 与可选的 FFmpeg target 均为静态库。唯一的共享输出是 `libludork.so`，Gradle 将其作为预构建的 `jniLibs` 条目使用。流程不使用 Android Studio 的 SDK CMake 与 Ninja。

### 3. 加载运行时模块

```lua
local Engine = require("Engine")
local GlobalCore = require("GlobalCore")
local GlobalFunctions = require("GlobalFunctions")

local Components = GlobalFunctions.Components
local UI = GlobalFunctions.UI
local NodeGraph = GlobalFunctions.NodeGraph
local Manager = GlobalFunctions.Manager
```

这三个根模块必须按上面的顺序加载。`GlobalFunctions` 的各个分组通过对应 table 访问，不得泄漏到模块根。Standard 全局已经安装完毕。`CoreSystem` 不是运行时模块。
