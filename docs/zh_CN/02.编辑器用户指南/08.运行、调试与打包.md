# 运行、调试与打包

## 目标

运行项目并获得可操作的诊断信息，测试原生可执行文件，并为受支持的目标平台产出完整发行包。

## 编译、导出与运行

工具栏按钮按 **编译 → 导出 → 运行** 排列，Standalone 项目隐藏编译按钮。**编译** 保存项目并构建 Debug 游戏程序与预览运行时，完成后不启动游戏。原生绑定仍随构建生成，UI 与本地化则通过独立的导出操作生成。

**导出** 保存并校验项目，执行 Export 插件 Hook，生成 UI View 与声明，然后在 `EditorCache/ProjectExport.json` 中记录成功结果。Official Locale Tools 通过该 Hook 导出工作簿。记录在重新打开项目后仍有效，记录内容指纹覆盖 UI JSON、参与窗口声明生成的 Lua 模块与手写声明、插件声明的输入、生成文件、生成器与导出插件。输入新增、修改或删除，输出缺失或被改写，以及生成器或导出插件变化，都要求重新导出。导出期间输入发生变化、导出失败或取消时，本次操作不会发布成功记录。

变量与通用数据仍在保存时生效，其 Lua 文件继续受版本管理，不属于导出范围。普通保存、编译、直接运行和模板创建不生成 UI 文件。显式 `ui-assets generate` 命令只生成 UI 文件，不执行 Export Hook，也不发布完整的编辑器导出记录。

项目必须有成功的导出记录，C++ Source 还必须有成功的 Debug 构建记录，运行按钮才可用。两者都缺少时，提示优先要求编译，然后才是导出。Standalone 只要求导出。**编译** 和成功完成 Debug 构建的 `tools/build_cpp` 都会发布共享构建记录；直接调用 CMake 不会发布该记录。

项目根目录的 `EditorCache/` 集中保存编译与导出记录、UI 预览元数据、编辑器地图目录缓存以及默认的动画 MP4 输出，并由 Git 忽略。删除其中的记录后，C++ Source 需要重新编译，所有项目需要重新导出，才可运行。CMake 构建目录仍是 `build/`，运行时动画缓存仍位于游戏用户数据目录的 `Cache/Animations`。

已有记录后，内容过期不会直接禁用运行按钮。点击运行时先检查编译，原生源码或产物过期时询问 **编译后运行**；再检查导出，输入或输出过期时询问 **导出后运行**。任一步骤取消或失败都会结束本次运行。运行会保存并校验项目、执行 before-Run Hook，实际启动前再次按编译、导出的顺序检查，准备期间的变化也需要同样的确认。仅修改 Lua、UI JSON、游戏数据或本地化内容不要求原生编译。源码编辑和窗口重新获得焦点不会触发后台检查。

每个项目预热并复用只读检查进程。预热不扫描文件内容，每次请求检查时仍重新比较当前文件内容；取消检查或关闭项目会释放该进程。

运行准备期间与游戏运行中，该按钮变为 **停止**，点击可取消准备或停止当前进程。编译与导出期间禁止重复操作和项目编辑。游戏自然退出、取消和失败都会恢复编辑，关闭项目会取消活动中的准备操作。

**独立窗口** 使用单独的游戏窗口，并保留编辑器中当前地图或大地图的画面。准备、编译与导出期间，项目编辑、已打开的文档窗口、撤销/重做及编辑快捷键均不可用。运行时默认保持这些限制；只有在运行前开启 **实时调试**，才按下文规则开放临时编辑。控制台、性能监视器与帮助仍可使用。嵌入模式则在编辑器内部显示 Windows 运行时，并锁定游戏视口布局。只有 Windows 可以配置这一窗口选择，其他平台始终使用独立窗口。Windows 上无法取得嵌入句柄时，会以 `EmbeddedHandleUnavailable` 失败。

操作对话框和控制台报告失败。导出失败会阻止运行或打包继续；先修复首个校验、Hook 或生成错误，再重新导出。

## 实时调试

运行前开启 **编辑 → 开发工具与设置 → 实时调试**，即可从编辑器修改正在运行的地图。该项目偏好默认关闭，准备或运行期间不能修改。它仅适用于 **独立窗口**；切换到嵌入模式会将其清除并禁用。准备、编译与导出仍保持原有编辑锁定。

游戏运行后，编辑器跟随玩家所在的普通地图，或组合式大地图中的当前子地图，禁止手动切换地图。大地图空洞、尚未加载完成的地图、没有存活玩家的场景，以及连接不可用时均为只读。**文件浏览器** 可以浏览和定位资源，但项目文件的新建、重命名、移动、删除以及文档编辑仍被禁止。

在已有的可编辑图层上，实时调试允许：

- 使用与[项目地图编辑](<03.图块集、自动图块与地图.md#图层与绘制>)相同的图块画笔：绘制、擦除、取样和填充。图层结构、显隐、图块集绑定、地图属性、灯光及大地图摆放保持锁定。
- 选中和删除存活 Actor，包括玩家、运行时生成的 Actor 与子 Actor，并移动顶层 Actor。编辑器不能新增、粘贴或复制 Actor。
- 查看 **角色信息** 并修改普通变量。**组件**、父类、蓝图身份和地图 tag 保持只读。

Actor 的位置、生成、销毁以及所查看的变量值会随游戏更新。移动 Actor 会取消其当前移动路线；删除使用正常 Actor 销毁及既有生命周期回调。隐藏 Actor 按[地图预览规则](<03.图块集、自动图块与地图.md#灯光与-actor>)保留检查能力，隐藏图层仍只读。实时编辑不支持撤销/重做，不写入项目文档，也不会把项目数据标为已修改。

**世界大纲** 将子 Actor 嵌套在其当前父 Actor 下。在地图上单击或拖动子 Actor，会选中其所属的顶层 Actor；拖动时由该顶层对象带着全部后代一起移动。可在 **世界大纲** 中单独选择子 Actor，检查或修改普通变量，或通过正常生命周期删除它。禁止直接移动子 Actor，包括修改 **角色信息** 中的坐标。

修改属于存活的 Actor 或地图实例。只要同一实例仍存在，修改就会保留，包括大地图的休眠实例；销毁、换图或卸载之后，不会向重建实例重放这些修改。重建使用项目定义和正常玩法持久化记录。游戏存档保持正常工作，可能保存受到实时编辑影响的玩法状态；此模式保护项目源数据，不隔离存档槽。

点击停止、游戏自然退出或启动失败后，会恢复项目地图视图和运行前选中的地图，并丢弃临时快照。焦点位于编辑器时，**独立窗口** 中的游戏仍继续运行。

## 运行中重载 Lua

在外部编辑器保存改动过的 Lua 源文件，在控制台输入 `$r`，再按 `Enter` 或点击 **发送**。这会更新已有函数，同时保留场景、对象和运行时状态。游戏必须由编辑器启动，并使用散放的 Lua 源文件。

控制台会报告结果。数据或模块结构的变化可能需要重启；支持的改动范围与失败处理见 [Lua 热更新](<../03.Lua 与蓝图脚本/01.Lua 运行时与模块.md#lua-热更新>)。

## 测试层次

- 保存之前校验改动过的蓝图。
- 在编辑器中测试地图，并让控制台输出保持可见。
- 用性能监视器查看帧与逻辑耗时。
- 在编辑器之外运行原生可执行文件，以发现对工作目录的假设。
- 测试打包产物，因为它的可写设置与资产布局都和编辑器模式不同。

## 打包

选择 **文件 → 打包项目**，选定目标平台并跟进打包日志。项目必须有有效的入口脚本和兼容的模板。在 `Scripts/Entry.lua` 顶层只定义一个 `local APP_NAME`，赋值为非空的静态字符串字面量，使用该游戏专用的名称，不包含控制字符，也不在之后重新赋值。打包会拒绝示例值 `LudorkSample`、缺失的定义，以及需要执行 Lua 才能确定名称的表达式。

移动端和 macOS 的应用显示名称使用 `Data/Configs/System.json` 中 `title.value` 的原始文本。标题必须非空且不包含控制字符，打包不解析本地化键。`APP_NAME` 用于生成稳定的 application ID、bundle identifier，以及经过文件名净化的 `<game-name>` 名称主体。修改标题或版本不改变应用的安装身份；修改 `APP_NAME` 可能需要重新配置签名或 provisioning。

编辑器每次打包都会先完整导出一次，包括 Export Hook 与 UI 生成，成功后继续执行 before-Pack Hook 和打包。Official Locale Tools 的 before-Pack Hook 只排除 `Data/Locale/Locale.xlsx`。直接使用命令行运行或打包时，需要预先导出文件；这些命令保留原有校验，但不执行完整导出，也不隐式生成 UI。

**加密游戏数据** 控制脚本编译，以及 shader、JSON 和存档加密；只勾选其中一部分时，复选框显示为不确定状态。**加密存档内容** 设置 C++ Source 运行时的默认值。Standalone 项目通过 `Scripts/Entry.lua` 中的 `SAVE_AS_LDC` 配置它；生效时机与格式规则见[存档](<../03.Lua 与蓝图脚本/05.Game 玩法/06.运行时数据、配置与存档.md#存档>)。`.ldpak` 选项与加密相互独立。

打包要求项目提供有效的预览 registry；构建与恢复要求见[声明式 UI 校验与打包](<../03.Lua 与蓝图脚本/04.声明式 UI/05.校验与打包.md>)。

最终化流程用源项目 registry 校验一份暂存副本，然后应用插件排除项以及所选的编译、加密与归档。它会移除开发文件、预览专用二进制和项目根目录的 `EditorCache`/`Cache`，同时保留游戏共用的依赖。`Assets`、`Data` 或 `Scripts` 内部名为 `EditorCache` 或 `Cache` 的目录仍属于普通项目内容。

### 发行版本与内部测试包

在打包窗口设置 **发行版本**。C++ Source 项目还会显示 **内部测试包（dev）**。窗口读取 `Main.proj` 的 `packaging.version`，并对 C++ Source 项目读取 `packaging.dev`，默认值分别为 `"1.0.0"`、`false`。确认有效参数后保存版本及适用的 dev 设置，取消不写入。Standalone 项目始终保存 `packaging.dev=false`，包括旧项目原先为 `true` 的情况。版本使用 `1.0.0` 或 `0.1.0` 这样的三段非负十进制整数，总长度不超过 127 字节，不允许 `v` 前缀、前导零、日期或预发布后缀；发行版本不在 Entry 中定义。

所有游戏打包命令均接受 `--version 1.0.0` 和 `--release`。C++ Source 项目还接受 `--dev`；传入渠道选项只在本次打包覆盖 `packaging.dev`。Standalone 项目始终按正式版打包，忽略旧配置中的 `packaging.dev=true`，并拒绝显式传入的 `--dev`。命令行不回写项目配置。

打包开始时取一次 UTC+8 时间，所有阶段复用该时间。正式包的完整发行标识等于基础版本；dev 包在其后追加 `YYYYMMDDHH`，例如在 `2026-01-01T07:00:00+08:00` 打包，`1.0.0` 得到 `1.0.0.2026010107`，使用本次打包开始时冻结的时间。dev 不改变 Release 优化、签名、加密或安装身份。

| 平台字段 | 两种模式共用的值 | 上述时间的示例 |
|---|---|---|
| Android/HarmonyOS `versionName`；Apple `CFBundleShortVersionString` | 基础版本 | `1.0.0` |
| Android/HarmonyOS `versionCode` | `YYMMDDHH` 整数 | `26010107` |
| iOS/macOS `CFBundleVersion` | `YYMM.DD.HH` | `2601.1.7` |

构建日期限定为 2000–2099 年，替换已有输出前会校验平台上限。同一小时重新打包视为同一构建号，需要新的商店构建记录时应在下一小时打包。产物路径在原有平台、架构、变体和签名后缀前使用 `<game-name>-<full-version>`。重新打包同一标识会替换对应产物，其他版本及无关文件保留。

打包暂存区会生成 `Data/BuildInfo.json`，包含 `version`、`fullVersion`、`dev` 和 `builtAt`（带 `+08:00` 的 ISO 8601 时间）。该文件随既有 Data 加密与 `.ldpak` 流程进入产物，不写回源项目 Data。应用发行版本独立于[存档 schema 版本](<../03.Lua 与蓝图脚本/05.Game 玩法/06.运行时数据、配置与存档.md#存档>)。

编辑器自身的安装包独立遵循相同的标识规则。计划任务和 GitHub 手动触发的编辑器包使用 dev；只有 `v*` tag 触发的包使用 release。两种编辑器包内的 Standalone 模板都保持正式版设置。编辑器基础版本来自仓库 `versions.conf` 中的 `EDITOR_VERSION`，**关于 Ludork** 窗口显示当前安装包的完整发行标识。相关仓库命令见 [tools/README.md](../../../tools/README.md)。

### 散放与归档

所有平台默认都把运行时文件、`Assets`、`Data` 与运行时 `Scripts` 作为散放目录保留。`.ldpak` 选项默认不勾选；勾选后，三个目录的完整内容分别成为根级 `Assets.ldpak`、`Data.ldpak` 与 `Scripts.ldpak`。归档条目保留相对于原目录的路径，因此资源路径、Data 路径与 Lua 模块名都保持不变。加密与 Lua 编译在归档之前执行；归档本身不会加密其内容，该选项也与加密相互独立。移动端发行包执行同样的散放或归档契约，且 Android 与 HarmonyOS 都不会重新压缩 `.ldpak`。

资源打包会拒绝符号链接、大小写冲突、非法路径和输出冲突。一个发行包要么同时包含三个散放目录（`Assets`、`Data`、`Scripts`），要么同时包含三个根级归档。损坏的归档、缺少根目录、布局混用以及旧式的分组归档都会被拒绝。

最终化流程还会移除仅供开发使用的 `Scripts/stub` 目录树。`Scripts` 下若还留有其他 `.d.lua` 文件，打包就会失败。

### Windows 与 macOS

Windows 输出为 `dist/<game-name>-<full-version>/Main.exe`，同目录包含所需运行时文件。macOS 输出为 `dist/<game-name>-<full-version>.app`，应用显示名称取 System 标题。指定自定义输出目录时，该目录替代 `dist`，作为发行包的父目录。发行包目录及其祖先目录不得是符号链接或目录联接。

Windows 与 macOS 发行包复制运行时文件、`Assets`、`Data` 与运行时 `Scripts`。Standalone 发行包在根部保留启动器，并把运行时二进制放在平台包目录中（Windows 为 `Binaries`，macOS 应用的 `Contents/Frameworks`）。适用时会附带 FFmpeg 声明与源码提供材料；发行要求见 [FFmpeg 选项](<../01.快速入门/02.项目模板.md#ffmpeg-选项>)。Windows 发行包排除 PDB 文件，应将它们与对应构建一起保留用于调试。

macOS 打包对 C++ Source 与 Standalone 项目执行相同的处理：使用 `strip -x` 移除最终 app 中 Main 可执行文件和真实动态库文件的本地原生符号，跳过符号链接。调整依赖路径后，打包器为这些二进制逐个进行 ad-hoc 临时签名；资源最终化后，再使用配置的签名身份签名并验证整个 app，未配置时仍使用 ad-hoc 临时签名。剥离或签名失败会中止打包。源构建产物、Standalone 模板和共享预览库保持未剥离状态。

选择 macOS 后会出现 **签名应用**，默认不勾选。保持不勾选时使用本机环境变量中配置的签名，例如 `LUDORK_MACOS_SIGNING_IDENTITY`、`LUDORK_MACOS_SIGNING_CERTIFICATE` 与 `LUDORK_MACOS_NOTARY_*` 公证凭据；都没有配置时应用只获得 ad-hoc 临时签名。勾选后可以选择 `.p12` 证书并填写口令、可选的签名身份，以及可选的公证：Apple ID 配合 Team ID 与专用口令，或 App Store Connect 密钥配合密钥 ID 与 Issuer ID。编辑器把这些值作为命令行参数传入，并在本次运行中忽略环境变量，因此以对话框内容为准。公证要求真实的签名身份，会先提交给 Apple、等待结果并装订票据；ad-hoc 身份会被拒绝。选择同一证书后会自动恢复已保存的签名信息。临时签名不能替代发行方的证书签名与公证。

macOS 签名器先处理嵌套代码及各应用包 `Contents/MacOS` 下的所有普通文件，再签名应用包和主程序，包括编辑器包内的 .NET 程序集与配置文件。非 Mach-O 文件的签名保存在扩展属性中，因此复制已签名应用时必须保留这些属性；编辑器 DMG 打包器会从挂载后的镜像再次校验应用签名。 内嵌 ScriptTools 运行时先按原清单校验，二进制签名后重新生成文件清单，最后签名外层应用包，确保两项完整性校验都对应最终内容。 使用 Developer ID 签名时，`Contents/Resources` 中的工具和模板可执行文件同样启用 Hardened Runtime。公证失败会输出提交 ID，并在可用时获取 Apple 的详细日志。

查询 CI 公证提交时，在 GitHub Actions 手动运行 **Query macOS Notarization**。`submission_id` 留空可查看近期提交历史，填写提交 UUID 可查看其状态及处理完成后的公证日志。流程复用仓库公证 Secrets，不重新构建或提交包。Apple 结果显示在查询步骤日志中；workflow 成功仅表示查询成功，不代表公证通过。

### iOS

在 macOS 上选择 iOS 15.0 或更高版本的目标，需要 C++ Source 项目、带 iPhoneOS SDK 的完整 Xcode 安装，以及已完成首次启动设置的 Xcode。选择 iOS 后会出现 **签名应用**，默认不勾选。保持不勾选时使用已登录的 Apple Development 团队，设置了 `LUDORK_IOS_DEVELOPMENT_TEAM` 时以它为准，并由 Xcode 自动签名。勾选后可以填写 Team ID、`.p12` 证书与其口令，以及 `.mobileprovision` 描述文件；打包器随后使用该身份与描述文件手动签名，并拒绝团队或 application identifier 不匹配的描述文件。编辑器把这些值作为命令行参数传入，并在本次运行中忽略环境变量。证书与描述文件必须同时提供，选择同一证书后会自动恢复已保存的记录。

Xcode 会在签名前移除最终 Release 应用的非全局符号，不会单独剥离参与链接的静态库。

默认情况下，iOS 打包只生成 `dist/<game-name>-<full-version>.ipa`，无需连接任何 iPhone。勾选 **导出到 iPhone** 后，还会把应用安装到设备上并启动。该模式要求 iPhoneOS 平台上恰好有一台物理设备，iPhone 或 iPad 均可，且 `xcdevice` 报告它可用。模拟器不符合要求。解锁、信任或开发者模式之类的提示都来自设备本身。安装之后，设备还必须信任开发者描述文件，目前该问题会表现为签名错误。

### HarmonyOS

HarmonyOS 打包需要 C++ Source 项目、Apple Silicon 的 macOS，以及带 OpenHarmony native SDK 的 DevEco Studio。所有 HarmonyOS 变体都使用 HarmonyOS 6.0.2 / API 22。面向 OpenGL ES 的手机与平板宿主请选择 **Mobile**；或选择 **2in1**，再选 OpenGL（默认）或 OpenGL ES。

不导出到设备时，打包器会在 `dist` 中生成一个 arm64-v8a 的未签名 HAP：`<game-name>-<full-version>-harmony-mobile-unsigned.hap`、`<game-name>-<full-version>-harmony-2in1-opengl-unsigned.hap` 或 `<game-name>-<full-version>-harmony-2in1-opengl-es-unsigned.hap`。勾选 **导出到匹配的 HarmonyOS 设备** 后，改为生成对应的 `-signed.hap`，并把它安装到设备上启动游戏。设备导出会打开 DevEco Studio，最多等待三分钟以完成自动签名与设备端确认，然后才写入签名后的 HAP。Mobile 导出接受上报为 `default`、`phone` 或 `tablet` 的已连接设备，尽管 Mobile HAP 自身声明的是 `deviceTypes: ["phone","tablet"]`。2in1 导出只接受 `2in1`。必须恰好有一台已连接设备与所选形态匹配，另一形态的设备可以保持连接。已连接设备的类型无法读取时，即使它属于另一形态，也会中止导出。2in1 OpenGL 包要求设备上存在 `libGLv4.so`，部分模拟器没有提供。应用会报告模块缺失，而不会回退到 OpenGL ES，因此在这些映像上请改用 OpenGL ES 包。

`Licenses` 以及根目录的许可证与声明文件并不是 HAP 格式的前置条件：存在时打包器会一并包含，缺失时也不会拒绝项目。

Hvigor 在生成各个 Release HAP 变体时、签名前剥离原生库；打包器不会对已签名 HAP 再次剥离。应保留匹配的原生构建产物用于调试。

### Android

只有当 macOS 上的 C++ Source 项目检测到 Android Studio 安装在 `/Applications` 或当前用户的 `Applications` 目录时，才会显示 Android 打包。它要求 SDK Platform 36、Build Tools 36.0.0、本机安装的 SDK 下完整且稳定的 NDK r27 或更高版本工具链，以及本机 CMake 3.28 或更高版本。打包器从该 SDK 的 `ndk` 目录中挑选版本最高且合格的 NDK。项目包与编辑器包都不携带 SDK 或 NDK。随后打包器使用本机 CMake 配合所选工具链，把 Android Studio 自带的 JBR 设为 `JAVA_HOME`，并使用项目 `Engine/PlatformHosts/Android` 模板内由引擎维护的 Gradle wrapper。该 wrapper 会下载 Gradle 9.5.0 与 Android Gradle Plugin 9.3.0，并运行 `:app:lintRelease :app:assembleRelease`。APK 声明的最低版本为 API 24（Android 7.0），因此可安装在 Android 7.0 及更高版本上；它的 `compileSdk` 与 `targetSdk` 均为 36。它把应用标识为游戏，并请求由传感器决定方向的横屏，因此两个横屏方向都受支持。Android 打包从不调用 SDK Manager、AVD 或 `adb`；无论签名与否，都不会安装或启动 APK。

选择 Android 后会出现 **签名 APK**，默认不勾选。保持不勾选时发布 `dist/<game-name>-<full-version>-android-arm64-v8a-unsigned.apk`。勾选后可以选择 JKS 或 PKCS12 keystore，填写它的 alias 与密码，并可选地把这些信息保存在本机。选择器接受 `.keystore`、`.p12`、`.pfx` 和 `.pkcs12` 文件，并自动识别类型。key 密码默认与 keystore 密码相同；已保存的记录会自动恢复 keystore 路径与 alias。取消该对话框会回到 Pack Options；签名成功时只发布 `dist/<game-name>-<full-version>-android-arm64-v8a-signed.apk`。

保存的记录位于编辑器的当前用户设置目录中，即 `Ludork.ini` 旁边的 `android-signing.json`，macOS 上则在 `~/Library/Application Support/Ludork` 下。记录只保存 keystore 路径与 alias，密码交由操作系统的凭据存储保存。密码永远不会写入项目、Gradle 文件或日志。Android 平台本身要求更新已安装应用时使用相同的签名证书，因此用不同密钥签名的更新会被设备拒绝。

Android 资源使用带 SHA-256 manifest 的 APK assets，以及带版本号的运行时目录，同时保留该平台原生的二进制布局。生成的工程使用顶层 `Licenses` 中的运行时文本，而不是编辑器声明。

Gradle 打包之前，NDK 的 `llvm-strip --strip-unneeded` 会处理暂存的 `libludork.so`，原生构建的原始输出保持未剥离状态，用于调试。

## 失败检查清单

导出、运行或打包中途停止时，先读对应的失败对话框、控制台或打包日志中第一个可操作的错误。依次检查插件 Hook、`Main.proj`、入口脚本、JSON 语法、蓝图校验、生成的原生模块与缺失的资源。若提示拒绝访问路径（Access to the path is denied），先关闭输出目录的资源管理器窗口以及仍在运行的上一份游戏，然后重试；语言服务或杀毒扫描占用生成的 Lua 或二进制文件也会导致同样的错误。Android 签名失败时，核对 keystore 路径、alias 与密码，并在对话框中修正已失效的保存值。macOS 与 iOS 签名失败时，核对证书、签名身份、描述文件与公证凭据，并在签名对话框中清理已失效的保存值。打包无法修复无效的项目引用，也不能替代针对目标平台的测试。
