# 运行、调试与打包

## 目标

运行项目并获得可操作的诊断信息，测试原生可执行文件，并为受支持的目标平台产出完整发行包。

## 运行模式

Play 控件按当前选定的开发模式启动项目。**独立窗口** 使用单独的游戏窗口，嵌入模式则把 Windows 运行时托管在编辑器内部。只有 Windows 可以配置这一选择：其他平台一律使用独立窗口，那里的 **独立窗口** 设置处于禁用状态。在 Windows 上，无法取得嵌入游戏面板句柄时，运行会以 `EmbeddedHandleUnavailable` 失败。更换原生二进制之前，先停止当前进程。

编辑器先执行 before-run 插件 Hook，按需构建 C++ 目标，带上编辑器的启动参数拉起运行时，并打开命令通道。Hook、构建或协议握手任一失败都会弹出 **运行失败** 对话框，控制台则收到子进程输出的各行内容。

## 运行中重载 Lua

保存改动过的 Lua 源文件，在控制台输入 `$r`，再按 `Enter` 或点击 **发送**。这会更新已有函数，同时保留场景、对象和运行时状态。游戏必须由编辑器启动，并使用散放的 Lua 源文件。

控制台会报告结果。数据或模块结构的变化可能需要重启；支持的改动范围与失败处理见 [Lua 热更新](<../03.Lua 与蓝图脚本/01.Lua 运行时与模块.md#lua-热更新>)。

## 测试层次

- 保存之前校验改动过的蓝图。
- 在编辑器中测试地图，并让控制台输出保持可见。
- 用性能监视器查看帧与逻辑耗时。
- 在编辑器之外运行原生可执行文件，以发现对工作目录的假设。
- 测试打包产物，因为它的可写设置与资产布局都和编辑器模式不同。

## 打包

选择 **文件 → 打包项目**，选定目标平台并跟进打包日志。项目必须有有效的入口脚本和兼容的模板。打包之前，把 `Scripts/Entry.lua` 中 Game 项目的 `APP_NAME = "LudorkSample"` 换成该游戏专用的名称，因为打包脚本会拒绝默认值。输出文件名使用 `<game-name>`，它取自 `Data/Configs/System.json` 中经过净化的游戏标题，而不是 `APP_NAME`，所以只改 `APP_NAME` 不会改变输出文件名。Official Locale Tools 通过 before-pack Hook 导出 `Locale.xlsx`；底层打包脚本自己不会执行这一步导出。

**加密游戏数据** 控制脚本编译，以及 shader、JSON 和存档加密；只勾选其中一部分时，复选框显示为不确定状态。**加密存档内容** 设置 C++ Source 运行时的默认值。Standalone 项目通过 `Scripts/Entry.lua` 中的 `SAVE_AS_LDC` 配置它；生效时机与格式规则见[存档](<../03.Lua 与蓝图脚本/05.Game 玩法/06.运行时数据、配置与存档.md#存档>)。`.ldpak` 选项与加密相互独立。

打包要求项目提供有效的预览 registry；构建与恢复要求见[声明式 UI 校验与打包](<../03.Lua 与蓝图脚本/04.声明式 UI/05.校验与打包.md>)。

最终化流程用源项目 registry 校验一份暂存副本，然后应用插件排除项以及所选的编译、加密与归档。它会移除开发文件、预览专用二进制和项目根目录的 `Temp`/`Cache`，同时保留游戏共用的依赖。`Assets`、`Data` 或 `Scripts` 内部名为 `Temp` 或 `Cache` 的目录仍属于普通项目内容。

### 散放与归档

所有平台默认都把运行时文件、`Assets`、`Data` 与运行时 `Scripts` 作为散放目录保留。`.ldpak` 选项默认不勾选；勾选后，三个目录的完整内容分别成为根级 `Assets.ldpak`、`Data.ldpak` 与 `Scripts.ldpak`。归档条目保留相对于原目录的路径，因此资源路径、Data 路径与 Lua 模块名都保持不变。加密与 Lua 编译在归档之前执行；归档本身不会加密其内容，该选项也与加密相互独立。移动端发行包执行同样的散放或归档契约，且 Android 与 HarmonyOS 都不会重新压缩 `.ldpak`。

打包会拒绝符号链接、大小写冲突、非法路径和输出冲突。一个发行包要么同时包含三个散放目录（`Assets`、`Data`、`Scripts`），要么同时包含三个根级归档。损坏的归档、缺少根目录、布局混用以及旧式的分组归档都会被拒绝。

最终化流程还会移除仅供开发使用的 `Scripts/stub` 目录树。`Scripts` 下若还留有其他 `.d.lua` 文件，打包就会失败。

### Windows 与 macOS

Windows 与 macOS 发行包复制运行时文件、`Assets`、`Data` 与运行时 `Scripts`。Standalone 发行包在根部保留启动器，并把运行时二进制放在平台包目录中（Windows 为 `Binaries`，macOS 应用的 `Contents/Frameworks`）。适用时会附带 FFmpeg 声明与源码提供材料；发行要求见 [FFmpeg 选项](<../01.快速入门/02.项目模板.md#ffmpeg-选项>)。在 macOS 上，签名与公证由发行方负责。

### iOS

在 macOS 上选择 iOS 15.0 或更高版本的目标，需要 C++ Source 项目、带 iPhoneOS SDK 的完整 Xcode 安装，以及已完成首次启动设置的 Xcode。编辑器不会要求提供签名身份：打包器会自动选用已登录的 Apple Development 团队并为应用签名。

默认情况下，iOS 打包只生成 `dist/<game-name>.ipa`，无需连接任何 iPhone。勾选 **导出到 iPhone** 后，还会把应用安装到设备上并启动。该模式要求 iPhoneOS 平台上恰好有一台物理设备，iPhone 或 iPad 均可，且 `xcdevice` 报告它可用。模拟器不符合要求。解锁、信任或开发者模式之类的提示都来自设备本身。安装之后，设备还必须信任开发者描述文件，目前该问题会表现为签名错误。

### HarmonyOS

HarmonyOS 打包需要 C++ Source 项目、Apple Silicon 的 macOS，以及带 OpenHarmony native SDK 的 DevEco Studio。所有 HarmonyOS 变体都使用 HarmonyOS 6.0.2 / API 22。面向 OpenGL ES 的手机与平板宿主请选择 **Mobile**；或选择 **2in1**，再选 OpenGL（默认）或 OpenGL ES。

不导出到设备时，打包器会在 `dist` 中生成一个 arm64-v8a 的未签名 HAP：`<game-name>-harmony-mobile-unsigned.hap`、`<game-name>-harmony-2in1-opengl-unsigned.hap` 或 `<game-name>-harmony-2in1-opengl-es-unsigned.hap`。勾选 **导出到匹配的 HarmonyOS 设备** 后，改为生成对应的 `-signed.hap`，并把它安装到设备上启动游戏。设备导出会打开 DevEco Studio，最多等待三分钟以完成自动签名与设备端确认，然后才写入签名后的 HAP。Mobile 导出接受上报为 `default`、`phone` 或 `tablet` 的已连接设备，尽管 Mobile HAP 自身声明的是 `deviceTypes: ["phone","tablet"]`。2in1 导出只接受 `2in1`。必须恰好有一台已连接设备与所选形态匹配，另一形态的设备可以保持连接。已连接设备的类型无法读取时，即使它属于另一形态，也会中止导出。2in1 OpenGL 包要求设备上存在 `libGLv4.so`，部分模拟器没有提供。应用会报告模块缺失，而不会回退到 OpenGL ES，因此在这些映像上请改用 OpenGL ES 包。

`Licenses` 以及根目录的许可证与声明文件并不是 HAP 格式的前置条件：存在时打包器会一并包含，缺失时也不会拒绝项目。

### Android

只有当 macOS 上的 C++ Source 项目检测到 Android Studio 安装在 `/Applications` 或当前用户的 `Applications` 目录时，才会显示 Android 打包。它要求 SDK Platform 36、Build Tools 36.0.0、本机安装的 SDK 下完整且稳定的 NDK r27 或更高版本工具链，以及本机 CMake 3.28 或更高版本。打包器从该 SDK 的 `ndk` 目录中挑选版本最高且合格的 NDK。项目包与编辑器包都不携带 SDK 或 NDK。随后打包器使用本机 CMake 配合所选工具链，把 Android Studio 自带的 JBR 设为 `JAVA_HOME`，并使用从内置 SFML 示例中复制出的 Gradle wrapper。该 wrapper 会下载 Gradle 9.5.0 与 Android Gradle Plugin 9.3.0，并运行 `:app:lintRelease :app:assembleRelease`。APK 声明的最低版本为 API 24（Android 7.0），因此可安装在 Android 7.0 及更高版本上；它的 `compileSdk` 与 `targetSdk` 均为 36。它把应用标识为游戏，并请求由传感器决定方向的横屏，因此两个横屏方向都受支持。Android 打包从不调用 SDK Manager、AVD 或 `adb`；无论签名与否，都不会安装或启动 APK。

选择 Android 后会出现 **签名 APK**，默认不勾选。保持不勾选时发布 `dist/<game-name>-android-arm64-v8a-unsigned.apk`。勾选后可以选择 JKS 或 PKCS12 keystore，填写它的 alias 与密码，并可选地把这些信息保存在本机。选择器接受 `.keystore`、`.p12`、`.pfx` 和 `.pkcs12` 文件，并自动识别类型。key 密码默认与 keystore 密码相同；已保存的记录会自动恢复 keystore 路径与 alias。取消该对话框会回到 Pack Options；签名成功时只发布 `dist/<game-name>-android-arm64-v8a-signed.apk`。

保存的记录位于编辑器的当前用户设置目录中，即 `Ludork.ini` 旁边的 `android-signing.json`，macOS 上则在 `~/Library/Application Support/Ludork` 下。记录只保存 keystore 路径与 alias，密码交由操作系统的凭据存储保存。密码永远不会写入项目、Gradle 文件或日志。Android 平台本身要求更新已安装应用时使用相同的签名证书，因此用不同密钥签名的更新会被设备拒绝。

Android 资源使用带 SHA-256 manifest 的 APK assets，以及带版本号的运行时目录，同时保留该平台原生的二进制布局。生成的工程使用顶层 `Licenses` 中的运行时文本，而不是编辑器声明。

## 失败检查清单

运行或打包中途停止时，先读 **运行失败** 对话框、控制台或打包日志中第一个可操作的错误。依次检查插件 Hook、`Main.proj`、入口脚本、JSON 语法、蓝图校验、生成的原生模块与缺失的资源。Android 签名失败时，核对 keystore 路径、alias 与密码，并在对话框中修正已失效的保存值。打包无法修复无效的项目引用，也不能替代针对目标平台的测试。
