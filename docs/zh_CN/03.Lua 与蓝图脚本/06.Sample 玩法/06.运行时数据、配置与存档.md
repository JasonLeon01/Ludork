# 运行时数据、配置与存档

## 配置

`Data/Configs` 保存游戏配置 JSON，`Main.ini` 保存可变启动和用户设置。应使用配置 API 与编辑器字段，使未知 section/key 在读写后仍被保留。

编辑器模式下，`LUDORK_EDITOR=1` 选择项目内 `Main.ini`。普通打包运行使用平台用户数据目录，并在适用时以打包配置作为初始来源。

Android 发行包会在原生运行时启动前，把不可变运行时资源镜像到 `filesDir/ludork/runtime/<runtime-hash>`。可变配置与存档使用 `filesDir/ludork/user-data`；它们不会写回带版本的运行时目录，也不需要外部存储权限。

## 运行时状态

不可变定义放在 Blueprint、Config 或 General Data 文件中；可变游戏状态放在游戏实例、Actor 或组件上。不要把临时状态写回源码 JSON。

### 游戏变量

Game Variable Manager 生成 `Scripts/Source/Configs/GameVariables.lua` 作为已声明的“名称→初始值”映射，并生成 `GameVariables_meta.lua` 保存仅供编辑器使用的类型、顺序与可选备注 schema。其 `bool`、`int`、`float`、`string`、`list` 与 `dict` 选项分别映射为 metadata 类型 `bool`、`int`、`float`、`string`、`any[]` 与 `Dict[string, any]`。list 和 dict 初始值使用普通 Lua table，不使用 Standard 容器。Manager 与 metadata 会区分这两种形状，但运行时不会；空 table 经过 JSON 序列化后不保证继续保持 array 与 object 的区别。

`GameInstance:init` 会 `deepcopy` 生成的 runtime 映射，因此每个新游戏都获得彼此独立的可变初始值。Sample 声明了 `MTExample = 0` 与 `ShopPrice = 20`。运行时系统仍可创建动态名称，但只有生成 metadata 中的声明会出现在 `InstVar` 选择器中。

读取存档时，会以该存档保存的变量 table 覆盖新建实例上的变量 table。因此生成初始值只用于新游戏：增加、删除或修改声明不会迁移或合并已有 slot。修改声明类型同样只会重置项目初始值，不会改变存档中已保存的值。

## 存档

模板在 `Scripts/Entry.lua` 中把全局 `SAVE_AS_LDC` 默认设为 `false`。此时标准 slot 使用 `.json` 文件；设为 `true` 时，游戏状态序列化为 JSON 数据并写入加密的 `.ldc` 文件。`GetSavePath(slot)` 的参数是从 1 开始的 slot 编号，扩展名由该全局开关决定。应使用稳定的 slot 编号，序列化前应校验数据，并通过节点执行分支显式处理文件缺失。存档路径由 runtime 辅助函数获取，不得硬编码开发机目录。

`SAVE_AS_LDC` 只控制运行时用户存档。Pack Options 中的 **Encrypt Data** 只处理发行包内的项目 `Data` JSON，两者彼此独立；开启其中一个不会自动开启另一个。

## 数据边界上的原生容器

Standard 的小写运行时容器 `list`、`tuple` 与 `dict` 不会被 `cjson`、Core binding、Blueprint 值或资产加载器隐式转换。应在边界通过 `toTable` 显式转换：

```lua
local cjson = require("cjson")

local route = list("north", nil, "east")
local payload = dict {
    route = route,
}
local encoded = cjson.encode(payload:toTable())
```

`toTable` 会递归转换嵌套原生容器。list 与 tuple 的结果即使为空或处于嵌套位置，也会保留 JSON array 形状。原生 list 的 nil 槽位与 dict 的 nil value 会变为 `cjson.null`；JSON decode 的结果仍是普通 Lua table，不是原生容器。继续传给 Core API 前，应根据该 API 声明的数组或映射形状校验 raw table。

JSON object 的 key 是字符串。显式调用 `dict:toTable()` 时，tuple key 会转换为 `(1,2)` 这类固定字符串；若与已有字符串 key 冲突则抛错。JSON decode 不会把该字符串还原成 tuple。读取后仍需保留原 key 类型时，应把 dict 转换为 `{ key = key:toTable(), value = value }` 形式的 record array，并在读取后重建原生 key。不得持久化内部 tuple hash。

## 存档格式变更

存档 schema 变化时应增加显式版本与升级处理器。测试新存档、缺失存档、损坏存档及当前发行版支持的每个旧版本。运行时本地化数据不是存档格式，只在“插件开发与安装”专题说明。

## 验证

修改一个受支持设置，保存并重启游戏，确认未知配置 key 仍被保留。开始两个新游戏，确认可变游戏变量初始值彼此独立。分别在 `SAVE_AS_LDC = false` 与 `SAVE_AS_LDC = true` 下创建和读取 slot，确认文件扩展名、已保存游戏变量与内容形式正确；再为每个受支持 schema 版本读取和拒绝相应 slot，验证原生容器转换，并检查打包程序实际使用的用户数据位置。

## 限制

Sample 不承诺兼容项目未来的 schema。切换 `SAVE_AS_LDC` 不会重命名或迁移已有 slot；项目应在发行前确定格式，或自行提供明确的迁移流程。原生容器需要显式转换，tuple-key record 格式由项目自行定义。存档升级、原子写入、备份策略和云同步均由项目负责。
