# Windows, Menus, Input and Controls

The default Lua UI is built from runtime window and control classes. Scenes create windows, controls receive focus and input, and the UI manager controls stacking and ownership.

## Windows and menus

Create controls in the owning window, add them in a predictable order, and release callbacks when the window closes. Menus should keep stable command identifiers separate from displayed text. Long descriptions should use the existing wrapping and formatting helpers.

The in-game menu lists Items, Equipments, Files, Config and Exit Game. Selecting Config opens the shared Config window over the menu and deactivates the command list; closing the Config window returns focus to the menu.

Every visible default screen has one top-level asset: Init, Title, Game Over, Region Title, HUD, Menu, Config, Message, Item, Equip, Shop, Save/Load, Attribute Shop, Enemy Book, Encyclopedia and Floor Teleporter. Multi-pane screens nest their panes under one root; sibling input hosts reuse the nested lists and scroll boxes.

Top-level window transitions are linear and last 0.2 seconds; internal panes and tabs switch immediately. Input is disabled during playback, and close results run after FadeOut hides the root. Initialisation and disposal hide immediately.

| UI | Timeline behaviour |
|---|---|
| Default windows and Config | `FadeIn`: centre Scale `0.5` to `1` plus colour; `FadeOut`: colour only. |
| Title command | `FadeIn`: local Y `80` to `0` plus colour. Opening Config or Save/Load does not hide it. |
| Map Menu | `FadeIn`/`FadeOut`: local X `-192` to `0` and back, plus colour. |
| Item and Equip | Menu animations only. Save/Load has both default and Menu pairs; Config always uses the default pair. |
| Message | `Panel` colour only. |
| Game Over | Colour-only `FadeIn`/`FadeOut`; input and scene switching wait for completion. |
| Region Title | `Display` holds colour for one second, then fades for one second. |

Related FadeOuts may run in parallel; the overall transition remains 0.2 seconds.

Assets include representative `#TAB`/`#ITEM` children and Sample visuals. Controllers replace them before display and localise TabView items without changing their count. Enemy Book and Encyclopedia use `CharacterView`; runtime passes the real actor snapshot, while native code owns cropping, animation, scale and Shader/Hue effects.

Each window module returns one public class. Callers require its concrete path; there are no aggregate export tables or old-path aliases.

On the title screen, an open Config or Save/Load window prevents the underlying command window from receiving any part of the same touch gesture.

`WindowBase` provides an optional 16 × 16 return button on the top-left border, outside `Content`. Cancellable windows enable it with `setHasReturnBtn(true)` and override the no-op `onReturn()` with the same state-aware step used by other Cancel inputs. That shared return step plays the System CancelSE once; do not play it again from a second Cancel source. Multi-pane groups expose the button only on the active interactive pane; hidden, inactive or suppressed windows do not expose it.

Static command rows store a `localeKey`, while dynamic rows store literal `text`; a row must never define both. The row resolves `localeKey` when it refreshes, so a language change can update the existing controls without replacing their callbacks or cursor state. The title commands, in-game menu, save/load tabs, shop tabs and details, and a visible map-region title update immediately when the runtime language changes.

Whenever a reusable selectable window begins a new open session, its selectors start at zero and scroll to the top; an empty selector uses `nil`. This applies to the in-game menu, item and equipment windows, shops, Config, Enemy Book and Teleporter. Focus changes and in-place refreshes within that session preserve selection.

The shop keeps its two-column item list focused while Q/E, LB/RB, mouse or touch switches Buy/Sell. Switching tabs resets the cursor and scroll; transaction refresh preserves a still-valid selection. Buy cells show the icon, Sell cells also show the owned count, and details show the localised name, description and right-aligned price. Selling grants `floor(price / 2)` GOLD and omits zero-price results. Buy-only shops hide tabs and centre the remaining panes; Cancel closes the shop.

Overflowing lists use `Engine.ScrollBox`. It clips rendering and hit testing, scrolls only overflowing axes, and keeps keyboard/controller selection visible. Native edge indicators show remaining content; see [Layout and Image Controls](<../07.API Reference/04.Core Modules/02.Engine/10.Layout and Image Controls.md>).

The message window uses a full-screen Canvas and a transparent `FunctionalImage` to consume one click or tap for plain-message confirmation. Choice mode disables that layer, so blank-space clicks cannot select an option. Its maximum four options fit directly in the panel without ScrollBox; `SceneMap` only blocks map input while dialogue is active.

`SceneMap` owns one `LocaleChanged` subscription for its long-lived map windows. Active dialogue retains the raw speaker, message or options, explicit `localeArgs`, and snapshots of node-local and instance variables. It reruns template localisation, localises string `localeArgs`, applies those arguments, then applies the two variable snapshots before updating the existing `WindowMessage` controls. Item and equipment details, shop tabs and details, attribute shops, Enemy Book, `WindowEnemyEncyclopedia`, and Teleporter (`WindowFloorTeleporter`) likewise refresh localised text in place while preserving their current selection, mode, focus and preview state. Hidden windows resolve the active language when they next open; Config, save-slot and player-HUD controllers keep their own subscriptions. The player HUD also polls lightweight map, combat-revision, progression, key and ordered-state signatures, and refreshes only the affected controls when one changes.

The Teleporter's left slot alternates between floor and telepoint lists; cancelling telepoint selection restores floors. The telepoint list scrolls without moving the right-side preview. A composite manifest remains one floor identity: intersecting children are composed at world offsets, and telepoint labels come from the containing child map.

## Input

Runtime input comes from the C++ input service. Use documented key, mouse, controller and injected-input APIs rather than reading editor state. Embedded Windows mode forwards compatible input through the runtime protocol; standalone games use the native window directly.

On Android and HarmonyOS, the host converts system Back—button or gesture—into one Cancel/Escape pulse instead of closing or backgrounding the app. This remains separate from HarmonyOS external-keyboard forwarding, which sends ordinary SFML-mapped keys as scancode edges, adds logical-key edges where resolvable, and preserves their modifier state. Two-finger touch remains a separate right-click cancellation gesture. System Back and two-finger touch both reach the focused window's `onReturn()`, but only the latter emits right-mouse input.

Physical Enter and Space use the Confirm action, while Escape uses Cancel. Keyboard press and release are edge events; see [Input and Services](<../07.API Reference/04.Core Modules/02.Engine/07.Input and Services.md>).

Controller buttons are selected through the platform-resolved `Engine.JoystickButton.getA()` through `getShare()` getters; fixed numeric fields are not part of the API. Android and HarmonyOS use their existing SFML controller backends. The current SFML iOS joystick backend cannot report connections, buttons or axes, although its logical getter profile is reserved for future backend support.

Default movement and menu directions use only left-stick `X`/`Y` and D-pad `PovX`/`PovY`. Horizontal wins when `|X| >= |Y|`, vertical wins otherwise, and exact 45-degree input is horizontal. This same sector rule drives triggered navigation and held movement; right-stick and trigger axes cannot steal the direction.

`WindowSelectable` owns the default Cancel key and right-button close behaviour; derived windows return unhandled input to it so each edge produces one Cancel sound and one close transition.

## Focus and navigation

Keyboard/controller navigation needs an explicit focus order. A disabled or hidden control should not remain the active focus target. Test pointer activation and keyboard/controller activation independently.

## Configuration controls

Config opens on Graphics with its first row focused. Q/E, LB/RB, mouse hover and touch taps switch tabs and play CursorSE. Each tab keeps its cursor and scroll during that open session; reopening resets all tabs, while locale refresh preserves them.

Switching tabs silently collapses an open DropBox. Cancel and the return button also collapse it first, then close Config on the next input. [Game Settings Reference](<07.Game Settings Reference.md>) defines the settings.

On mobile, a Slider tap sets its value on release. After the drag threshold, horizontal movement belongs to the Slider, while vertical or tied movement belongs to the Config list. Gesture ownership remains fixed until release, and the list scrolls only when its content exceeds the visible area.

An expanded Config DropBox overlays the settings rows and owns input until it collapses or Config closes; either restores parent-list input. A height-limited popup scrolls internally, and mobile touch uses preview-then-confirm. See [Interactive and Declarative UI Controls](<../07.API Reference/04.Core Modules/02.Engine/13.Interactive and Declarative UI Controls.md>).

Save/Load uses one shared slot list. Switching Load/Save tabs preserves its cursor, scroll and detail; reopening selects Load and the newest existing save, or slot zero when none exists. Cancel closes it. Title load-only mode omits the tabs.

Exact UI and input APIs are in [Blueprint API Reference](<../07.API Reference/01.Node Functions/01.Container.md>). Game-localised labels follow [Game Localisation Workflow](<../../05.Plug-in Development and Installation/06.Game Localisation Workflow.md>); editor language switching is not part of this runtime section.

## Limitations

Embedded input forwarding is specific to supported Windows editor-run modes. A native standalone window remains the authoritative environment for final input, focus and controller testing.
