# Windows, Menus, Input and Controls

The default Lua UI is built from runtime window and control classes. Scenes create windows, controls receive focus and input, and the UI manager controls stacking and ownership.

## Scope

Use this page to review the Sample's imperative window, input and focus conventions. For asset-authored interfaces and controller binding, use the Declarative UI section instead.

## Windows and menus

Create controls in the owning window, add them in a predictable order, and release callbacks when the window closes. Menus should keep stable command identifiers separate from displayed text. Long descriptions should use the existing wrapping and formatting helpers.

## Input

Runtime input comes from the C++ input service. Use documented key, mouse, controller and injected-input APIs rather than reading editor state. Embedded Windows mode forwards compatible input through the runtime protocol; standalone games use the native window directly.

## Focus and navigation

Keyboard/controller navigation needs an explicit focus order. A disabled or hidden control should not remain the active focus target. Test pointer activation and keyboard/controller activation independently.

## Configuration controls

The default Config window changes language, frame rate, vertical synchronisation and audio options. Desktop runs also show scale choices for Fullscreen, 1, 1.25, 1.5, 1.75 and 2; selecting one applies it immediately. Mobile runs omit the scale row because their platform window is always fullscreen. Desktop windowed games are resizable, retain the game aspect ratio and centre the canvas with black bars when needed. Pointer input in those bars is ignored.

On mobile runs, each audio Slider is rendered at 160 × 8 logical units but uses a 160 × 32 touch hit rectangle with the same horizontal span, covering the full row height. A touch beginning in that rectangle selects the row and adjusts its Slider immediately, including when the row was not previously selected. Gesture ownership is fixed at the beginning: a Slider that wins the hit keeps the gesture through out-of-bounds movement and release, while a touch beginning outside every Slider hit rectangle belongs to the settings list for selection or vertical scrolling. Crossing into or out of a Slider later does not transfer ownership.

Fullscreen uses a borderless desktop-sized window without changing the display mode. Embedded runs keep using the host size, and mobile runs keep their platform fullscreen behaviour.

Use Blueprint API Reference for the exact UI and input APIs. Game-localised labels belong to Plugin System and Localisation; editor language switching is not part of this runtime section.

## Verification

Open each modified menu with a pointer and a keyboard or controller. Move focus through every enabled control, activate each command, close the window, and confirm that reopening it does not duplicate callbacks or retain stale focus. On a touch device, tap each audio Slider without preselecting its row, drag horizontally after leaving the row vertically, drag beyond both horizontal ends, and begin a vertical list scroll immediately outside the enlarged Slider rectangle. Confirm that each gesture keeps its original owner until release.

## Limitations

Embedded input forwarding is specific to supported Windows editor-run modes. A native standalone window remains the authoritative environment for final input, focus and controller testing.
