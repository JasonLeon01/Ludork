# Windows, Menus, Input and Controls

The default Lua UI is built from runtime window and control classes. Scenes create windows, controls receive focus and input, and the UI manager controls stacking and ownership.

## Windows and menus

Create controls in the owning window, add them in a predictable order, and release callbacks when the window closes. Menus should keep stable command identifiers separate from displayed text. Long descriptions should use the existing wrapping and formatting helpers.

The in-game menu lists Items, Equipments, Files, Config and Exit Game. Selecting Config opens the shared Config window over the menu and deactivates the command list; closing the Config window returns focus to the menu.

On the title screen, an open Config or Save/Load window prevents the underlying command window from receiving any part of the same touch gesture.

`WindowBase` provides an optional 16 × 16 return button on the top-left border, outside `Content`. Cancellable windows enable it with `setHasReturnBtn(true)` and override the no-op `onReturn()` with the same state-aware step used by other Cancel inputs. That shared return step plays the System CancelSE once; do not play it again from a second Cancel source. Multi-pane groups expose the button only on the active interactive pane; hidden, inactive or suppressed windows do not expose it.

Static command rows store a `localeKey`, while dynamic rows store literal `text`; a row must never define both. The row resolves `localeKey` when it refreshes, so a language change can update the existing controls without replacing their callbacks or cursor state. The title commands, in-game menu, save/load commands, shop commands and a visible map-region title update immediately when the runtime language changes.

`SceneMap` owns one `LocaleChanged` subscription for its long-lived map windows. Active dialogue retains the raw speaker, message or options, explicit `localeArgs`, and snapshots of node-local and instance variables. It reruns template localisation, localises string `localeArgs`, applies those arguments, then applies the two variable snapshots before updating the existing `WindowMessage` controls. Item and equipment details, attribute shops, Enemy Book, `WindowEnemyEncyclopedia`, and Teleporter (`WindowFloorTeleporter`) likewise refresh localised text in place while preserving their current selection, focus and preview state. Hidden windows resolve the active language when they next open; Config, save-slot and player-HUD controllers keep their own subscriptions. The player HUD also polls lightweight map, combat-revision, progression, key and ordered-state signatures, and refreshes only the affected controls when one changes.

## Input

Runtime input comes from the C++ input service. Use documented key, mouse, controller and injected-input APIs rather than reading editor state. Embedded Windows mode forwards compatible input through the runtime protocol; standalone games use the native window directly.

On Android and HarmonyOS, the host converts system Back—button or gesture—into one Cancel/Escape pulse instead of closing or backgrounding the app. This remains separate from HarmonyOS external-keyboard forwarding, which sends ordinary SFML-mapped keys as scancode edges, adds logical-key edges where resolvable, and preserves their modifier state. Two-finger touch remains a separate right-click cancellation gesture. System Back and two-finger touch both reach the focused window's `onReturn()`, but only the latter emits right-mouse input.

Physical Enter and Space use the Confirm action, while Escape uses Cancel. Keyboard press and release are edge events; see [Input and Services](<../07.API Reference/04.Core Modules/02.Engine/07.Input and Services.md>).

## Focus and navigation

Keyboard/controller navigation needs an explicit focus order. A disabled or hidden control should not remain the active focus target. Test pointer activation and keyboard/controller activation independently.

## Configuration controls

The default Config window changes Language, Maximum Render Scale, Frame Rate, Anti-Aliasing Level, Vertical Sync and audio options (Sound, Voice, Music). It also shows Scale when `System.isDisplayScaleConfigurable()` reports that the current host supports it. Anti-aliasing offers `0`, `2`, `4` and `8`, while retaining another configured non-negative value; it takes effect on the next display initialisation.

Desktop Scale defaults to `1.0` and offers Fullscreen (`0`) plus `1`, `1.25`, `1.5`, `1.75`, `2`, `3` and `4`; standalone runs keep the positive values that fit the current display's work area, plus a fitting configured non-preset value. A configurable HarmonyOS tablet filters the same presets against the smaller of the current display's available area and the Stage window's maximum dimensions. Other mobile hosts omit Scale.

Maximum Render Scale offers `1`, `1.5`, `2`, `3`, `4` and Unlimited (`0`), retains any other finite non-negative configured value, and applies immediately on every platform. It limits the internal rendering scale without changing the window or logical game size. See [Game Settings Reference](<07.Game Settings Reference.md>) for startup and persistence rules.

Desktop windowed games remain freely resizable. Manually resizing to a non-game aspect ratio centres the canvas with letterboxing; pointer input in those black bars is ignored.

On mobile, a Slider tap sets its value on release. After the drag threshold, horizontal movement belongs to the Slider, while vertical or tied movement belongs to the Config list. Gesture ownership remains fixed until release, and the list scrolls only when its content exceeds the visible area.

An expanded Config DropBox owns input until it collapses or Config closes; either restores parent-list input. On mobile touch it uses preview-then-confirm; see [Interactive and Declarative UI Controls](<../07.API Reference/04.Core Modules/02.Engine/13.Interactive and Declarative UI Controls.md>).

On desktop, Fullscreen uses a borderless desktop-sized window without changing the display mode. Embedded runs keep using the host size. On a configurable HarmonyOS tablet, Fullscreen requests the operating system's maximised/fullscreen window state.

Exact UI and input APIs are in [Blueprint API Reference](<../07.API Reference/01.Node Functions/01.Container.md>). Game-localised labels follow [Game Localisation Workflow](<../../05.Plug-in Development and Installation/06.Game Localisation Workflow.md>); editor language switching is not part of this runtime section.

## Limitations

Embedded input forwarding is specific to supported Windows editor-run modes. A native standalone window remains the authoritative environment for final input, focus and controller testing.
