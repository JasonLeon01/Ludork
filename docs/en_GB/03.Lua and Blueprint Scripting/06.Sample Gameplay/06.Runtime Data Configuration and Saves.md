# Runtime Data, Configuration and Saves

## Configuration

`Data/Configs` contains game configuration JSON. `Main.ini` contains mutable launch and user settings. Use the configuration APIs and editor fields so unknown sections and keys survive a round trip.

In editor mode, `LUDORK_EDITOR=1` selects the project `Main.ini`. A normal packaged run uses the platform user-data location, with the packaged configuration as the initial source where applicable.

An Android package mirrors its immutable runtime assets into `filesDir/ludork/runtime/<runtime-hash>` before native startup. Mutable configuration and saves use `filesDir/ludork/user-data`; they are never written back into that versioned runtime directory and do not require external-storage permission.

## Runtime state

Keep immutable definitions in Blueprint, Config or General Data files and mutable play-session state on the game instance, actors or components. Avoid writing transient state back into source JSON.

### Game variables

The Game Variable Manager generates `Scripts/Source/Configs/GameVariables.lua` as the declared name-to-initial-value map and `GameVariables_meta.lua` as its editor-only type, order and optional-remark schema. Its `bool`, `int`, `float`, `string`, `list` and `dict` choices map to metadata types `bool`, `int`, `float`, `string`, `any[]` and `Dict[string, any]`. List and dictionary initial values are ordinary Lua tables rather than Standard containers. The manager and metadata distinguish the two shapes, but runtime does not; an empty table serialised through JSON is not guaranteed to retain array-versus-object shape.

`GameInstance:init` deep-copies the generated runtime map, so every new game receives independent mutable initial values. The Sample declares `MTExample = 0` and `ShopPrice = 20`. Runtime systems may still create dynamic names, but only declarations in generated metadata appear in `InstVar` selectors.

A loaded save replaces the newly constructed instance's variable table with the table stored in that save. Generated initial values therefore apply to new games only: changing, adding or removing a declaration does not migrate or merge an existing slot. Changing a declaration's type also resets its project initial value, not values already stored in saves.

## Saves

The template sets the global `SAVE_AS_LDC` to `false` in `Scripts/Entry.lua`. Standard slots then use `.json` files. When it is `true`, game state is serialised as JSON data and written to an encrypted `.ldc` file. `GetSavePath(slot)` takes a 1-based slot number and selects the extension from this global. Use stable slot numbers, validate data before serialisation and handle missing files explicitly through the node's execution branches. Save paths come from runtime helpers; do not hard-code a development-machine directory.

`SAVE_AS_LDC` controls only runtime user saves. **Encrypt Data** in Pack Options processes project JSON under `Data` in the distribution package. The two settings are independent; enabling either one does not enable the other.

## Native containers at data boundaries

Standard's lower-case runtime `list`, `tuple` and `dict` containers are not converted implicitly by `cjson`, Core bindings, Blueprint values or asset loaders. Convert them explicitly with `toTable` at the boundary:

```lua
local cjson = require("cjson")

local route = list("north", nil, "east")
local payload = dict {
    route = route,
}
local encoded = cjson.encode(payload:toTable())
```

`toTable` recursively converts nested native containers. List and tuple results retain JSON-array shape even when empty or nested. Native nil list slots and dictionary values become `cjson.null`, and decoding JSON produces ordinary Lua tables rather than native containers. Validate the raw table against the Core API's declared array or mapping shape before passing it onward.

JSON object keys are strings. An explicit `dict:toTable()` call serialises tuple keys as fixed strings such as `(1,2)` and raises on a collision with an existing string key. This representation does not reconstruct tuple keys when decoded. When the loaded data needs the original key type, convert the dictionary to an explicit array of records such as `{ key = key:toTable(), value = value }` and rebuild native keys after reading. Never persist an internal tuple hash.

## Save format changes

When a saved schema changes, add an explicit version and an upgrade handler. Test a new save, an absent save, a malformed save and each older version that the release supports. Runtime localisation data is not a save format and is documented only in Plug-in Development and Installation.

## Verification

Change a supported setting, save and restart the game, then confirm that unknown configuration keys remain intact. Start two new games and verify that mutable game-variable initial values are independent. Create and load a slot with both `SAVE_AS_LDC = false` and `SAVE_AS_LDC = true`, confirming the expected extension, stored game variables and on-disk representation. Then load and reject slots for every supported schema version, verify native-container conversion and inspect the actual packaged user-data location.

## Limitations

The Sample does not promise compatibility with a project's future schemas. Changing `SAVE_AS_LDC` does not rename or migrate existing slots; choose the format before release or provide an explicit project migration. Native containers require explicit conversion, and tuple-key record formats are project-defined. Save-version upgrades, atomicity, backup policy and cloud synchronisation remain project responsibilities.
