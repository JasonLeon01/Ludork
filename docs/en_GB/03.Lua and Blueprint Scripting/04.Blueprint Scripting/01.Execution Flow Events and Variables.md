# Events, Common Functions and Blueprint Flow

## Goal

Build a validated event graph with explicit execution flow, typed data pins, reusable Common Functions and intentional defaults.

## Prerequisites

- A graph-mode Blueprint with current metadata.
- A supported event entry and the node APIs required by the workflow.
- Stable names for any Common Functions and referenced project data.

## Steps

1. Add one supported event entry.
2. Add nodes, connect execution before data, and set every required unconnected input.
3. Move repeated logic into a Common Function opened with F10.
4. Validate, save, then run the event with Console visible.

## Events

An event is an entry point declared with `type = "event"`. It supplies ordered data pins and execution outputs. An event without an explicit split receives the default execution output. Events are entry nodes only and do not also appear as ordinary callable functions.

## Common Functions

Open **Database → Common Functions** (F10). A Common Function owns one reusable graph and can be created, renamed, copied, deleted, arranged and validated. Call it through the matching node instead of duplicating graph fragments.

## Execution semantics

- `Pure = true` removes execution input/output; return values do not imply purity.
- `ExecSplit` maps named execution outputs to result values.
- `Latent` nodes suspend the graph and later resume through declared states.
- `LoopNode` describes loop-body and completion behaviour.
- Data links connect compatible typed pins; execution links connect flow pins.

## Defaults and references

Parameter defaults are positional and correspond to the declared parameter-name array. An explicit `nil` return type is still a data output, while an empty return table means no output. Reference-style nodes and fields should not be confused with copied scalar values.

## Debugging

Begin at the event start, follow execution links, then inspect data sources and unconnected defaults. Validate after moving or renaming node functions. The metadata format behind these behaviours is specified in Blueprint Metadata.

## Expected result

Every execution node is reachable through a declared flow, data links have compatible types, and reusable logic has one validated Common Function definition.

## Verification

- Validate after adding, deleting or reconnecting nodes.
- Test every `ExecSplit`, latent resume and loop completion branch.
- Exercise defaulted and explicitly supplied inputs separately.
- Reopen the saved graph and inspect unresolved node diagnostics.

## Limitations

Graph validation checks structure and metadata contracts; it does not prove gameplay correctness or execute latent work.
