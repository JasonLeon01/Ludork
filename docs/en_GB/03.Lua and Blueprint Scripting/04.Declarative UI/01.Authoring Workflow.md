# Declarative UI Authoring Workflow

## Goal

Declarative UI in Ludork generates Lua Views from JSON assets and keeps business behaviour in handwritten Controllers. Use the [UI Asset Editor](<../../02.Editor User Guide/07.UI Asset Editor.md>) for visual editing.

| Layer | Owns |
|---|---|
| JSON View | Hierarchy, asset-local node names, static control properties, Slots, animation timelines and design-only preview data |
| Generated Lua View | Complete typed control and child-View tree, asset identity, mounting and owned-object lifetime |
| Lua Controller | Model access, callbacks, localised and formatted text, state refresh and dynamic composition |
| Window UI | Native window and input state, its generated View and its private Controller |
| Native control | Rendering, measurement, hit testing, focus and primitive interaction state |
| UIManager | Mounting and removing prepared root controls |

Do not store Controller functions, expressions, event handlers or `LOC(...)` calls in a UI asset.

## Steps

### File layout

The asset root is fixed at `Data/UI/Assets`:

```text
Data/UI/Assets/
    ├── Inventory.json
    └── Parts/
        ├── Inventory/ItemRow.json
        └── Shared/KeyPrompt.json
```

Complete screens, windows, HUDs and overlays live directly below `Assets`. Put parts owned by one large UI in `Parts/<Owner>`, and parts shared by several UIs in `Parts/Shared`. Do not create directories organised only by control shape.

Generated Lua Views mirror the asset hierarchy. Every file under `Scripts/Source/UI` and `Scripts/stub/Source/UI` is generator-owned:

```text
Scripts/Source/UI/
├── Inventory.lua
└── Parts/
    ├── Inventory/ItemRow.lua
    └── Shared/KeyPrompt.lua
```

Handwritten foundations live under `Scripts/Source/UIBase`. A window module such as `Scripts/Source/Windows/WindowInventory.lua` contains its private Controller and returns the UI class through `Ui.DefineWindow`. Independent row and Scene Controllers use separate modules, such as `Source.Windows.WindowInventory.ItemRow.Controller` and `Source.Scenes.SceneTitle.Controller`.

The matching window stub declares only the private Controller, using bare `---@meta`. Public window declarations are generated under `Scripts/stub/Source/UIWindows` and must not be edited by hand. See [Declarative UI Controller Examples](<03.Controller Examples.md#declare-business-members-once>) for the declaration format.

### Create the UI and add its behaviour

1. Create the JSON asset in the UI Asset Editor and give runtime-accessed nodes stable names.
2. Enable **Exposed** to make the asset appear in the Project Palette.
3. Save the asset and resolve any validation diagnostics. Then require the generated View in the window module.
4. Define a local Controller and return `Ui.DefineWindow(ViewClass, Controller, nativeBase?)`. Add business initialisation in `init`, callbacks in `bind`, and state updates through `watch` or `refresh`.
5. Use `windowOptions` for initial window behaviour, `createChild` for authored child panes, and collections for model-dependent rows. See [Declarative UI Runtime Contract](<02.Runtime Contract.md>) and [Declarative UI Controller Examples](<03.Controller Examples.md>).
6. Maintain the private Controller declaration and regenerate. Create and mount the window from its owner, then dispose of it when it is no longer needed.

### Regenerate after asset changes

After moving an asset or renaming nodes, update handwritten `require` calls and node references, then run `ScriptTools ui-assets generate <project-root>`. Automatic generation and read-only checks are described in [Declarative UI Validation and Packaging](<05.Validation and Packaging.md>).

### Scrollable content

Put overflow-prone content in `Engine.ScrollBox`. Do not move a Canvas from Controller code. `size` defines the viewport, and an empty `windowSkin` uses the system skin. ScrollBox owns clipping, offsets, and wheel and touch input. It scrolls an axis only when the laid-out content overflows that axis. Indicator-atlas details are in [Engine: Layout and Image Controls](<../08.Global and Core Modules/02.Core Modules/01.Engine/10.Layout and Image Controls.md>).

## Limitations

Every visible screen has one top-level asset. Multi-pane screens nest owner-specific assets from `Parts/<TopLevelName>/`. Nested parts use `palette.exposed = true`, while runtime-only helpers may remain unexposed.

Use representative `#TAB` and `#ITEM` children and Game visuals as preview data only, and never as fallback game data. Before display, business code localises tab labels and fills dynamic collections. Fixed controls and rows remain the instances created from JSON. Literal `text` is reserved for permanent, language-independent symbols.

Use `Engine.CharacterView` for frame-animated characters and enemies. Assets provide preview values, and the runtime passes the real texture, Rect, scale, animation, Shader and Hue to `setCharacter`. Lua does not crop or compose the actor visual.
