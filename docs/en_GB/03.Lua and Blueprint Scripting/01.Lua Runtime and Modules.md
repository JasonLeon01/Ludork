# Lua Runtime and Modules

Ludork runs Lua 5.5 with Standard extensions, LuaSF and project-native modules.

Readers new to Lua can begin with [Lua Basics](<../01.Getting Started/03.Lua Basics.md>). Ludork-native language additions such as `class`, `bool`, `list`, `dict`, copying, filesystem helpers and `asyncio` are described in [Ludork Lua Advanced](<../01.Getting Started/04.Ludork Lua Advanced.md>). This section covers project scripting architecture rather than language syntax.

| Model | Best suited to | Primary source |
|---|---|---|
| Blueprint graph | Visual event and execution flow | `Data/Blueprints/*.json` |
| Lua class | Reusable systems and gameplay types | `Scripts/**/*.lua` |
| Script Mixin | Lua behaviour attached directly to a Blueprint class | `Scripts/Mixins/**/*.lua` plus same-name `_meta.lua` |
| Declarative UI | JSON assets and generated typed View trees | `Data/UI/Assets/**/*.json`, generated `Scripts/Source/UI/**/*.lua` and matching stubs |
| UI behaviour | Handwritten foundations and business Controllers | `Scripts/Source/UIBase`; private Controllers inside window modules; independent row and Scene `Controller.lua` modules |

A Blueprint inheritance chain uses either graph mode or Script Mixin mode. Do not switch modes within one chain.

## Entry and module order

`Main.ini` selects the entry script, normally `Scripts/Entry.lua`. Load the root native modules in the order shown below, finish the direct `require` calls, then declare aliases:

```lua
local Engine = require("Engine")
local GlobalCore = require("GlobalCore")
local GlobalFunctions = require("GlobalFunctions")
local Logging = require("Global.Utils.Logging")

local Input = Engine.Input
local System = GlobalCore.System
local ManagerFunctions = GlobalFunctions.Manager
```

`GlobalFunctions` exposes `Components`, `UI`, `NodeGraph` and `Manager`. Other modules use their full dotted path. Do not add directory-level `init.lua` aggregators. Delay a `require` to resolve a real dependency cycle, or at an explicit first-use boundary such as an optional window's factory. The owning scene or feature must define that lifecycle; ordinary dependencies remain direct imports.

Static dependencies flow from the root native modules through `Scripts/Global` to `Scripts/Source`. Global modules must not require Source. Generic infrastructure can resolve opaque module names supplied by data, but it must not hard-code a higher-layer business module.

Shared constants belong to their owning domain. Native resource suffixes are exposed through `Engine.ResourceFileConstants`; game-specific map identities, Gameplay tags and movement latent output indices live in `Source.Configs.MapConstants`, `Source.Configs.GameplayConstants` and `Source.Configs.MovementLatentOutputs`. Host-owned implementation settings are passed down as arguments. For example, `WorldGameMap` supplies its publication budget to its streaming and region-publishing modules; those modules do not require their host.

At runtime, scripts use exactly one storage form: loose `Scripts` during development, or a root `Scripts.ldpak` in a packed release. Mixed, missing or invalid layouts fail during startup. Logical module and entry paths are identical in both forms.

Every Lua state exposes project modules through `package.preload` without replacing native modules. Script Mixins still load fresh on every execution. Standard filesystem APIs do not expose archive contents.

Packed Data remains available through the same logical `Data/...` paths, including encrypted `.ldc` alternatives. This is a read-only runtime boundary, not a general archive filesystem.

Each independently reusable class has its own module, and that module returns the class. A window module may contain its private Controller and export the UI through `Ui.DefineWindow`; see the [Declarative UI Authoring Workflow](<04.Declarative UI/01.Authoring Workflow.md>). Utility modules may group related helpers.

When a private implementation needs separate modules, a public module hosts them in a same-name directory, such as `Global/GameMap.lua` and `Global/GameMap/*.lua`. The host owns its public methods and delegates to the implementation. Implementation modules must not require or extend the host. A helper with its own mirrored `.d.lua` declaration remains an independent module.

Access private members only through `self` or same-instance `super(..., self)` dispatch. For other objects, including chained and dynamic access, use public getters, commands or data.

## Native modules and values

Standard globals such as `os.createDirectories`, `os.removeFile`, `zlib` and `base64` are host-installed and are not required. The host also installs the `SAVE_AS_LDC` default from `LUDORK_SAVE_AS_LDC`; project overrides are described in [Saves](<05.Default Gameplay/06.Runtime Data Configuration and Saves.md#saves>). `LudorkRuntime` is a native library, not a Lua module. Core bindings load only through `Engine`, `GlobalCore` and `GlobalFunctions`, and there is no `Runtime` or `CoreSystem` alias.

LuaSF registers the global `sf`. Use exact native values such as `sf.Vector2i.new(...)`, `sf.Vector2f.new(...)` and `sf.Color.new(...)` when an API declares those types. Native containers and ordinary tables are not implicit vector adapters.

## Session lifetime

The main thread and coroutines in one Lua VM share a native session. Captured callbacks and opaque values survive yields but cannot cross VMs, and session shutdown invalidates them. Native host integration is covered in [Session and module lifetime](<../04.Native C++ Development/01.Build and Module Layout.md#session-and-module-lifetime>).

## Live Debug

The default Game runtime installs `Source.LiveDebug` only when the editor launches the game with Live Debug enabled: both `LUDORK_EDITOR` and `LUDORK_LIVE_DEBUG` must equal `1`. It registers through `Engine.EditorLiveDebug` and binds to the active `SceneMap`. Requests identify Actors by instance ID rather than map tag, so runtime-spawned Actors are included. The handler does not write project data or replay edits onto rebuilt instances.

Project scripts should not replace this handler during normal play. See [Live Debug](<../02.Editor User Guide/08.Run Debug and Package.md#live-debug>) for the editor contract and [EditorLiveDebug](<08.Global and Core Modules/02.Core Modules/01.Engine/12.Events and Module Root.md#editorlivedebug>) for the native entry points.

## Lua hot reload

In an editor-launched game that uses loose Lua sources under `Scripts`, save the changes and enter `$r` in the Console. At the next Console update, between gameplay callbacks, the runtime updates loaded project modules and used Script Mixins while keeping the current scene, objects and Lua VM. Both Debug and Release builds support the command. Packed or compiled-only scripts do not.

Reload replaces existing named functions while preserving module and class identities, instance fields, module data, constants, defaults and captured non-function values. Changing a function body takes effect. Changing a class default requires a restart. Cached references to matched functions, including native callbacks, are redirected to new function objects. Existing anonymous callbacks and suspended coroutine frames keep their original bodies, although references to matched helpers are updated. Constructors and lifecycle callbacks do not run again.

Loaded modules and used Script Mixins must retain their export names, class bases, field and function kinds, native callback members and compatible captured state. Deleting one of these modules, or making an incompatible structural change, requires a restart. Adding or removing ordinary global accesses is supported. An unmatchable custom `_ENV` requires a restart.

The runtime compiles all Lua sources before it applies changes. Entry is checked but not rerun. New and unloaded modules remain available on demand through `require`. Metadata, declarations, JSON data, UI assets and native code are excluded. Existing [audio processors](<05.Default Gameplay/05.Resources Audio Video and Effects.md#audio>) keep their code until a new playback starts.

Syntax, compatibility or candidate-execution failures leave the existing definitions in place and report an error in the Console. External side effects from candidate execution cannot be rolled back, so restart after an error that may have changed native resources or shared objects. Keep module top levels to definitions and dependencies, and put resource creation and subscriptions in explicit startup or lifecycle functions. See the [Game entry sequence](<05.Default Gameplay/01.Default Template Overview.md#entry-and-modules>).

## Logging and errors

Runtime Lua logs through `Global.Utils.Logging`: `debug` for diagnostic detail, `info` for significant stages, `warning` for recoverable data problems and `error` for unrecoverable failures. Logging does not raise. Use `error` or `assert` when execution must stop.

Engine providers are installed explicitly during [startup](<05.Default Gameplay/01.Default Template Overview.md#entry-and-modules>), not by `require`. Missing or duplicate providers, stopped sessions and invalid return counts or types raise errors. Returning no values differs from returning one `nil`.

## Runtime, declarations and metadata

Lua files have separate owners:

- `.lua` files contain runtime behaviour and implementation-only annotations.
- Mirrored `Scripts/stub/**/*.d.lua` files contain public documentation and LuaLS declarations, with no runtime side effects or `require`.
- Same-name `_meta.lua` files contain pure editor metadata and never run as gameplay scripts.

A requireable declaration uses `---@meta` with its module path; for example, `Global/Pool.d.lua` declares `---@meta Global.Pool`. Global-only `Standard.d.lua`, `Class.d.lua` and `LuaSF.d.lua` use a bare `---@meta`.

The EmmyLua workspace indexes `Scripts/stub`. Templates retain declarations except the generated UI declarations, which Export recreates in each project. Packaging removes it, Lua compilation ignores `.d.lua`, and shipped packages must contain none. Standalone and C++ Source templates include a Windows VS Code configuration named `Ludork: EmmyLua Attach (Windows)` that attaches the `tangzx.emmylua` `emmylua_attach` debugger to a running `Main.exe`. C++ Source templates also keep the native `cppvsdbg` and `lldb` launch and attach configurations. The EmmyLua attach debugger supports Windows only.
