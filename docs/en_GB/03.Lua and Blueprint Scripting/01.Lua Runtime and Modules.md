# Lua Runtime and Modules

Ludork runs Lua 5.5 with Standard extensions, LuaSF and project-native modules.

New Lua users should begin with [Lua Basics](<../01.Getting Started/03.Lua Basics.md>). Ludork-native language additions such as `class`, `bool`, `list`, `dict`, copying, filesystem helpers and `asyncio` are in [Ludork Lua Advanced](<../01.Getting Started/04.Ludork Lua Advanced.md>). This section describes project scripting architecture rather than language syntax.

| Model | Best suited to | Primary source |
|---|---|---|
| Blueprint graph | Visual event and execution flow | `Data/Blueprints/*.json` |
| Lua class | Reusable systems and gameplay types | `Scripts/**/*.lua` |
| Script Mixin | Lua behaviour attached directly to a Blueprint class | `Scripts/Mixins/**/*.lua` plus same-name `_meta.lua` |
| Declarative UI | JSON assets and generated typed View trees | `Data/UI/Assets/**/*.json`, generated `Scripts/Source/UI/**/*.lua` and matching stubs |
| UI behaviour | Handwritten foundations and business Controllers | `Scripts/Source/UIBase`; private Controllers inside window modules; independent row and Scene `Controller.lua` modules |

A Blueprint inheritance chain uses either graph mode or Script Mixin mode; do not switch within the chain.

## Entry and module order

`Main.ini` selects the entry script, normally `Scripts/Entry.lua`. Load root native modules in this order, finish direct `require` calls, then declare aliases:

```lua
local Engine = require("Engine")
local GlobalCore = require("GlobalCore")
local GlobalFunctions = require("GlobalFunctions")
local Logging = require("Global.Utils.Logging")

local Input = Engine.Input
local System = GlobalCore.System
local ManagerFunctions = GlobalFunctions.Manager
```

`GlobalFunctions` exposes `Components`, `UI`, `NodeGraph` and `Manager`. Other modules use their full dotted path. Do not add directory-level `init.lua` aggregators; delay a `require` only to resolve a real dependency cycle.

Static dependencies flow from root native modules through `Scripts/Global` to `Scripts/Source`. Global modules must not require Source. Generic infrastructure may resolve opaque data-supplied module names, but must not hard-code a higher-layer business module.

At runtime, scripts use exactly one storage form: loose `Scripts` during development or root `Scripts.ldpak` in a packed release. Mixed, missing or invalid layouts fail during startup; logical module and entry paths remain unchanged.

Every Lua state exposes project modules through `package.preload` without replacing native modules. Script Mixins still load fresh on every execution, and Standard filesystem APIs do not expose archive contents.

Packed Data remains available through the same logical `Data/...` paths, including encrypted `.ldc` alternatives. This is a read-only runtime boundary, not a general archive filesystem.

Each independently reusable class has its own module that returns the class. A window module may contain its private Controller and export the UI through `Ui.DefineWindow`; see the [UI Authoring Workflow](<05.Declarative UI/01.Authoring Workflow.md>). Utility modules may group related helpers.

When private implementation needs separate modules, a public module hosts them in a same-name directory, such as `Global/GameMap.lua` and `Global/GameMap/*.lua`. The host owns its public methods and delegates to the implementation; implementation modules must not require or extend the host. A helper with its own mirrored `.d.lua` declaration remains an independent module.

Access private members only through `self` or same-instance `super(..., self)` dispatch. Use public getters, commands or data for other objects, including chained and dynamic access.

## Native modules and values

Standard globals such as `os.createDirectories`, `os.removeFile`, `zlib` and `base64` are host-installed and are not required. The host also installs the `SAVE_AS_LDC` default from `LUDORK_SAVE_AS_LDC`; project overrides are described in [Saves](<06.Sample Gameplay/06.Runtime Data Configuration and Saves.md#saves>). `LudorkRuntime` is a native library, not a Lua module; Core bindings load only through `Engine`, `GlobalCore` and `GlobalFunctions`, with no `Runtime` or `CoreSystem` alias.

LuaSF registers the global `sf`. Use exact native values such as `sf.Vector2i.new(...)`, `sf.Vector2f.new(...)` and `sf.Color.new(...)` when an API declares those types; native containers and ordinary tables are not implicit vector adapters.

## Session lifetime

The main thread and coroutines in one Lua VM share a native session. Captured callbacks and opaque values survive yields but cannot cross VMs; session shutdown invalidates them. Native host integration is covered in [Session and module lifetime](<../04.Native C++ Development/01.Build and Module Layout.md#session-and-module-lifetime>).

## Lua hot reload

In an editor-launched game using loose Lua sources under `Scripts`, save your changes and enter `$r` in the Console. At the next Console update, between gameplay callbacks, the runtime updates loaded project modules and used Script Mixins while keeping the current scene, objects and Lua VM. Debug and Release builds both support the command; packed or compiled-only scripts do not.

Reload replaces existing named functions while preserving module and class identities, instance fields, module data, constants, defaults and captured non-function values. Changing a function body takes effect; changing a class default requires a restart. Cached references to matched functions, including native callbacks, are redirected to new function objects. Existing anonymous callbacks and suspended coroutine frames keep their original bodies, though references to matched helpers are updated. Constructors and lifecycle callbacks do not run again.

Loaded modules and used Mixins must retain their export names, class bases, field/function kinds, native callback members and compatible captured state. Deleting one of these modules or making an incompatible structural change requires a restart. Adding or removing ordinary global accesses is supported; an unmatchable custom `_ENV` requires a restart.

All runtime Lua sources are compiled before applying changes. Entry is checked but not rerun; new and unloaded modules remain available on demand through `require`. Metadata, declarations, JSON data, UI assets and native code are excluded. Existing [audio processors](<06.Sample Gameplay/05.Resources Audio Video and Effects.md#audio>) keep their code until a new playback starts.

Syntax, compatibility or candidate-execution failures leave the existing definitions in place and report an error in the Console. External side effects from candidate execution cannot be rolled back; restart after an error that may have changed native resources or shared objects. Keep module top levels to definitions and dependencies, with resource creation and subscriptions in explicit startup or lifecycle functions. See the [Sample entry sequence](<06.Sample Gameplay/01.Default Template Overview.md#entry-and-modules>).

## Logging and errors

Runtime Lua logs through `Global.Utils.Logging`: `debug` for diagnostic detail, `info` for significant stages, `warning` for recoverable data problems and `error` for unrecoverable failures. Logging does not raise; use `error` or `assert` when execution must stop.

Engine providers are installed explicitly during [startup](<06.Sample Gameplay/01.Default Template Overview.md#entry-and-modules>), not by `require`. Missing or duplicate providers, stopped sessions and invalid return counts or types raise errors; returning no values differs from returning one `nil`.

## Runtime, declarations and metadata

Lua files have separate owners:

- `.lua` files contain runtime behaviour and implementation-only annotations;
- mirrored `Scripts/stub/**/*.d.lua` files contain public documentation and LuaLS declarations, with no runtime side effects or `require`;
- same-name `_meta.lua` files contain pure editor metadata and never run as gameplay scripts.

A requireable declaration uses `---@meta` with its module path, for example `Global/Pool.d.lua` declares `---@meta Global.Pool`. Global-only `Standard.d.lua`, `Class.d.lua` and `LuaSF.d.lua` use bare `---@meta`.

The EmmyLua workspace indexes `Scripts/stub`. Templates retain the declaration tree for development; packaging removes it, Lua compilation ignores `.d.lua`, and shipped packages must contain none.
