# Events, Common Functions and Blueprint Flow

Blueprints store class defaults and a visual graph in `Data/Blueprints`. Common Functions store reusable graphs. The editor validates both against the current project metadata catalogue.

Create a Blueprint from **Game → New Blueprint**, select a valid parent and add supported event entries. Connect execution and data pins, then validate and save. Open Common Functions with F7 when multiple graphs need the same operation. A Script Mixin Blueprint follows the separate [Script Mixin Authoring Workflow](<../02.Script Mixins/01.Authoring Workflow.md>) contract and does not execute its graph.

## Goal

Build a validated event graph with explicit execution flow, typed data pins, reusable Common Functions and intentional defaults.

## Prerequisites

- A graph-mode Blueprint with current metadata.
- A supported event entry and the node APIs required by the workflow.
- Stable names for any Common Functions and referenced project data.

## Steps

1. Add one supported event entry.
2. Add nodes, connect execution before data, and set every required unconnected input.
3. Move repeated logic into a Common Function opened with F7.
4. Validate and save, then run the event with the Console visible.

## Events

An event is an entry point declared with `type = "event"`. It supplies ordered data pins and execution outputs. An event without an explicit split receives the default execution output.

General Data member graphs are synchronous abilities, not inherited or implicit Blueprint events. `Source.Gameplay.GeneralDataGraphAbility` activates a selected graph with `GameplayEventData` as parent. A `null` start returns `NoGraph`. Latent nodes are invalid, and errors propagate to the caller.

## Common Functions

Open **Database → Common Functions** (F7). A Common Function owns one reusable graph. It can be created, renamed, copied, deleted, arranged and validated. Call it through the matching node instead of duplicating graph fragments.

## Execution semantics

- `Pure = true` removes the execution input and output pins. Return values do not imply purity.
- `ExecSplit` maps named execution outputs to result values.
- `Latent` nodes suspend the graph and later resume through declared states.
- Every Blueprint event drops repeated triggers for the same graph instance and event key while latent nodes from the current execution remain pending. A new trigger is accepted after all latent work of that execution resolves. Different graph instances and event keys remain independent.
- `LoopNode` describes loop-body and completion behaviour.
- Data links connect compatible typed pins, and execution links connect flow pins.

Runtime event queries and execution use native `Engine.Graph` userdata. Raw GraphData supports definition-time event inspection. Local execution contexts hold invocation state and are not executable graphs.

## Typed connections

A value may connect to a union when at least one branch accepts its type. A union output may connect only when the target accepts every possible branch. Lists, dictionaries and tuples apply the rule recursively. Derived types may connect to their declared bases. `int` may connect to `float`, but a `float` to `int` connection and conversions between different SFML vector types are rejected. `any` allows dynamic connections whose actual values are checked at runtime.

Incompatible connections remain visible in red after loading or pasting a graph, and their tooltip explains the error. Correct the connection before a normal save.

## Defaults and references

New inputs use the declared default or a valid literal for their type. Object and function inputs without either remain unset. Saved literals must match the declared type, even on connected inputs. Invalid values remain visible and block normal saving, and connected values are checked at runtime. Metadata default and return declarations are covered in [Functions and events](<02.Metadata Schema and Decorators.md#functions-and-events>).

## Class definitions and session lifetime

ClassDict instances in one Lua VM share resolved classes, definition tables and compiled graph templates. Changes to JSON class definitions or graph templates require a restart. [Lua hot reload](<../01.Lua Runtime and Modules.md#lua-hot-reload>) updates only compatible script functions.

`ClassDict:getData(path)`, also exposed as `Data.GetClassData(path)` in the Sample, resolves through the same loading path as `get` before returning the resolver's JSON definition table. Unknown paths raise, and module classes without a JSON definition return nil. Repeated reads in one VM return the same table. Use `copy` or `deepcopy` when an independent table is needed.

Editing that table is visible to later definition reads, but it does not update generated classes, instance-default records or compiled templates. New instances and executable-event queries continue to use the generated results.

## Debugging

Begin at the event start, follow execution links, then inspect data sources and unconnected defaults. Validate after moving or renaming node functions.

## Limitations

Graph validation checks structure and metadata contracts. It does not prove gameplay correctness or execute latent work.
