# Engine: Interactive and Declarative UI Controls

## TextBox

Direct metadata bases: `Engine.ControlBase`, `Engine.FunctionalBase`.

TextBox is a single-line UTF-8 input with editing initially off. Click/tap or Confirm starts editing; focus alone does not. Desktop editing supports a blinking caret, selection, horizontal scrolling, grapheme-based navigation/deletion, Home/End and clipboard shortcuts.

Enter or `finishEdit` keeps the edited value; Escape or `cancelEdit` restores the value from activation. Neither submits the containing form. Focus loss keeps committed text and discards unfinished composition; hiding, disabling, detaching or destroying the control ends editing. Only one TextBox edits at a time.

iOS, Android and HarmonyOS Mobile use a system input dialog; HarmonyOS 2in1 uses desktop editing. Native Done updates the text and Cancel restores the pre-dialog value. Backgrounding closes the session without automatically reopening it on return.

## DropBox

Direct metadata bases: `{ "Engine", "ControlBase" }`, `{ "Engine", "FunctionalBase" }`

### Properties

No editable properties are declared.

### Overlay and measurement

When a DropBox has a Canvas ancestor, its expanded popup is drawn in the outermost ancestor Canvas overlay layer, after that Canvas's ordinary content and animations. It therefore escapes nested Canvas clipping and does not resize or reposition controls in its parent layout.

The popup's visible height is limited to the intersection of the root Canvas content rectangle and the game screen. It opens downwards when the complete list fits, otherwise upwards when the complete list fits there; if neither side fits, it uses the side with more space and scrolls its items internally.

`getSize()` always returns the collapsed layout size. `getLocalBounds()` returns that rectangle while collapsed and its union with the visible popup while expanded; an upward popup can make the local Y position negative. The inherited absolute bounds and default touch hit bounds follow this visual extent.

### Popup scrolling and selection

An ordinary mouse wheel scrolls towards a row-sized target; a precise wheel and mobile touch dragging apply their offsets directly. These inputs move only the popup viewport, not the cursor or committed selection, and releasing a drag never confirms an item. Directional keys move the cursor and reveal it as needed. Mouse hover previews a visible item, a desktop click confirms it, and mobile taps use the two-stage confirmation described below. All indices still address the complete `items` array.

### Mobile touch confirmation

On mobile, an expanded DropBox uses two-stage confirmation: tapping a non-highlighted item only moves the highlight and plays the cursor sound, without changing `selectedIndex` or firing either selection callback. Tapping the highlighted item confirms it, including the initial highlight. Cancelling discards the preview and preserves `selectedIndex`.

### Selection callbacks

`setOnSelectedIndexChanged(callback)` fires with the new index only when `setSelectedIndex` resolves to a different selection; during confirmation it runs before the confirmation callback. `setOnSelectionConfirmed(callback)` fires with the current index when an expanded, non-empty DropBox confirms, even if unchanged. Programmatic selection or item replacement, cancellation and empty confirmation do not fire it; pass `nil` to either setter to clear it.

## TabView

Direct metadata bases: `{ "Engine", "ControlBase" }`, `{ "Engine", "FunctionalBase" }`

### Selection and navigation

A TabView has a fixed, non-zero item count, zero-based clamped indices and an always-visible selection. The middle area contains equal tab slots; each side reserves 16 logical pixels for hints. The control never takes keyboard focus. Declarative assets construct that fixed count from the required non-empty `items: string[]` property; `tabCount` is not an asset property.

`setItems(items)` replaces same-count labels without changing selection or the callback; a wrong count leaves the control unchanged. `setOnSelectedIndexChanged(callback)` binds the selection callback, and `nil` clears it. A real `setSelectedIndex` change calls the callback without sound. `selectPrevious`, `selectNext` and real Q/E, LB/RB, mouse-move or touch-tap changes play the configured cursor sound once, then call the callback. Unchanged and boundary selections do neither, and tabs do not wrap.

Focused content calls `handleNavigationInput()`. It consumes Q/E/LB/RB while the TabView is visible and active; duplicate same-direction inputs move once and opposing inputs cancel. Mouse movement selects central slots. A left click there is consumed but does not select; right/middle clicks and both hint gutters pass through. Touch movement does not select; a tap does.

### Key hints

`setKeyHint(leftHint, rightHint)` accepts two `Engine.KeyHint` values with optional `Keyboard` and `Joystick` fields: a non-Unknown `sf.Keyboard.Key` and an `Engine.JoystickButton` getter value, respectively. An empty hint clears that side; a missing current-device field hides it. Invalid input leaves both hints unchanged.

```lua
tabView:setKeyHint(
    Engine.KeyHint.new({ Keyboard = sf.Keyboard.Key.Q, Joystick = Engine.JoystickButton.getLB() }),
    Engine.KeyHint.new({ Keyboard = sf.Keyboard.Key.E, Joystick = Engine.JoystickButton.getRB() })
)
```

Hints appear only where movement is possible. A connected joystick uses the `Joystick` hint; otherwise desktop, HarmonyOS 2in1 and HarmonyOS Mobile tablets use `Keyboard`, while Android, iOS and HarmonyOS phones hide hints. Hints never rebind or disable input.

## Slider

Direct metadata bases: `{ "Engine", "ControlBase" }`, `{ "Engine", "FunctionalBase" }`

### Touch interaction

On touch capture, a Slider sets its value from the pointer's X position against its visual bounds, then continues updating and clamping until release even outside the hit bounds. `setTouchHitBounds` changes only the touch target, not visual or mouse bounds.
