# Runtime Data, Configuration and Saves

## Configuration

`Data/Configs` contains game configuration JSON. `Main.ini` contains mutable launch and user settings. Use the configuration APIs and editor fields so unknown sections and keys survive a round trip.

Resource-valued Config `file` fields store complete `/Game/Assets/...` paths, while `base` and `ext` only constrain the selector. Data references remain separate. `System.json` keeps `startPlayerBlueprint` relative to `Data/Blueprints` with `root = "Data"` and converts it to `Data.Blueprints.*`. `startRegion` names the initial region. Both affect new games only, and saves retain their player class and region.

Cell size is fixed by the compiled engine (`32` by default). Read it through `Engine.GetCellSize()`. `System.json` and the System Config editor do not configure it. A leftover `System/cellSize` field is neither used nor editable, and it is not converted into a runtime setting.

Game Lua configuration modules live under `Scripts/Source/Configs` and are loaded through `Source.Configs.*`.

`Source.Locale.Core.DEFAULT_LANGUAGE` is the shared initial and fallback language (`en_GB`); `Source.Configs.Main` uses the same value. `Source.Configs.MapConstants.WORLD_MANIFEST_FILE` defines the composite-world filename (`_world.json`). Data readers and saves use the suffixes from `Engine.ResourceFileConstants`.

In editor mode, `LUDORK_EDITOR=1` selects the project `Main.ini`. A normal packaged run uses the platform user-data location, with the packaged configuration as the initial source where applicable.

An Android package mirrors its immutable runtime assets into `filesDir/ludork/runtime/<runtime-hash>` before native startup. Mutable configuration and saves use `filesDir/ludork/user-data`. They are never written back into that versioned runtime directory and do not require external-storage permission.

## Runtime state

Keep immutable definitions in Blueprint, Config or General Data files, and keep mutable play-session state on the game instance, actors or components. Avoid writing transient state back into source JSON.

`Data.GetClassData(path)` exposes the shared session definition; see [Events, Common Functions and Blueprint Flow](<../03.Blueprint Scripting/01.Execution Flow Events and Variables.md#class-definitions-and-session-lifetime>).

Construct General Data Attribute Sets with `Source.Configs.GeneralDataTypes.Create`. The [General Data and Text Config](<../../02.Editor User Guide/05.General Data and Text Config.md>) page describes value conversion and defaults.

### Players

`GameInstance` stores player order in `_playerKeys` and player objects in `_players`, keyed by the stable Player General Data key from `Player.ID`. Player keys must be non-empty and unique. `getPlayers()` returns the live keyed dictionary, while `getPlayerKeys()` returns the live ordered key array. Its first key identifies the primary player used by `getPlayer()`. `getPlayerByIndex()` resolves a zero-based index through the same order, and `setPlayer(playerKey)` moves an existing key to the first position.

Saves preserve the same structure as sibling `playerKeys` and `players` fields. `playerKeys` defines the order, and every key must have exactly one matching entry in `players` with the same restored `Player.ID`.

Each Player saves every numeric Attribute Set Base under `attr` from `getNumericAttributeBases()`. Derived Current values are not saved, and non-numeric attributes are rebuilt from Player General Data. Values must be finite and follow the generated `int` or `float` schema. Missing keys in an older save keep the restored member's initial Base.

Saves retain inventory/equipment counts, equipped IDs and State stacks. Loading restores all Base values first, then Item abilities, equipment Effects and State Effects without running initial-equipment or member graphs. Handles, derived Current values, transient Effects, ability specs and tags are not saved. Persistent additions need their own stable record and rebuild step.

Player saves require a string `customName` alongside `attr`. `""` selects the localised General Data default. Non-empty values must already be trimmed and satisfy the rules in [Source.Player](<../07.Source Classes/09.Player.md>).

### Game variables

The runtime reads initial values from the generated `Scripts/Source/Configs/GameVariables.lua`. Save the edits in [General Data](<../../02.Editor User Guide/05.General Data and Text Config.md#game-variable-manager>) before starting the runtime. List and dictionary initial values are ordinary Lua tables rather than Standard containers, and an empty table serialised through JSON is not guaranteed to retain its array or object shape.

`GameInstance:init` deep-copies the generated runtime map, so every new game receives independent mutable initial values. The Game project declares `MTExample = 0` and `ShopPrice = 20`. Runtime systems may still create dynamic names, but only editor-declared names appear in `InstVar` selectors.

A loaded save replaces the newly constructed instance's variable table with the table stored in that save. Generated initial values therefore apply to new games only. Changing, adding or removing a declaration does not migrate or merge an existing slot. Changing a declaration's type also resets its project initial value, but not the values already stored in saves.

Variable snapshots include the current logical values of monitored fields. `deepcopy` excludes monitor proxies and subscriptions, so ConditionalActor listeners stay within the live game instance. After restoring records, `onCreate` subscribes to the restored variables and recomputes visibility. No extra save fields are needed.

### Map Actor identity

The placement `tag` in map JSON becomes the Actor's map-persistence tag. `GameMap:getActorByTag` and `GameInstance` persistence records identify Actors only through `Actor:getMapTag()`, and `Actor.tag` remains independent. Actors without a map tag are not recorded, and map paths are normalised for these records.

Runtime-spawned Actors that must survive a map rebuild are stored through the added-Actor record using their own generated map-placement tag. When such an Actor is later destroyed, its destroyed record suppresses the stored addition. Reborn enemies use this existing pair of records rather than reusing the original placement tag.

World runtime tags use `<child-file-stem>.runtime_default_<N>` in placements and `<world-directory>.runtime_default_<N>` in holes. All tags remain reserved for the world lifetime, and conflicts fail. Editor tags are unique world-wide and stable across map renames.

### Composite-world persistence

The current `map` stores the manifest path even when entry used a child. Player, added, moved and destroyed records use that identity, world coordinates and global tags. Conflicting added or moved records fail loading.

Added Actors restore at `actorPositions[tag]` when it is present, and otherwise at their original position. Destroyed tags are skipped. Placement Actors restore with their child payload without distant child I/O, while hole Actors may restore immediately.

`worldMovedActors` owns authored roots outside their definition child, storing identity, owner, layer overrides and world position. They rebuild only at that owner. Returning or destruction removes the moved record.

Destroying a tag removes its moved record and suppresses authored, added, resident and in-progress instances without loading absent children. Suppressed tags stay reserved, and invalid records and collisions fail.

Terrain records use child paths and local coordinates. They apply when that child builds and update only its affected live layer. Holes cannot own terrain changes.

A world save requires `worldMovedActors`. Moved snapshots preserve reconstruction identity, class-variable overrides, layer and position, but not arbitrary instance fields, private Lua state or timer progress. Persist those separately, or recover the time through `onWorldWake`.

## Saves

[Live Debug](<../../02.Editor User Guide/08.Run Debug and Package.md#live-debug>) does not write project documents and does not change the save schema, slots or persistence records. A save during that run can keep gameplay state that live edits affected.

The Game project save schema is version `1`. Only the current structure and version are supported. `SaveCodec` rejects incompatible saves without migration. Development-time schema changes may retain the version.

`telepoints` maps normalised map paths to ordered `{ position = {x, y}, tag = "raw tag" }` records. Runtime positions use `sf.Vector2u`, and tags remain unlocalised strings. `GameInstance:recordTelepoint(mapPath, position, tag)` preserves the first record for each map and position pair, and `getTelepoints(mapPath)` returns the records. World records use the manifest identity and world coordinates.

`GameInstance:getCurrentMapPath()` returns the current map or `nil`. `getVisitedMapPaths()` returns sorted telepoint map paths, and `getTelepointsForMap(key)` ignores the extension when matching. Both collection queries return copies. `restoreFromData(data)` restores a validated save into the instance.

`SAVE_AS_LDC` selects plain `.json` saves (`false`, the default) or encrypted `.ldc` saves (`true`). **Encrypt save contents** sets the native default for C++ Source packages. Any project, including Standalone, can override it with the global assignment `SAVE_AS_LDC = true` or `false` at the top of `Scripts/Entry.lua`, before all `require` calls. `Source.Save` captures the format on first load, and later assignments have no effect.

`GetSavePath(slot)` selects the extension for a 1-based slot number. Use stable slot numbers, validate data before serialisation, handle missing files explicitly, and avoid hard-coded save directories.

Save encryption is independent of project JSON encryption, although Pack Options groups both under **Encrypt game data**.

## Native containers at data boundaries

Convert Standard `list`, `tuple` and `dict` values to Lua tables before saving them as JSON:

```lua
local cjson = require("cjson")
local encoded = cjson.encode(payload:toTable())
```

Decoding JSON yields ordinary Lua tables. Tuple-key strings, `cjson.null` nil slots and record-array reconstruction are in [Ludork Lua Advanced](<../../01.Getting Started/04.Ludork Lua Advanced.md>). Never persist an internal tuple hash.

## Limitations

Changing the save format does not rename or migrate existing slots. Choose the format before release, or provide a migration. Save upgrades, atomic writes, backups, cloud synchronisation and tuple-key record formats remain project responsibilities.
