# Windows, Menus, Input and Controls

The default Lua UI uses JSON assets and generated View trees. Scenes create windows, Views provide their complete controls and nested panes, and the UI manager controls stacking. Business Controllers add model updates and input callbacks.

## Windows and menus

Window views follow the [Declarative UI Runtime Contract](<../04.Declarative UI/02.Runtime Contract.md>). Menus keep stable command identifiers separate from displayed text. Long descriptions use the existing wrapping and formatting helpers.

The title's Save/Load and Config windows and the map's optional windows use separate `Source.UIBase.LazyWindow` handles. Map entry creates the HUD and Region Title directly; Menu, Item, Equip, shops, Save/Load, Config, Enemy Book, Encyclopedia, Floor Teleporter and Player Name are created on their first display. The message window is created by the first message or selection. Opening Menu does not create its Item, Equip, Save/Load or Config windows. Each window's complete authored child tree is built on that first use, then reused until the owning scene is destroyed.

The in-game menu lists Items, Equipments, Files, Config and Return to Title. `WindowMenu.new(player, windows, onExit)` receives the scene's exit action and invokes it after the menu's closing animation. The scene owns the destination and assigns one stacking layer to the menu and its independent sub-windows. Selecting Config opens the shared Config window over the menu and deactivates the command list. Closing the Config window returns focus to the menu.

Every visible default screen has one top-level asset: Init, Title, Game Over, Region Title, HUD, Menu, Config, Message, Item, Equip, Shop, Save/Load, Attribute Shop, Enemy Book, Encyclopedia, Floor Teleporter and Player Name. Multi-pane screens nest their panes under one root, and sibling input hosts reuse the nested lists and scroll boxes.

Top-level window transitions are linear and default to 0.2 seconds. Internal panes and tabs switch immediately. Input is disabled during playback, and close results run after `FadeOut` hides the root. Initialisation and disposal hide immediately.

| UI | Timeline behaviour |
|---|---|
| Default windows and Config | `FadeIn`: centre Scale `0.5` to `1` plus colour; `FadeOut`: colour only. |
| Title command | `FadeIn`: local Y `80` to `0` plus colour. Opening Config or Save/Load does not hide it. |
| Map Menu | `FadeIn`/`FadeOut`: local X `-192` to `0` and back, plus colour. |
| Item and Equip | Menu animations only. Save/Load has both default and Menu pairs, while Config always uses the default pair. |
| Message | `Panel` colour only. |
| Game Over | Colour-only `FadeIn` (0.5 seconds) and `FadeOut` (1 second). Scene switching waits for `FadeOut`, which holds its transparent final frame until scene disposal. |
| Region Title | `Display` holds colour for one second, then fades for one second. |

Related `FadeOut` transitions may run in parallel.

Assets include representative `#TAB` and `#ITEM` children and Game visuals. Dynamic collections replace list placeholders before display, and Controllers localise TabView items without changing their count. Enemy Book and Encyclopedia use `CharacterView`. The runtime passes the real actor snapshot, while native code owns cropping, animation, scale and Shader/Hue effects. Enemy Book passes its cell dimensions through the collection's `logicalSize` argument. The cell Controller retains that size for name and special-tag layout, including language changes.

`Source.Windows` modules export UI classes through `Ui.DefineWindow`, with business behaviour in private Controllers. `WindowCommand` is a shared native command-window utility. UI authoring and file layout are described in [Declarative UI Authoring Workflow](<../04.Declarative UI/01.Authoring Workflow.md>).

On the title screen, an open Config or Save/Load window prevents the underlying command window from receiving any part of the same touch gesture.

`WindowBase` provides an optional 16 × 16 return button on the top-left border, outside `Content`. Cancellable windows enable it with `windowOptions.returnButton = true`, and implement `Controller:onReturn()` with the same state-aware step used by other Cancel inputs. That shared return step plays the System CancelSE once, so a second Cancel source must not play it again. Multi-pane groups expose the button only on the active interactive pane. Hidden, inactive or suppressed windows do not expose it.

`WindowBase` also embeds an `Engine.GamepadHintBar` on the bottom border, outside `Content`. Like the return button, it belongs to the window rather than an asset, and it stays empty unless a gamepad is connected and the window supplies hints. A window sets up to three `Engine.GamepadHint` entries with `setGamepadHints`, toggles one with `setGamepadHintEnabled`, reads `getGamepadHintCount` and `isGamepadConnected`, and handles completions through `setOnGamepadHintTriggered`. See [GamepadHintBar](<../08.Global and Core Modules/02.Core Modules/01.Engine/13.Interactive and Declarative UI Controls.md#gamepadhintbar>) for rendering and the one-second long-press.

Static command rows store a `localeKey`, while dynamic rows store literal `text`. A row must never define both. The row resolves `localeKey` when it refreshes, so a language change can update the existing controls without replacing their callbacks or cursor state. The title commands, in-game menu, save/load tabs, shop tabs and details, and a visible map-region title update immediately when the runtime language changes.

Whenever a reusable selectable window begins a new open session, its selectors start at zero and scroll to the top. An empty selector uses `nil`. This behaviour applies to the in-game menu, item and equipment windows, shops, Config and Enemy Book. Focus changes and in-place refreshes within that session preserve the selection.

The shop keeps its two-column item list focused while Q/E, LB/RB, mouse or touch switches Buy/Sell. Switching tabs resets the cursor and scroll, while a transaction refresh preserves a still-valid selection. Buy and Sell cells show the icon and current owned count, and details show the localised name, description, a localised `Price` label and the right-aligned price. Selling grants `floor(price / 2)` GOLD and omits zero-price results. Buy-only shops hide the tabs and centre the remaining panes. Cancel closes the shop.

Overflowing lists use `Engine.ScrollBox`. It clips rendering and hit testing, scrolls only overflowing axes, and keeps keyboard/controller selection visible. Native edge indicators show the remaining content. See [Engine: Layout and Image Controls](<../08.Global and Core Modules/02.Core Modules/01.Engine/10.Layout and Image Controls.md>).

The message window uses a full-screen Canvas and a transparent `FunctionalImage` to consume one click or tap for plain-message confirmation. Choice mode disables that layer, so blank-space clicks cannot select an option. Its maximum of four options fits directly in the panel without a ScrollBox. `SceneMap` only blocks map input while dialogue is active.

`SceneMap` owns one `LocaleChanged` subscription for its long-lived map windows. Active dialogue retains the raw speaker, message or options, explicit `localeArgs`, and snapshots of node-local and instance variables. It reruns template localisation and localises string `localeArgs`. It then applies those arguments and the two variable snapshots before updating the existing `WindowMessage` controls. Item and equipment details, shop tabs and details, attribute shops, Enemy Book, `WindowEnemyEncyclopedia`, and Teleporter (`WindowFloorTeleporter`) likewise refresh localised text in place while preserving their current selection, mode, focus and preview state. Hidden windows resolve the active language when they next open, while Config, save-slot and player-HUD controllers keep their own subscriptions. The player HUD also subscribes to `AbilitySystemChanged` and `PlayerChanged` from `EventKeys`, ignores payloads whose `owner` is another battler, and refreshes only the affected controls when a signature of the current player changes.

Language changes, loaded-player rebinding, visibility queries and input checks only inspect already-created windows through `peek()`. An unused window does not block map input or acquire focus, and its factory reads the current player, game instance and configuration when it is eventually opened. Destroying a scene disposes its handles, releasing existing windows without constructing unused ones.

The Teleporter opens with the current map's floor entry selected and scrolled into view, falling back to the first entry when the current map is absent. An empty list uses `nil`. Telepoint selection starts at the first entry. Its left slot alternates between the floor and telepoint lists, and cancelling telepoint selection restores the floors. The telepoint list scrolls without moving the right-side preview. A composite manifest remains one floor identity, with child maps composed at world offsets.

Telepoints are discovered through stair transfers or `Teleporter:goToMap(mapPath, position, record)` with `record` omitted or `true`, even before the Teleporter item is acquired. `goToMap` records the source actor's offset position and the exact destination tile on their respective maps, without searching for a destination stair. Passing `false` records neither endpoint. The window lists only the current map's region; a map without a configured region has an empty floor list. Opening the window or approaching stairs does not record a visit. Record structure and deduplication are described in [Runtime Data, Configuration and Saves](<06.Runtime Data Configuration and Saves.md>).

Telepoint labels resolve the recorded tag through `LOC`. Empty or automatically generated tags use the localised `POINT` number format, and missing translations retain the raw tag.

Keyboard, mouse and touch selection update the destination and preview before confirmation. The preview keeps a fixed scale and stays within map bounds, centring axes smaller than the view. Composite previews use the full manifest bounds.

Attribute shops expose display snapshots through `getOffers()` and validate purchases through `purchaseAttribute(key)`. A scalar price reference is shared by all offers, while an array sets per-offer prices. A purchase increments the corresponding price.

### Player name window

The NPC beside the starting point in `Map_01` opens `WindowPlayerName` and pauses map input until it closes. Activate the input to edit with the Confirm action. Tab/Shift+Tab and directional actions move between the input and Confirm.

Confirm stays visible for every input device. Mouse and touch activate the button. Keyboard Enter/Space applies the name when Confirm has focus, otherwise starts editing. The asset binds Confirm to a one-second X long-press (`gamepadButton = "X"`, `gamepadLongPress = true`) and does not populate the window hint bar. A only starts editing, including while Confirm has focus. Holding X applies the name from any focus in the active window. See [Button](<../08.Global and Core Modules/02.Core Modules/01.Engine/09.Runtime Values and Functional Controls.md#button>) for the empty-texture and hint appearance. The return button or Cancel discards the draft; while editing, Cancel (B or Escape) first ends editing and a second Cancel closes the window. Completing the mobile input dialog only updates the draft. Invalid names disable Confirm; see [Source.Player](<../07.Source Classes/09.Player.md>) for the validation rules. The HUD shows the confirmed name above the level, shortened to fit.

## Input

`Source.Configs.HotKey` maps native keys to a `Scene`, a `Filter` and optional `FunctionWhenPressed` / `FunctionWhenReleased` callbacks. Each callback receives the scene instance.

Runtime input comes from the C++ input service. Use documented key, mouse, controller and injected-input APIs rather than reading editor state. Embedded Windows mode forwards compatible input through the runtime protocol, while standalone games use the native window directly.

On Android and HarmonyOS, the host converts the system Back button or gesture into one Cancel/Escape pulse instead of closing or backgrounding the app. This conversion remains separate from HarmonyOS external-keyboard forwarding, which sends ordinary SFML-mapped keys as scancode edges, adds logical-key edges where they can be resolved, and preserves their modifier state. Two-finger touch remains a separate right-click cancellation gesture. System Back and two-finger touch both reach the focused window's `onReturn()`, but only the latter emits right-mouse input.

Physical Enter and Space use the Confirm action, while Escape uses Cancel. Keyboard press and release are edge events; see [Engine: Input and Services](<../08.Global and Core Modules/02.Core Modules/01.Engine/07.Input and Services.md>).

Controller buttons use the logical `Engine.JoystickButton.getA()` through `getShare()` values. Confirm is A/Cross and Cancel is B/Circle. Per-controller resolution, mappings and hints are in [Engine: Input and Services](<../08.Global and Core Modules/02.Core Modules/01.Engine/07.Input and Services.md>).

Default movement and menu directions use only left-stick `X`/`Y` and D-pad `PovX`/`PovY`. Horizontal wins when `|X| >= |Y|`, and vertical wins otherwise. Exact 45-degree input is horizontal. This same sector rule drives triggered navigation and held movement, and right-stick and trigger axes cannot steal the direction.

`WindowSelectable` owns the default Cancel key and the right-button close behaviour. Derived windows return unhandled input to it, so each edge produces one Cancel sound and one close transition.

## Focus and navigation

Keyboard and controller navigation needs an explicit focus order. A disabled or hidden control must not remain the active focus target. Test pointer activation and keyboard or controller activation independently.

## Configuration controls

Config opens on Graphics with its first row focused. Q/E, LB/RB, mouse hover and touch taps switch tabs and play CursorSE. Each tab keeps its cursor and scroll during that open session. Reopening resets all tabs, while a locale refresh preserves them.

Switching tabs silently collapses an open DropBox. Cancel and the return button also collapse it first, then close Config on the next input. [Game Settings Reference](<07.Game Settings Reference.md>) defines the settings.

On mobile, a Slider tap sets its value on release. After the drag threshold, horizontal movement belongs to the Slider, while vertical or tied movement belongs to the Config list. Gesture ownership remains fixed until release, and the list scrolls only when its content exceeds the visible area.

An expanded Config DropBox overlays the settings rows and owns input until it collapses or Config closes. Either restores parent-list input. A height-limited popup scrolls internally, and mobile touch uses preview-then-confirm. See [Engine: Interactive and Declarative UI Controls](<../08.Global and Core Modules/02.Core Modules/01.Engine/13.Interactive and Declarative UI Controls.md>).

Save/Load uses one shared slot list. Switching the Load/Save tabs preserves its cursor, scroll and detail. Reopening defaults to Load and the newest existing save, or slot zero when none exists; map hotkey S opens Save instead. Cancel closes it. Title load-only mode omits the tabs and centres the remaining panes.

Exact UI and input APIs are in the API reference, starting with [NodeFunctions.Container](<../06.Node Functions/01.Container.md>). Game-localised labels follow [Game Localisation Workflow](<../../05.Plug-in Development and Installation/06.Game Localisation Workflow.md>). Editor language switching is not part of this runtime section.

## Limitations

Embedded input forwarding is specific to supported Windows editor-run modes. A native standalone window remains the authoritative environment for final input, focus and controller testing.
