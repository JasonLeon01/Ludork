# Build and Module Layout

Use C++ Source projects when Lua and Blueprint APIs are insufficient, when a new native UI adapter is required, or when producing an iOS, HarmonyOS or Android build. The runtime uses C++20, CMake and declaration-driven bindings.

## Goal

Select the correct native module, build its generated bindings and load the resulting Lua modules in the supported order.

## Prerequisites

- A C++ Source project with CMake, a C++20 toolchain and its platform dependencies installed.
- A clean build configuration for the target platform.
- A supported target: Windows 10 or newer on x64, macOS 13.3 or newer on Apple Silicon, iOS 15.0 or newer on arm64, HarmonyOS 6.0.2 / API 22 or newer on arm64-v8a, or Android 7.0 / API 24 or newer on arm64-v8a.

Public headers contain ordinary C++ declarations plus empty-at-compile-time `BIND_*` markers. Core bindgen reads the module and shared Runtime declaration roots, then generates stable per-class sol2 sources, one module aggregate/stub source, a LuaLS stub and editor metadata.

## Steps

### 1. Choose a module

| Module | Responsibility | Native dependency direction |
|---|---|---|
| `LudorkRuntime` | Values, VM/binding services, Blueprint execution, typed/component data, JSON and Asset/Data/Script stores | Standard, SFML and private zlib; LuaSF in full mode; never Core modules |
| `Engine` | Engine types, services, state and gameplay foundations | LudorkRuntime and SFML |
| `GlobalCore` | Global game classes and services | Engine, Standard and SFML; optional platform/FFmpeg libraries |
| `GlobalFunctions` | `Components`, `UI`, `NodeGraph` and `Manager` free-function groups | GlobalCore and SFML |

`LudorkRuntime` is shared on desktop, static on mobile and exposes no Lua root; bindings remain under `Engine`. AssetStore, DataStore and ScriptStore provide the read-only Asset, Data and Lua-module boundaries for both loose and `.ldpak` layouts. Standard receives only DataStore file access, so script archives do not appear through filesystem APIs. Private zlib is used only for archive CRC32. Gameplay modules retain fixed load order, no reverse link to `GlobalFunctions`, and complete cross-module declarations.

`.ldpak` v1 is little-endian. Its `LDPK` header stores version, group, entry count, index range and CRC32; the UTF-8-byte-sorted file/directory index stores 64-bit offsets/sizes and data CRC32. Raw bodies are 8-byte aligned.

Runtime owns Blueprint class generation, Script Mixins, graph execution and latent scheduling. Engine supplies Actor graph lookup, EventBus and frame-loop integration. `RuntimeProviders.installBlueprint(classDataByPath, compileGraph, instantiateGraphTemplate)` installs its three Blueprint callbacks. ClassDict delegates to the VM resolver; cache and definition identity follow the [Blueprint runtime contract](<../03.Lua and Blueprint Scripting/04.Blueprint Scripting/01.Execution Flow Events and Variables.md#class-definitions-and-session-lifetime>).

Bootstrap-only native modules are host-owned: the application registers `cjson` and `cjson.safe`, Standard owns `Class` registration, and Engine uses its initialised native tables and APIs instead of reverse module links. Asset- and metadata-driven dynamic module resolution is unchanged.

`LUDORK_SAVE_AS_LDC` is an `OFF`-by-default CMake option that Standard exposes as `SAVE_AS_LDC` before Entry runs. C++ Source packaging sets it through **Encrypt save contents**.

Android and HarmonyOS application shells live under `Engine/PlatformHosts/Android` and `Engine/PlatformHosts/Harmony`. Build support lives in `Engine/cmake/`, including FFmpeg builds in `Engine/cmake/FFmpeg/`.

`LUDORK_WITH_LUA` defaults to `ON` and is required for game builds. The independent `UiPreviewHost` build sets it to `OFF` and uses native Runtime/Standard and SFML without Lua, LuaSF bindings or Blueprint execution.

Preview and game builds use separate directories: `.tools/UiPreviewHost/build` and `.tools/UiPreviewHost/bin/<configuration>` for preview; `Sample/build`, `Sample/Intermediate` and `Sample/bin` for the game.

### Session and module lifetime

Standard owns the Lua session. `runtime::initialize` requires a running Standard session; repeated calls preserve the attached Runtime state. After `runtime::shutdown` detaches Runtime, restarting it requires a new Standard session and Lua VM.

Standard shuts down modules in reverse dependency order (Global, Engine, Runtime) before releasing its state. The host owns the Lua VM and must wait for shutdown to finish on the thread that initiated it before calling `lua_close`.

AssetStore, DataStore, ScriptStore and Standard's read-only file provider are host configuration, independent of the VM session, and survive session shutdown.

### Host and implementation sources

Each independent class or bound type uses a same-named header and, when needed, source file. Public declarations belong under `include`, and member definitions under `src`. Owner-specific data types may be nested; shared data and helper collections may stay together.

Host-private implementation stays under `src` and uses an `Impl` suffix, such as `HostImpl.hpp` for `Host::Impl`. Larger implementations may use a same-name subdirectory and contribute sources through `target_sources`. Dependencies flow from the host into its implementation. Child directories must not include parent-private headers, including through include-root shortcuts; public headers must not include private headers.

Shared Runtime Lua services live in `Runtime/src/LuaServices`; pure ConfigVars parsing lives in `Runtime/src/Metadata`.

Standard ClassRuntime dependencies flow `Class → Composite → Instance → Native → Detail`, with downward shortcuts allowed. Detail owns neutral state and queries; Native owns native members and properties; Instance owns native construction and disposal; Composite owns indexing and metatables; Class coordinates allocation, finalisation and super. The boundary checker includes Standard and rejects upward layer includes, parent-private includes and cycles formed by those edges.

System privately composes Display, FramePipeline, SceneStack and Lifecycle. Display owns the window; FramePipeline owns the canvas, effects and transition targets; SceneStack owns queued operations and retired scenes; Lifecycle owns shutdown state. Components expose operations instead of mutable state aggregates. Frame presentation remains outside the scene logic lock, and render targets rebuild between frames.

`EngineState::CellSize` is a positive C++ compile-time constant. Editor builds generate their matching `EngineConstants.CellSize` from this declaration through ScriptTools. Changing it requires rebuilding the engine, editor and templates; there is no project-level or runtime override.

### Core headers and Runtime boundary

Core Lua-binding headers include `<CoreMinimal.hpp>` from `Engine/Runtime/include` for annotations, runtime types, common C++ types and SFML Graphics/Window/System. Include module exports and direct type dependencies explicitly; each public header must compile independently.

Handwritten Core, including private sources, accesses VM and binding services through Runtime without direct or transitive sol dependencies. Runtime also owns isolated audio execution; Core retains gameplay and playback policy. Generated bindings may use sol. Runtime internals use private operations within an active `RuntimeScope`; Facades provide the external entry boundary.

Choose API types, container ownership and Lua-reference operations using [Runtime Value Boundaries](<09.Runtime Value Boundaries.md>).

### 2. Build the project

```sh
./tools/build_cpp.sh Sample Debug
./tools/build_cpp.sh Sample Release
```

```bat
tools\build_cpp.bat Sample Debug
tools\build_cpp.bat Sample Release
```

`LUDORK_DEBUG_SOL_SAFETIES` defaults to `OFF`; enabling it adds full sol safety checks in Debug only. `LUDORK_OPTIMIZE_DEBUG` defaults to `ON` and independently controls Debug optimisation.

Validate host-to-implementation direction locally before building:

```sh
.tools/ScriptTools/ScriptTools impl-boundary-check Sample
```

```bat
.tools\ScriptTools\ScriptTools.exe impl-boundary-check Sample
```

The command discovers C++ boundaries from a host source and its same-name directory. Lua boundaries use the matching host/module directory convention and treat child modules with their own mirrored `.d.lua` as independent hosts. CMake exposes the same validation as the `ImplBoundaryValidate` target and makes Engine depend on it; Windows and macOS CI also run the direct command during native input validation. Violations report their source file and line without a second boundary manifest to maintain. It also rejects sol usage and resolved transitive sol includes in handwritten Core.

CMake reads LuaSF from `Sample/Engine/ThirdParty/LuaSF` by default. Select a locally generated tree with `cmake -S Sample -B Sample/build -DLUDORK_LUASF_SOURCE_DIR=/absolute/path/to/LuaSF/output`. This override applies only to that build directory; dependency initialisation uses the version pinned in `versions.conf`.

CMake runs `ScriptTools core-bindgen` automatically. Generated C++ files live under top-level `Intermediate/`, grouped by build directory and module; LuaLS stubs and metadata are emitted under `Scripts`. See [Generated Metadata and Stubs](<05.Generated Metadata and Stubs.md>) for output and regeneration details.

`Intermediate/` is excluded from templates and recreated by a normal build when missing. `bin/` and `build/` remain at the project root.

HarmonyOS packaging is an Apple Silicon macOS cross-build through DevEco Studio's OpenHarmony native SDK. Each package recreates its Stage and native build directories so a CMake cache cannot cross device forms or graphics backends. The HAP target and compatible SDK are both `6.0.2(22)`, and CMake receives `OHOS_COMPATIBLE_SDK_VERSION=22`; the toolchain therefore compiles Ludork, Lua, LuaSF and SFML for `aarch64-linux-ohos22.0.0` with API availability diagnostics enabled. A newer installed SDK is the compile SDK only and does not raise that deployment target.

The Mobile variant configures `SFML_HARMONY_DEVICE_FORM=MOBILE` and `SFML_OPENGL_ES=ON`, advertises `phone` and `tablet`, and uses the fixed-landscape mobile host. The 2in1 variants configure `SFML_HARMONY_DEVICE_FORM=2IN1`, advertise only `2in1`, support `fullscreen` and `floating` windows, publish `NEED_OPENGL=1`, request `ohos.permission.LOCK_WINDOW_CURSOR`, and set `SFML_OPENGL_ES=OFF` for OpenGL or `ON` for OpenGL ES. An FFmpeg-enabled HarmonyOS build uses the same versioned compiler target for its C/C++ compilation and linking while retaining the OpenHarmony sysroot, MUSL selection and availability checks.

A 2in1 OpenGL binary has a hard dependency on `libGLv4.so`. If the image lacks that library, the dynamic loader rejects the NAPI module before native initialisation; the binary does not switch to OpenGL ES.

Android packaging is a cross-build from Apple Silicon macOS. The packer invokes host CMake 3.28 or newer with `Unix Makefiles`, the highest complete stable NDK r27-or-newer toolchain found under the local SDK's `ndk` directory, `ANDROID_PLATFORM=android-24`, `ANDROID_ABI=arm64-v8a` and `ANDROID_STL=c++_static`. The project never contains its own SDK or NDK. Lua, LuaSF, Runtime, Core, cjson, SFML and optional FFmpeg targets are static; the single shared output is `libludork.so`, which Gradle consumes as a prebuilt `jniLibs` entry. Android Studio's SDK CMake and Ninja are not used.

### 3. Load the runtime modules

```lua
local Engine = require("Engine")
local GlobalCore = require("GlobalCore")
local GlobalFunctions = require("GlobalFunctions")

local Components = GlobalFunctions.Components
local UI = GlobalFunctions.UI
local NodeGraph = GlobalFunctions.NodeGraph
local Manager = GlobalFunctions.Manager
```

Load these three roots in the displayed order. `GlobalFunctions` groups are accessed through their tables and must not leak into the module root. Standard globals are already installed; `CoreSystem` is not a runtime module.
