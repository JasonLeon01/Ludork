# Build and Module Layout

Use C++ Source projects when Lua and Blueprint APIs are insufficient, when a new native UI adapter is required, or when producing an iOS, HarmonyOS or Android build. The runtime uses C++20, CMake and declaration-driven bindings.

One public declaration must drive C++ registration, LuaLS stubs and editor metadata. Never patch generated outputs or add generator branches keyed to a gameplay module, type or member name.

## Goal

Select the correct native module, build its generated bindings and load the resulting Lua modules in the supported order.

## Prerequisites

- A C++ Source project with CMake, a C++20 toolchain and its platform dependencies installed.
- A clean build configuration for the target platform.
- A supported target: Windows 10 or newer on x64, macOS 13.3 or newer on Apple Silicon, iOS 15.0 or newer on arm64, HarmonyOS 6.0.2 / API 22 or newer on arm64-v8a, or Android 7.0 / API 24 or newer on arm64-v8a.

Public headers contain ordinary C++ declarations plus empty-at-compile-time `BIND_*` markers. During a build, the Core bindgen reads those headers and generates stable per-native-class sol2 registration sources, one module aggregate/stub source, a module-level LuaLS stub and editor metadata.

## Steps

### 1. Choose a module

| Module | Responsibility | Native dependency direction |
|---|---|---|
| `CoreSystem` | Low-level system and utility functions | Independent module target; uses zlib |
| `Engine` | Engine types, services, state and gameplay foundations | Core binding/Standard, SFML and zlib |
| `GlobalCore` | Global game classes and services | Engine, Standard and SFML; optional platform/FFmpeg libraries |
| `GlobalFunctions` | `Components`, `UI`, `NodeGraph` and `Manager` free-function groups | GlobalCore and SFML |

The three root gameplay modules have a fixed Lua load order. `CoreSystem` is an independent module and is loaded only by code that needs it; this does not imply that Engine links to the CoreSystem target. `Engine` and `GlobalCore` do not link back to `GlobalFunctions`. Include complete declarations where a public signature crosses modules.

Bootstrap-only native modules are host-owned: the application registers `cjson` and `cjson.safe`, Standard owns `Class` registration, and Engine uses its initialised native tables and APIs instead of reverse module links. Asset- and metadata-driven dynamic module resolution is unchanged.

Complete platform application shells live under `PlatformHosts/Android` and `PlatformHosts/Harmony`. The packers copy these Gradle and Hvigor host projects when producing platform packages; `cmake` remains reserved for project CMake support and optional FFmpeg build wiring.

`UiPreviewHost` ships with its dedicated `UiPreviewHostRuntime` library and does not load the complete Engine Lua module. C++ Source projects continue to build and package the complete Engine module.

### Host and implementation sources

A source file implementing a public bound class is that class's host. Code used only by the host belongs below a same-name directory. Only the host source may define `Host::...` members. Files below the implementation directory contain independent state, ports, algorithms or runtime services: they do not include the host header, name the host type, use an upward `../` include, or call back through the host contract. The host owns orchestration and passes explicit data and lower-level dependencies down.

Keep a companion as an independent host when it has its own public binding contract. A subdirectory may have a `CMakeLists.txt` only when it represents a real target boundary with its own build contract. Engine and GlobalCore already discover ordinary sources recursively, so implementation folders do not add redundant sub-CMake files.

### 2. Build the project

```sh
./tools/build_cpp.sh Sample Debug
./tools/build_cpp.sh Sample Release
```

```bat
tools\build_cpp.bat Sample Debug
tools\build_cpp.bat Sample Release
```

Validate host-to-implementation direction locally before building:

```sh
.tools/ScriptTools/ScriptTools impl-boundary-check Sample
```

```bat
.tools\ScriptTools\ScriptTools.exe impl-boundary-check Sample
```

The command discovers C++ boundaries from a host source and its same-name directory. Lua boundaries use the matching host/module directory convention and treat child modules with their own mirrored `.d.lua` as independent hosts. CMake exposes the same validation as the `ImplBoundaryValidate` target and makes Engine depend on it; Windows and macOS CI also run the direct command during native input validation. Violations report their source file and line without a second boundary manifest to maintain.

The Sample CMake project reads LuaSF from `Sample/LuaSF` by default. To validate a locally generated LuaSF tree without copying into or editing that ignored dependency, configure with an absolute generated-project path, for example `cmake -S Sample -B Sample/build -DLUDORK_LUASF_SOURCE_DIR=/absolute/path/to/LuaSF/output`. This is a build-directory override only: it does not change `versions.conf`, and a clean dependency initialisation still downloads the pinned LuaSF version.

CMake invokes the standalone `ScriptTools` executable with the `core-bindgen` command for changed public headers. The implementation lives under `ScriptTools/core_bindgen`. For each bound native class, bindgen writes a stable `<Module>.<NativeClass>.auto.cpp` in the build tree; adding or removing a class does not renumber or rename unrelated class units. Each module also has exactly one `<Module>.stub.auto.cpp`. This source is both the module aggregate and the generated-stub writer: it owns module-level registration and calls the class units in binding order. There is no separate `<Module>.auto.cpp`.

Bindgen writes every generated file only when its content changes. An annotated-header edit therefore leaves unrelated class sources untouched so the build can reuse their object files. The module-level LuaLS stub and root metadata remain single files emitted under `Scripts`.

HarmonyOS packaging is an Apple Silicon macOS cross-build through DevEco Studio's OpenHarmony native SDK. Each package recreates its Stage and native build directories so a CMake cache cannot cross device forms or graphics backends. The HAP target and compatible SDK are both `6.0.2(22)`, and CMake receives `OHOS_COMPATIBLE_SDK_VERSION=22`; the toolchain therefore compiles Ludork, Lua, LuaSF and SFML for `aarch64-linux-ohos22.0.0` with API availability diagnostics enabled. A newer installed SDK is the compile SDK only and does not raise that deployment target.

The Mobile variant configures `SFML_HARMONY_DEVICE_FORM=MOBILE` and `SFML_OPENGL_ES=ON`, advertises `phone` and `tablet`, and uses the fixed-landscape mobile host. The 2in1 variants configure `SFML_HARMONY_DEVICE_FORM=2IN1`, advertise only `2in1`, support `fullscreen` and `floating` windows, publish `NEED_OPENGL=1`, request `ohos.permission.LOCK_WINDOW_CURSOR`, and set `SFML_OPENGL_ES=OFF` for OpenGL or `ON` for OpenGL ES. An FFmpeg-enabled HarmonyOS build uses the same versioned compiler target for its C/C++ compilation and linking while retaining the OpenHarmony sysroot, MUSL selection and availability checks.

A 2in1 OpenGL binary has a hard dependency on `libGLv4.so`. If the image lacks that library, the dynamic loader rejects the NAPI module before native initialisation; the binary does not switch to OpenGL ES.

Android packaging is a cross-build from Apple Silicon macOS. The packer invokes host CMake 3.28 or newer with `Unix Makefiles`, the highest complete stable NDK r27-or-newer toolchain found under the local SDK's `ndk` directory, `ANDROID_PLATFORM=android-24`, `ANDROID_ABI=arm64-v8a` and `ANDROID_STL=c++_static`. The project never contains its own SDK or NDK. Lua, LuaSF, Core, cjson, SFML and optional FFmpeg targets are static; the single shared output is `libludork.so`, which Gradle consumes as a prebuilt `jniLibs` entry. Android Studio's SDK CMake and Ninja are not used.

### 3. Load the runtime modules

```lua
local Engine = require("Engine")
local GlobalCore = require("GlobalCore")
local GlobalFunctions = require("GlobalFunctions")

local Components = GlobalFunctions.Components
local UI = GlobalFunctions.UI
local NodeGraph = GlobalFunctions.NodeGraph
local Manager = GlobalFunctions.Manager
```

Load these three roots in the displayed order. `GlobalFunctions` groups are accessed through their tables and must not leak into the module root. Code that needs the separate system module may use `local CoreSystem = require("CoreSystem")` outside this three-module sequence.

## Limitations

Building a module does not make reverse dependency directions valid. Cross-module public signatures still require complete declarations, and `CoreSystem` remains outside the fixed gameplay-root load sequence.

Per-class source identity does not remove ordinary C++ header dependencies. If one public header declares several bound classes, changing that header may recompile every generated class unit that includes it, although classes from unrelated headers keep their stable sources and objects.
