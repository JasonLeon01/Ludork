# Build and Module Layout

Choose a C++ Source project when the Lua and Blueprint APIs are insufficient, when a new native UI adapter is required, or when producing an iOS, HarmonyOS or Android build. The runtime uses C++20, CMake and declaration-driven bindings.

## Goal

Choose the correct native module, build its generated bindings and load the resulting Lua modules in the supported order.

## Prerequisites

- A C++ Source project with CMake, a C++20 toolchain and its platform dependencies installed.
- A clean build configuration for the target platform.
- A supported target: Windows 10 or newer on x64, macOS 13.3 or newer on Apple Silicon, iOS 15.0 or newer on arm64, HarmonyOS 6.0.2 / API 22 or newer on arm64-v8a, or Android 7.0 / API 24 or newer on arm64-v8a.

Public headers contain ordinary C++ declarations plus `BIND_*` markers that expand to nothing at compile time. Core bindgen reads the module and shared Runtime declaration roots, then generates one stable sol2 source per class, one module aggregate and stub source, a LuaLS stub and editor metadata.

## Steps

### 1. Choose a module

| Module | Responsibility | Native dependency direction |
|---|---|---|
| `LudorkRuntime` | Values, VM/binding services, Blueprint execution, typed/component data, JSON and Asset/Data/Script stores | Standard, SFML and private zlib, plus LuaSF in full mode; never Core modules |
| `Engine` | Engine types, services, state and gameplay foundations | LudorkRuntime and SFML |
| `GlobalCore` | Global game classes and services | Engine, Standard and SFML; optional platform/FFmpeg libraries |
| `GlobalFunctions` | `Components`, `UI`, `NodeGraph` and `Manager` free-function groups | GlobalCore and SFML |

`LudorkRuntime` is shared on desktop and static on mobile, and it exposes no Lua root. Bindings remain under `Engine`. AssetStore, DataStore and ScriptStore define the read-only Asset, Data and Lua-module boundaries for both the loose layout and the `.ldpak` layout. Standard receives DataStore file access only, so script archives never appear through filesystem APIs. Private zlib serves archive CRC32 only. Gameplay modules keep a fixed load order, do not link back to `GlobalFunctions` and carry complete cross-module declarations.

`.ldpak` v1 is little-endian. Its `LDPK` header stores the version, group, entry count, index range and CRC32. The file and directory index is sorted by UTF-8 byte order and stores 64-bit offsets and sizes plus a data CRC32. Raw bodies are 8-byte aligned.

Runtime owns Blueprint class generation, Script Mixins, graph execution and latent scheduling. Engine supplies Actor graph lookup, EventBus and frame-loop integration. `RuntimeProviders.installBlueprint(classDataByPath, compileGraph, instantiateGraphTemplate)` installs its three Blueprint callbacks. ClassDict delegates to the VM resolver. Cache and definition identity follow the rules in [Events, Common Functions and Blueprint Flow](<../03.Lua and Blueprint Scripting/03.Blueprint Scripting/01.Execution Flow Events and Variables.md#class-definitions-and-session-lifetime>).

Bootstrap-only native modules are host-owned. The application registers `cjson` and `cjson.safe`, Standard owns `Class` registration, and Engine uses its initialised native tables and APIs instead of reverse module links. Dynamic module resolution remains driven by assets and metadata.

`LUDORK_SAVE_AS_LDC` is a CMake option that defaults to `OFF`. Standard exposes it as `SAVE_AS_LDC` before Entry runs. C++ Source packaging sets this default through **Encrypt save contents**. Entry overrides follow the rules in [Runtime Data, Configuration and Saves](<../03.Lua and Blueprint Scripting/05.Default Gameplay/06.Runtime Data Configuration and Saves.md#saves>).

The game application host lives in `Application/` (`include/` and `src/`). Android and HarmonyOS application shells live under `Engine/PlatformHosts/Android` and `Engine/PlatformHosts/Harmony`. Build support lives in `Engine/cmake/`, including the FFmpeg builds in `Engine/cmake/FFmpeg/`.

`LUDORK_WITH_LUA` defaults to `ON` and is required for game builds. The desktop preview target of a project leaves that setting unchanged. Its dedicated `UiPreviewHostRuntime` compiles the project's UI implementation with preview resource loading. The Host does not start the game or create Lua Controllers.

Game builds also run `UiAssetGenerate` to synchronise generated Lua Views and typed stubs from UI JSON. This step needs no desktop preview. Full native asset validation still uses the project registry. The [Declarative UI Authoring Workflow](<../03.Lua and Blueprint Scripting/04.Declarative UI/01.Authoring Workflow.md>) describes generated and handwritten ownership.

Source preview and game binaries share `bin/<configuration>`. Desktop builds generate the project preview artifacts described in [Native UI Adapters](<08.Native UI Adapters.md#project-preview-artifacts>). Mobile cross-builds use an explicitly supplied desktop registry.

### Session and module lifetime

Standard owns the Lua session. `runtime::initialize` requires a running Standard session, and repeated calls preserve the attached Runtime state. After `runtime::shutdown` detaches Runtime, a restart requires a new Standard session and Lua VM.

Standard shuts down modules in reverse dependency order (Global, Engine, Runtime) before releasing its state. The host owns the Lua VM, and it must wait for shutdown to finish on the thread that initiated it before calling `lua_close`.

AssetStore, DataStore, ScriptStore and the Standard read-only file provider are host configuration. They are independent of the VM session and survive session shutdown.

### Host and implementation sources

Each independent class or bound type uses a same-named header and, where needed, a source file. Public declarations belong under `include`, and member definitions under `src`. Owner-specific data types may be nested. Shared data and helper collections may stay together.

Host-private implementation stays under `src` and uses an `Impl` suffix, such as `HostImpl.hpp` for `Host::Impl`. Larger implementations may use a same-named subdirectory and contribute sources through `target_sources`. Dependencies flow from the host into its implementation. Child directories must not include parent-private headers, including through include-root shortcuts, and public headers must not include private headers.

Shared Runtime Lua services live in `Runtime/src/LuaServices`. Pure ConfigVars parsing lives in `Runtime/src/Metadata`.

Standard ClassRuntime dependencies flow `Class → Composite → Instance → Native → Detail`, with downward shortcuts allowed. Each layer owns a distinct concern:

- Detail owns neutral state and queries.
- Native owns native members and properties.
- Instance owns native construction and disposal.
- Composite owns indexing and metatables.
- Class coordinates allocation, finalisation and super.

The boundary checker includes Standard and rejects upward layer includes, parent-private includes and cycles formed by those edges.

System privately composes Display, FramePipeline, SceneStack and Lifecycle. Display owns the window. FramePipeline owns the canvas, effects and transition targets. SceneStack owns queued operations and retired scenes. Lifecycle owns shutdown state. Components expose operations instead of mutable state aggregates. Frame presentation remains outside the scene logic lock, and render targets rebuild between frames.

`EngineState::CellSize` is a positive C++ compile-time constant. Editor builds generate their matching `EngineConstants.CellSize` from this declaration through ScriptTools. Changing it requires a rebuild of the engine, the editor and the templates. There is no project-level or runtime override.

### Native text input boundary

Engine owns the edit session through `Input/TextInputService.hpp`. Platform hosts implement `Input/TextInputHost.hpp`. The contract uses UTF-8, byte offsets at grapheme boundaries and caret rectangles in window-client pixels. Hosts return session-tagged events through a thread-safe sink. Service operations run on the game thread or before it starts. Standard provides Unicode segmentation and whitespace handling through utf8proc.

Windows embedded play keeps the HWND and IME context in the editor process. An embedded text host exchanges session-tagged text and composition events, together with client-pixel caret rectangles, over editor bridge protocol v1. It never subclasses the editor HWND from the game process. The editor and the runtime must use matching bridge versions. Disconnecting closes the edit session, keeps committed text and discards composition. Reconnecting does not reopen the session.

### Core headers and Runtime boundary

Core Lua-binding headers include `<CoreMinimal.hpp>` from `Engine/Runtime/include`. That header supplies annotations, runtime types, common C++ types and the SFML Graphics, Window and System modules. Include module exports and direct type dependencies explicitly. Every public header must compile independently.

Handwritten Core, including private sources, reaches VM and binding services through Runtime without direct or transitive sol dependencies. Runtime also owns isolated audio execution, while Core retains gameplay and playback policy. Generated bindings may use sol. Runtime internals use private operations within an active `RuntimeScope`. Facades provide the external entry boundary.

Choose API types, container ownership and Lua-reference operations using [Runtime Value Boundaries](<09.Runtime Value Boundaries.md>).

### 2. Build the project

```bash
./tools/build_cpp.sh Game Debug
./tools/build_cpp.sh Game Release
```

```text
tools\build_cpp.bat Game Debug
tools\build_cpp.bat Game Release
```

`LUDORK_DEBUG_SOL_SAFETIES` defaults to `OFF`. Enabling it adds full sol safety checks in Debug builds only. `LUDORK_OPTIMIZE_DEBUG` defaults to `ON` and independently controls Debug optimisation.

Validate host-to-implementation direction locally before building:

```bash
.tools/ScriptTools/ScriptTools impl-boundary-check Game
```

```text
.tools\ScriptTools\ScriptTools.exe impl-boundary-check Game
```

The command discovers C++ boundaries from a host source and its same-named directory. Lua boundaries use the matching host or module directory convention, and child modules with their own mirrored `.d.lua` count as independent hosts. CMake exposes the same validation as the `ImplBoundaryValidate` target and makes Engine depend on it. Windows and macOS CI also run the direct command during native input validation. Violations report their source file and line, so no second boundary manifest is needed. The check also rejects sol usage and resolved transitive sol includes in handwritten Core.

CMake reads LuaSF from `Game/Engine/ThirdParty/LuaSF` by default. Select a locally generated tree with `cmake -S Game -B Game/build -DLUDORK_LUASF_SOURCE_DIR=/absolute/path/to/LuaSF/output`. This override applies only to that build directory. Dependency initialisation uses the version pinned in `versions.conf`.

CMake runs `ScriptTools core-bindgen` automatically. Generated C++ files live under the top-level `Intermediate/` directory, grouped by build directory and module. LuaLS stubs and metadata are written under `Scripts`. See [Generated Metadata and Stubs](<05.Generated Metadata and Stubs.md>) for output and regeneration details.

`Intermediate/` is excluded from templates and recreated by a normal build when missing. `bin/` and `build/` remain at the project root.

HarmonyOS packaging is an Apple Silicon macOS cross-build through DevEco Studio's OpenHarmony native SDK. Each package recreates its Stage and native build directories, so a CMake cache cannot cross device forms or graphics backends. The HAP target and the compatible SDK are both `6.0.2(22)`, and CMake receives `OHOS_COMPATIBLE_SDK_VERSION=22`. The toolchain therefore compiles Ludork, Lua, LuaSF and SFML for `aarch64-linux-ohos22.0.0` with API availability diagnostics enabled. A newer installed SDK serves as the compile SDK only and does not raise that deployment target.

The Mobile variant configures `SFML_HARMONY_DEVICE_FORM=MOBILE` and `SFML_OPENGL_ES=ON`, advertises `phone` and `tablet`, and uses the fixed-landscape mobile host. The 2in1 variants configure `SFML_HARMONY_DEVICE_FORM=2IN1` and advertise only `2in1`. They support `fullscreen` and `floating` windows, publish `NEED_OPENGL=1`, request `ohos.permission.LOCK_WINDOW_CURSOR`, and set `SFML_OPENGL_ES=OFF` for OpenGL or `ON` for OpenGL ES. An FFmpeg-enabled HarmonyOS build keeps the same versioned compiler target for C and C++ compilation and linking, while retaining the OpenHarmony sysroot, MUSL selection and availability checks.

A 2in1 OpenGL binary has a hard dependency on `libGLv4.so`. If the image lacks that library, the dynamic loader rejects the NAPI module before native initialisation. The binary does not switch to OpenGL ES.

Android packaging is a cross-build from Apple Silicon macOS. The packer invokes host CMake 3.28 or newer with `Unix Makefiles`, the highest complete stable NDK r27-or-newer toolchain found under the local SDK's `ndk` directory, `ANDROID_PLATFORM=android-24`, `ANDROID_ABI=arm64-v8a` and `ANDROID_STL=c++_static`. The project never contains its own SDK or NDK. Lua, LuaSF, Runtime, Core, cjson, SFML and optional FFmpeg targets are static. The only shared output is `libludork.so`, which Gradle consumes as a prebuilt `jniLibs` entry. Android Studio's SDK CMake and Ninja are not used.

### 3. Load the runtime modules

```lua
local Engine = require("Engine")
local GlobalCore = require("GlobalCore")
local GlobalFunctions = require("GlobalFunctions")

local Components = GlobalFunctions.Components
local UI = GlobalFunctions.UI
local NodeGraph = GlobalFunctions.NodeGraph
local Manager = GlobalFunctions.Manager
```

Load these three roots in the displayed order. `GlobalFunctions` groups are accessed through their tables and must not leak into the module root. Standard globals are already installed. `CoreSystem` is not a runtime module.
