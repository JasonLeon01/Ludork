# Generated Metadata and Stubs

Generated files are build artefacts; do not edit them by hand.

One declaration feeds four generated outputs:

1. stable `<Module>.<NativeClass>.auto.cpp` registration units and exactly one `<Module>.stub.auto.cpp` used by the native Lua module;
2. `Scripts/stub/<Module>.d.lua` used by Lua language tooling;
3. `Scripts/<Module>_meta.lua` used by the editor, including the generated Engine, GlobalCore and GlobalFunctions catalogues.
4. `<Module>.traits.auto.hpp`, privately force-included by its native module and aggregating dynamic-value and opaque-identity traits from declarations and type registries.

These outputs must agree on the canonical module path, class name, function group and parameter order. Metadata additionally carries Blueprint execution and editor information.

Class filenames derive from the qualified C++ type name, independently of the Lua `name` option. `<Module>.stub.auto.cpp` registers the module, calls class units in binding order and provides the LuaLS stub writer.

Every logical public `BIND_METHOD` is included in metadata. `metadata = false` is reserved for internal helpers and secondary adapter overloads; it leaves the native registration and LuaLS stub intact. Bindgen rejects duplicate exposed method names within one type instead of silently overwriting an entry.

Generated stubs declare classes, ungrouped functions and module properties at the module root, such as `Engine.ListView`. Grouped functions appear in the table declared by `BIND_FUNCTION_GROUP`. Nested C++ types follow the naming rules in [Binding a Class](<02.Binding a Class.md#5-bind-owner-specific-nested-types>).

Each `BIND_ENUM` owns one module-root table; LuaLS keeps its nominal type, while runtime values and Blueprint metadata signatures use the underlying integer.

Core bindgen preserves complete multiline `///` documentation, including blank paragraphs and command lines, for ordinary and `Pure = true` members. It converts recognised Doxygen commands such as `\brief`, `\param`, `\return`, `\see`, `\code`/`\endcode`, warnings and inline formatting commands to the corresponding `@` form in `.d.lua`; unrelated backslashes, including path content, remain unchanged. LuaSF uses the same rule when it emits `Scripts/stub/LuaSF.d.lua`.

## Defaults and types

Bindgen may derive defaults only from safe boolean, numeric, string or empty-table member initialisers. Explicit complex defaults use annotation-native brace data; quoted JSON arrays and objects are rejected. Core object references use the full module/type pair. Arrays append `[]` to the type item.

LuaSF exports an absolute `LUASF_CALLBACK_CODECS_FILE` CMake path. Core bindgen consumes that schema-versioned manifest for callback aliases whose Lua calling convention differs from their canonical `std::function` type. Selection uses the declared semantic alias before canonical expansion; an unrelated alias with the same C++ signature does not inherit the codec. The manifest supplies the codec, named Lua type and exact Lua signature, so neither Core binding code nor ScriptTools contains an SFML callback-signature table. Codec-aware conversion composes recursively through `vector`, `array`, `optional`, `variant`, `pair`, `map` and `tuple` parameters and returns while preserving the callback policy at each leaf. A missing manifest or adjacent `sfml_api.json`, unsupported schema, duplicate selector, direction mismatch or disallowed `nil` stops generation. The generated codec use also asserts the alias against both the manifest and LuaSF API canonical types, so a stale canonical type stops compilation before the binding is available.

## Regeneration

Run the normal CMake build to add, update or remove generated class units and module outputs. Bindgen writes only changed content, preserving unchanged files' names and timestamps. If output appears stale, confirm that the annotated header belongs to the module's configured public-header set, inspect generator diagnostics and rebuild.

Changes to included headers may still recompile dependent class units even when their generated content is unchanged.

The pages in Blueprint API Reference describe the metadata catalogue; use LuaLS stubs for the full scripting API.
