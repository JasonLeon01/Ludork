# General Data

General Data is the editor-managed database beneath `Data/General`, suited to enemies, items, equipment, player presets, states and other data shared by many maps or Blueprints. Each JSON file defines a type schema and named members.

## Goal

Define a reusable data schema, enter validated members and create Text Config without breaking existing runtime references.

## Type structure

| Key | Meaning |
|---|---|
| `params` | Ordered field definitions with `type`, `defaultValue`, optional `comment`, required `itemType`/`valueType` for containers and a reference selector |
| `members` | Named records that store values for those fields |
| `events` | Optional ordered event names; each member may store an independent graph for them |

Supported fields include strings, booleans, integers, floating-point values, files, lists, dictionaries, `sf.Vector2f/i/u`, `sf.Vector3f/i/u`, `sf.Color` and `sf.IntRect`. Lists require `itemType`; string-keyed dictionaries require `valueType`. Containers may use `any` for heterogeneous JSON values, but cannot nest. Missing subtypes, missing or unknown non-underscore member fields, and values that do not match the schema fail during load. SFML arrays are constructed at that boundary; `any` preserves JSON literal types and never evaluates strings. Runtime consumers use the resulting typed member directly.

`linkedType` is unsupported and rejected.

Each field definition may store an optional English `comment`. Enter it through **Comment** when adding or editing a field; an empty comment is omitted. Form field names and Table headers show the comment on hover. This schema comment is distinct from a member value stored in a field that happens to be named `desc`, and it is plain project text rather than a locale key.

A reference declaration narrows a string value to another General Data type, an animation or another supported resource. List references apply to string items; dictionary references apply to string keys. An empty reference displays **— None —** and remains an empty string in JSON. Adding a referenced dictionary row keeps it pending until a real key is selected, so the editor never saves a placeholder such as `key`.

## Steps

1. Open **Database → General Data** (F9).
2. Select or create a type.
3. Define fields before creating many members. Right-click a Form field name to edit its definition.
4. Add members and fill their values.
5. Manage type events from the context menu, then open member graphs with **Edit Ability Graph**. Event renames and deletions update all member graphs; runtime activates them explicitly.
6. Inspect references before renaming or deleting types and members.
7. Save and exercise the runtime path that reads the data.

Saving regenerates the runtime/LuaLS pairs for `Source.Configs.GeneralEnum` and `Source.Configs.GeneralDataTypes`. `GeneralEnum` contains ordered type/member constants; `GeneralDataTypes` defines each `<TypeName>AttributeSet` and `Create(typeName, memberID, memberData)`, which copies a typed member and its ID. Do not edit generated files.

Editing a field can change its name, type, container item/value type, default and comment. Renaming preserves each member's current field value. Changing the field type, a list's item type or a dictionary's value type first asks for confirmation, then resets that field in every existing member to the new default value. Changing only the default does not overwrite existing members. Removing a field removes its meaning but does not automatically repair scripts that read it.

## Search and views

The member search is case-insensitive and matches member IDs plus direct scalar values such as names, numbers and booleans. It does not recursively search list, dictionary, tuple or graph content. The active search, selected member and Form/Table choice are kept for each data type while the General Data window remains open, including after Undo or Redo rebuilds the page; they are not written to the project.

Form presents the complete editor for one member. Table presents the ID and schema fields in declaration order, and directly edits boolean, integer, floating-point and string fields. Referenced strings keep their selector. File, list, dictionary, tuple and unknown structured fields show a summary with **Edit**; choosing it selects that member and returns to Form so structured JSON is never replaced by a display string. Table rows are vertically virtualised and the fixed-width columns scroll horizontally.

Continuous text and numeric changes in one focused field form one Undo step. Check boxes, selectors, member operations and schema operations remain separate steps. Saving, Undo and Redo split the current focused edit before later input begins a new step.

## Game Variable Manager

Open **Database → Game Variables** (F8) to declare mutable values shared by Blueprint and the active game instance. The left side lists declared variable names. Select one to edit its type, initial value and optional remark on the right; the remark is editor-only and has no runtime effect. Variable names are runtime identifiers, so keep them stable after graphs, maps or scripts begin to reference them.

Use the search box to filter variable names case-insensitively. **New Variable** adds a declaration after asking for its name and type; **Delete Variable** removes the selected declaration after confirmation.

![Game Variable Manager with a selected integer variable](../../_images/editor/game-variables.png)

*The selected declaration's type, initial value and editor-only remark are edited in the detail panel.*

Choose the type when creating a variable. The manager offers `bool`, `int`, `float`, `string`, `list` and `dict`; these are written to metadata as `bool`, `int`, `float`, `string`, `any[]` and `Dict[string, any]` respectively. Lists and dictionaries use ordinary Lua tables, not Standard's native `list` or `dict`. Changing an existing variable's type clears its initial value and replaces it with the new type's empty default.

Opening the manager creates `Scripts/Source/Configs/GameVariables.lua` and `GameVariables_meta.lua` when needed, and each successful change regenerates the pair. The runtime file maps each name to its initial value. The metadata file stores the ordered names, their declared types and `Meta.Remark` only when a remark is non-empty. Both files are generated outputs and carry a warning not to edit them manually.

Blueprint fields or node parameters marked with `InstVar` use a searchable selector instead of a free-form text box. A corresponding `InstVarValue` field reads the selected declaration's type and switches to the normal editor for that type. A type-filtered selector, such as the Sample conditional door, only lists compatible variables.

## Text Config

Ordinary UI text is styled on its UI node. Use **Game → New Text Config** only for shared or specialised text and rich tag styles. Keep referenced keys stable and validate the runtime consumer after schema changes.

![Text Config editor](../../_images/editor/text-config.png)

*Text Config provides a focused editor for structured text data used by the project.*

General Data preserves every string exactly as stored. String fields are not localised automatically because the same field type also carries semantic identifiers such as class, animation and equipment-slot keys. Pass brace-wrapped display values such as `{ITEM_NAME}` through `LOC` only at the presentation boundary, and resolve them again when a long-lived UI reacts to a language change. The catalogue format and runtime formatter are documented in [Game Localisation Workflow](<../05.Plug-in Development and Installation/06.Game Localisation Workflow.md>).

`Source.Gameplay.GeneralDataGraphAbility` activates member graphs explicitly with `GameplayEventData` context. They expose no pseudo parent/self node; use global nodes and that context. A `null` start returns `NoGraph`; graphs are synchronous, reject latent nodes and propagate errors.

The graph-only editor takes its event list from the type's `events` and has no class attributes or Blueprint inheritance. Project save rejects undeclared events and latent nodes.

See General Data Reference for the exact Sample schemas.

## Limitations

Changing a schema or game-variable declaration cannot automatically repair scripts, graphs, saves or string references. General Data and generated game-variable declarations are project definition data, not stores for mutable play-session state.
