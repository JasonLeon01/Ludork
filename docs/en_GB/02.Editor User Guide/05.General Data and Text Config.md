# General Data and Text Config

General Data is the editor-managed database beneath `Data/General`, suited to enemies, items, equipment, player presets, states and other data shared by many maps or Blueprints. Each JSON file defines a type schema and named members. Its Form, Table and member ability-graph windows share one document and one Undo/Redo history for that type file.

## Goal

Define a reusable data schema, enter validated members and create Text Config without breaking existing runtime references.

## Type structure

| Key | Meaning |
|---|---|
| `params` | Ordered field definitions with `type`, `defaultValue`, optional `comment`, required `itemType`/`valueType` for containers and a reference selector |
| `members` | Named records that store values for those fields |
| `events` | Optional ordered event names; each member may store an independent graph for each one |

Supported fields include strings, booleans, integers, floating-point values, files, lists, dictionaries, `sf.Vector2f/i/u`, `sf.Vector3f/i/u`, `sf.Color` and `sf.IntRect`. Lists require `itemType`, and string-keyed dictionaries require `valueType`. `type`, `itemType` and `valueType` also accept the recursive container and union schemas defined by [Blueprint Metadata](<../03.Lua and Blueprint Scripting/03.Blueprint Scripting/02.Metadata Schema and Decorators.md>). Select a union branch before entering its value.

Loading fails on a missing subtype, on a missing or unknown non-underscore member field, and on any value that does not match the schema. Use `any` for heterogeneous JSON values, because it preserves literal types and never evaluates strings.

`linkedType` is unsupported and rejected.

Each field definition may store an optional English `comment`. Enter it through **Comment** when adding or editing a field, and an empty comment is omitted. Form field names and Table headers show the comment on hover. This schema comment is distinct from a member value stored in a field that happens to be named `desc`, and it is plain project text rather than a locale key.

A reference declaration narrows a string value to another General Data type, an animation or another supported resource. List references apply to string items, and dictionary references apply to string keys. An empty reference displays **— None —** and remains an empty string in JSON. Adding a referenced dictionary row keeps it pending until a real key is selected, so the editor never saves a placeholder such as `key`.

A General Data type declared in a field's reference schema counts as a file reference even when no member value is selected. Renaming updates recognised schema keys, including self references, under the shared [reference-update rules](<01.Start Page Workspace and Shortcuts.md#editing-and-saving>). Remove and save these declarations before deleting the referenced type. Ordinary strings and Lua or C++ source are not rewritten.

## Steps

1. Open **Database → General Data** (`F9`).
2. Select or create a type.
3. Define fields before creating many members. Right-click a Form field name to edit its definition.
4. Add members and fill their values.
5. Manage type events from the context menu, then open member graphs with **Edit Ability Graph**. Event renames and deletions update all member graphs, and the runtime activates the graphs explicitly.
6. Inspect references before renaming or deleting types and members.
7. Save and exercise the runtime path that reads the data.

Saving regenerates `Source.Configs.GeneralEnum` (type and member constants), `Source.Configs.GeneralDataTypes` (typed `<TypeName>AttributeSet` classes) and their LuaLS declarations. Use `GeneralDataTypes.Create(typeName, memberID, memberData)` to restore a stored member with its ID and field types. Do not edit the generated files.

Editing a field can change its name, type, container item or value type, default and comment. Renaming preserves each member's current field value. Changing the field type, a list's item type or a dictionary's value type first asks for confirmation, then resets that field in every existing member to the new default value. Changing only the default does not overwrite existing members. Removing a field removes its meaning but does not automatically repair the scripts that read it.

## Search and views

The member search is case-insensitive and matches member IDs plus direct scalar values such as names, numbers and booleans. It does not recursively search list, dictionary, tuple or graph content. The active search, the selected member and the Form/Table choice are kept for each data type while the General Data window remains open, including after Undo or Redo rebuilds the page. They are not written to the project.

Form presents the complete editor for one member. Table presents the ID and schema fields in declaration order, and directly edits boolean, integer, floating-point and string fields. Referenced strings keep their selector. File, list, dictionary, tuple and unknown structured fields show a summary with **Edit**, and choosing it selects that member and returns to Form, so structured JSON is never replaced by a display string. Table rows are vertically virtualised, and the fixed-width columns scroll horizontally.

Text and numeric inputs follow the shared [Undo rules](<01.Start Page Workspace and Shortcuts.md#editing-and-saving>), and member and schema operations remain separate steps.

## Game Variable Manager

Open **Database → Game Variables** (`F8`) to declare mutable values shared by Blueprint and the active game instance. The left side lists the declared variable names. Select one to edit its type, initial value and optional remark on the right, and the remark remains editor-only with no runtime effect. Variable names are runtime identifiers, so keep them stable once graphs, maps or scripts begin to reference them.

Use the search box to filter variable names case-insensitively. **New Variable** adds a declaration after asking for its name and type, and **Delete Variable** removes the selected declaration after confirmation.

![Game Variable Manager with a selected integer variable](../../_images/editor/game-variables.png)

*The selected declaration's type, initial value and editor-only remark are edited in the detail panel.*

Choose the type when creating a variable. The manager offers `bool`, `int`, `float`, `string`, `list` and `dict`, and these are written to metadata as `bool`, `int`, `float`, `string`, `any[]` and `Dict[string, any]` respectively. Lists and dictionaries use ordinary Lua tables, not the native `list` or `dict` of Standard. Changing an existing variable's type clears its initial value and replaces it with the empty default of the new type.

The manager treats `Scripts/Source/Configs/GameVariables.lua` and `GameVariables_meta.lua` as one document with a shared Undo/Redo history. Opening it writes nothing, and missing files are generated on global Save. Edits immediately update declarations and selectors in memory.

Global Save regenerates both files together, and generation or write failures leave the document modified. The runtime file maps names to initial values, while the metadata stores ordered names, types and non-empty `Meta.Remark` values. Do not edit these generated files manually.

Blueprint fields or node parameters marked with `InstVar` use a searchable selector instead of a free-form text box. A corresponding `InstVarValue` field reads the type of the selected declaration and switches to the normal editor for that type. A type-filtered selector, such as the Game project conditional door, lists compatible variables only.

## Text Config

Ordinary UI text is styled on its UI node. Use **Game → New Text Config** only for shared or specialised text and rich tag styles. Keep referenced keys stable, and validate the runtime consumer after any schema change.

![Text Config editor](../../_images/editor/text-config.png)

*Text Config provides a focused editor for structured text data used by the project.*

General Data preserves every string exactly as stored. String fields are not localised automatically, because the same field type also carries semantic identifiers such as class, animation and equipment-slot keys. Pass brace-wrapped display values such as `{ITEM_NAME}` through `LOC` only at the presentation boundary, and resolve them again when a long-lived UI reacts to a language change. The catalogue format and the runtime formatter are documented in [Game Localisation Workflow](<../05.Plug-in Development and Installation/06.Game Localisation Workflow.md>).

`Source.Gameplay.GeneralDataGraphAbility` activates member graphs explicitly with `GameplayEventData` context. Those graphs expose no pseudo parent or self node, so use global nodes and that context. A `null` start returns `NoGraph`. All graphs are synchronous, reject latent nodes and propagate errors.

The graph-only editor takes its event list from the type's `events` and has no class attributes or Blueprint inheritance. Project save rejects undeclared events and latent nodes.

See the General Data Reference pages for the exact Game schemas.

## Limitations

Changing a schema or a game-variable declaration cannot automatically repair scripts, graphs, saves or string references. General Data and the generated game-variable declarations are project definition data, not stores for mutable play-session state.
