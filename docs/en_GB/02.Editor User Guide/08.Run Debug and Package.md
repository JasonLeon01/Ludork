# Running, Testing and Packaging

## Goal

Run the project with actionable diagnostics, test the native executable and produce a complete package for a supported target.

## Construct, Export and Play

The toolbar orders its actions as **Construct → Export → Play**. Standalone projects hide Construct. **Construct** saves the project and builds the Debug executable and preview runtime without launching the game. Native binding generation remains part of the build; UI and locale export is a separate operation.

**Export** saves and validates the project, runs the Export plug-in hooks, generates UI Views and declarations, then records success in `EditorCache/ProjectExport.json`. Official Locale Tools exports the workbook through this hook. The record survives reopening the project and fingerprints the UI JSON, Lua modules and handwritten declarations used for window generation, plug-in-declared inputs, generated files, generator and export plug-ins. Added, modified or deleted inputs, missing or modified outputs, and changed generators or export plug-ins require another export. If inputs change during export, or export fails or is cancelled, that attempt does not publish a successful record.

Variables and General Data still take effect on Save; their Lua files remain under version control and are outside Export. Ordinary Save, Construct, direct run and template creation do not generate UI files. The explicit `ui-assets generate` command produces UI files only; it does not run Export hooks or publish a complete editor export record.

Play stays disabled until the project has a successful Export record and, for C++ Source, a successful Debug build record. Its tooltip gives Construct priority over Export when both are missing. Standalone requires only Export. **Construct** and a successful Debug `tools/build_cpp` publish the shared build record; a bare CMake build does not.

The project-root `EditorCache/` contains build and export records, UI preview metadata, the editor map catalogue and the default animation MP4 output. Git ignores this directory. Removing its records requires another Construct for C++ Source and another Export before Play; the CMake build directory remains `build/`, and runtime animation caches remain under the game's user-data `Cache/Animations`.

Once those records exist, stale content does not disable Play. Clicking Play first checks Construct and offers **Build and Play** when native sources or outputs are stale. It then checks Export and offers **Export and Play** when export inputs or outputs are stale. Cancelling or failing either step ends the attempt. Play saves and validates the project and runs before-Run hooks, then rechecks Construct followed by Export before launch; changes during preparation require the same confirmations. Lua, UI JSON, game data and localisation changes do not require a native build. Source edits and window activation do not start background checks.

Each project reuses a prewarmed process for read-only checks. Prewarming does not scan file contents; every requested check compares the current contents again. Cancelling a check or closing the project releases the process.

While Play is preparing or running the game, its button becomes **Stop**. Clicking Stop cancels preparation or stops the current process. Construct and Export disable repeated actions and project editing until completion. Natural exit, cancellation and failures restore editing; closing the project cancels active preparation.

**Individual Window** opens a separate game window and keeps the selected map or world visible in the editor. Project editing, including already open document windows, Undo/Redo and editing shortcuts, is disabled during preparation, compilation and export. Running keeps these restrictions unless **Live Debug** was enabled before Play; see below. The Console, performance monitoring and Help remain available. Embedded mode instead displays the Windows runtime inside the editor and locks the game viewport layout. This window choice is configurable only on Windows; other platforms always use an individual window. An unavailable Windows embedded handle fails with `EmbeddedHandleUnavailable`.

Failures are reported in the operation dialog and Console. An export failure prevents Play or Pack from continuing; correct the first validation, hook or generation error and export again.

## Live Debug

Enable **Edit → Development Tools and Settings → Live Debug** before Play to edit the running map from the editor. The project preference defaults to off and cannot change during preparation or running. It requires **Individual Window**; selecting embedded mode clears and disables it. Preparation, Construct and Export keep their normal editing locks.

Once the game is running, the editor follows the player's current ordinary map or the current child of a composite world. Manual map switching is disabled. World holes, maps that are still loading, scenes without a live player and an unavailable connection are read-only. **File Explorer** can browse and locate resources; creating, renaming, moving, deleting and editing project files remain disabled.

On existing editable layers, Live Debug allows:

- The same tile brush as [project map editing](<03.Tilesets Autotiles and Maps.md#layers-and-painting>): paint, erase, sample and fill. Layer structure, visibility, tileset assignment, map properties, lights and world placements stay locked.
- Selecting and deleting live Actors, including the player, runtime-spawned Actors and child Actors, and moving top-level Actors. The editor cannot add, paste or duplicate Actors.
- Reading **Actor Info** and changing ordinary variables. **Components**, the parent class, Blueprint identity and map tags stay read-only.

Actor positions, creation, destruction and inspected values follow the running game. Moving an Actor cancels its current movement route. Deletion uses normal Actor destruction and its existing lifecycle callbacks. Hidden Actors remain inspectable according to the [map preview rules](<03.Tilesets Autotiles and Maps.md#lights-and-actors>); hidden layers stay read-only. Live edits have no Undo/Redo and do not write project documents or mark them modified.

**World Outliner** nests child Actors under their current parents. Clicking or dragging a child on the map selects its top-level owner; dragging moves that owner and its descendants. Select a child in **World Outliner** to inspect or edit ordinary variables, or to delete it through its normal lifecycle. Direct child movement, including **Actor Info** coordinates, is disabled.

Edits belong to the live Actor or map instance. They remain while that instance exists, including a dormant world instance, and are not replayed onto rebuilt instances. Rebuilt instances use the project's definitions and the normal gameplay persistence records. Game saves continue to work and may keep gameplay state affected by live edits; this mode protects project source data, not save slots.

Stopping, natural exit or a launch failure restores the project map view and the map selected before Play, and discards the temporary snapshots. The game in an **Individual Window** keeps running while the editor has focus.

## Reload Lua while running

Save the changed Lua source files in your external editor, enter `$r` in the Console, then press `Enter` or **Send**. This updates existing functions while preserving the scene, objects and runtime state. The game must be launched from the editor and use loose Lua sources.

The Console reports the result. Changes to data or module structure may require a restart; see [Lua hot reload](<../03.Lua and Blueprint Scripting/01.Lua Runtime and Modules.md#lua-hot-reload>) for the supported changes and the failure handling.

## Test layers

- Validate modified Blueprints before saving.
- Test maps in the editor with Console output visible.
- Use the Performance Monitor for frame and logic timing.
- Run the native executable outside the editor to catch working-directory assumptions.
- Test the packaged result, because its writable settings and asset layout differ from editor mode.

## Packaging

Choose **File → Pack Project**, select the target and follow the packaging log. The project must have a valid entry script and a compatible template. Define exactly one top-level `local APP_NAME` in `Scripts/Entry.lua` as a non-empty static string literal unique to the game, without control characters or later reassignment. Packaging rejects the sample value `LudorkSample`, a missing definition and expressions that require executing Lua to determine the name.

Packaged application display names use `APP_NAME`. Output paths use `<game-name>`, the same name sanitised for filenames, retaining platform, architecture and signing suffixes where applicable. The project folder name and `Data/Configs/System.json` title do not affect package names; the System title continues to control the game's existing runtime title behaviour. Generated application and bundle identifiers also derive from `APP_NAME`. A different name can change the installed application's identity and require new signing or provisioning setup.

Each editor Pack performs one complete Export, including Export hooks and UI generation, before continuing with before-Pack hooks and packaging. Official Locale Tools uses its before-Pack hook only to exclude `Data/Locale/Locale.xlsx`. Direct command-line run and pack consume files exported beforehand; they keep their validation but do not perform complete Export or implicit UI generation.

**Encrypt game data** controls script compilation and shader, JSON and save encryption, and a partial selection shows its indeterminate state. **Encrypt save contents** sets the C++ Source runtime default. Standalone projects configure it through `SAVE_AS_LDC` in `Scripts/Entry.lua`. See [Saves](<../03.Lua and Blueprint Scripting/05.Default Gameplay/06.Runtime Data Configuration and Saves.md#saves>) for the timing and format rules. The `.ldpak` option is independent of encryption.

Packaging requires a valid project preview registry. See [Declarative UI Validation and Packaging](<../03.Lua and Blueprint Scripting/04.Declarative UI/05.Validation and Packaging.md>) for the build and recovery requirements.

Finalisation validates a staging copy against the source project registry, then applies plug-in exclusions and the selected compilation, encryption and archiving. It removes development files, preview-specific binaries and project-root `EditorCache`/`Cache`, while retaining shared game dependencies. Directories named `EditorCache` or `Cache` inside `Assets`, `Data` or `Scripts` remain ordinary project content.

### Loose and packed output

Every platform keeps the runtime files, `Assets`, `Data` and the runtime `Scripts` as loose directories by default. The `.ldpak` option is clear by default. When it is selected, the complete contents of each directory become root `Assets.ldpak`, `Data.ldpak` and `Scripts.ldpak`. Archive entries retain paths relative to their original directory, so resource paths, Data paths and Lua module names stay unchanged. Encryption and Lua compilation run before archiving, and an archive does not encrypt its contents by itself. The option is independent of encryption. Mobile packages enforce the same loose-or-packed contract, and Android and HarmonyOS do not recompress `.ldpak`.

Resource packaging rejects symbolic links, case collisions, illegal paths and output conflicts. A package contains either all three loose directories (`Assets`, `Data`, `Scripts`) or all three root archives. Corrupt archives, missing roots, mixed layouts and old per-group archives are rejected.

Finalisation removes the development-only `Scripts/stub` tree. Any other `.d.lua` file left under `Scripts` fails packaging.

### Windows and macOS

Windows output is `dist/<game-name>/Main.exe` with its runtime files alongside it. macOS output is `dist/<game-name>.app`, whose display and bundle names use `APP_NAME`. A custom output directory replaces `dist` as the parent directory. Repacking replaces only the package for the current name and preserves sibling packages and unrelated files in that directory. The package directory and its ancestors must not be symbolic links or directory junctions.

Windows and macOS packages copy the runtime files, `Assets`, `Data` and the runtime `Scripts`. Standalone packages keep a root launcher and place the runtime binaries in the platform package directory (`Binaries` on Windows, `Contents/Frameworks` for a macOS app). FFmpeg notices and source-offer material are included where applicable; see [FFmpeg option](<../01.Getting Started/02.Project Templates.md#ffmpeg-option>) for the distribution requirements. Windows packages exclude PDB files; retain them with the corresponding build for debugging.

For both C++ Source and Standalone projects, macOS packaging removes local native symbols with `strip -x` from the final app's Main executable and real dynamic-library files, skipping symbolic links. After dependency-path adjustments, the packer applies ad-hoc signatures to those binaries; after resource finalisation, it signs and verifies the whole app. A strip or signing failure stops packaging. Source build outputs, Standalone templates and shared preview libraries remain unstripped. Ad-hoc signatures do not replace the distributor's certificate signing or notarisation.

### iOS

Selecting the iOS 15.0-or-newer target on macOS requires a C++ Source project, a full Xcode installation with the iPhoneOS SDK, and a completed first-launch Xcode setup. The editor does not ask for a signing identity: the packer selects the signed-in Apple Development team and signs the app automatically.

Xcode removes non-global symbols from the final Release application before signing. Static libraries used as link inputs are not stripped separately.

By default, iOS packaging only creates `dist/<game-name>.ipa`, and no iPhone needs to be connected. Select **Export to iPhone** to install and launch the app on the device as well. This mode requires exactly one physical device on the iPhoneOS platform, either an iPhone or an iPad, that `xcdevice` reports as available. Simulators do not qualify. Any unlock, trust or Developer Mode message comes from the device itself. After installation the device must also trust the developer profile, which currently surfaces as a signing error.

### HarmonyOS

HarmonyOS packaging requires a C++ Source project, Apple Silicon macOS and DevEco Studio with the OpenHarmony native SDK. Every HarmonyOS variant uses HarmonyOS 6.0.2 / API 22. Select **Mobile** for the OpenGL ES phone and tablet host, or **2in1** and then OpenGL (default) or OpenGL ES.

Without device export, the packer produces one arm64-v8a unsigned HAP in `dist`: `<game-name>-harmony-mobile-unsigned.hap`, `<game-name>-harmony-2in1-opengl-unsigned.hap` or `<game-name>-harmony-2in1-opengl-es-unsigned.hap`. Select **Export to matching HarmonyOS device** to produce the corresponding `-signed.hap`, install it and launch the game instead. Device export opens DevEco Studio and waits up to three minutes for automatic signing and the on-device confirmation before it writes the signed HAP. Mobile export accepts a connected device that reports `default`, `phone` or `tablet`, although the mobile HAP itself declares `deviceTypes: ["phone","tablet"]`. The 2in1 export accepts only `2in1`. Exactly one connected device must match the selected form, and devices of the other form may remain connected. A connected device whose type cannot be read aborts the export even when it is of the other form. The 2in1 OpenGL package requires `libGLv4.so` on the device. Some emulators omit it. The app reports the missing module and does not fall back to OpenGL ES, so use the OpenGL ES package on those images.

`Licenses` and root licence and notice files are not HAP-format prerequisites: the packer includes them when present but does not reject a project when they are absent.

Hvigor strips native libraries while producing each Release HAP variant, before signing; the packer does not strip a signed HAP. Retain the matching native build outputs for debugging.

### Android

Android packaging is shown only for a C++ Source project on macOS when Android Studio is installed in `/Applications` or the current user's `Applications` directory. It requires SDK Platform 36, Build Tools 36.0.0, a complete stable NDK r27-or-newer toolchain under the locally installed SDK and host CMake 3.28 or newer. The packer selects the highest qualifying NDK from the `ndk` directory of that SDK. Neither a project package nor the editor package carries an SDK or NDK. The packer then uses host CMake with the selected toolchain, the bundled JBR of Android Studio as `JAVA_HOME`, and the Gradle wrapper maintained in the project’s `Engine/PlatformHosts/Android` template, which downloads Gradle 9.5.0 with Android Gradle Plugin 9.3.0 and runs `:app:lintRelease :app:assembleRelease`. The APK declares API 24 (Android 7.0) as its minimum, so it installs on Android 7.0 and later. Its `compileSdk` and `targetSdk` are 36. It identifies the application as a game and requests sensor-selected landscape orientation, so either landscape rotation is supported. Android packaging never invokes SDK Manager, AVD or `adb`, and neither signed nor unsigned packaging installs or launches the APK.

Selecting Android shows **Sign APK**, which is clear by default. Leave it clear to publish `dist/<game-name>-android-arm64-v8a-unsigned.apk`. Select it to choose a JKS or PKCS12 keystore, enter its alias and passwords, and optionally save the information on this device. The picker accepts `.keystore`, `.p12`, `.pfx` and `.pkcs12` files and detects the type automatically. The key password defaults to the keystore password, and a saved record restores the keystore path and alias automatically. Cancelling the dialog returns to Pack Options, and a successful signed run publishes only `dist/<game-name>-android-arm64-v8a-signed.apk`.

Saved records live in the editor's per-user settings directory, as `android-signing.json` beside `Ludork.ini`, and on macOS under `~/Library/Application Support/Ludork`. A record stores the keystore path and alias only, while passwords use the credential store of the operating system. Passwords are never written to the project, Gradle files or logs. Android itself requires an update to an installed application to carry the same signing certificate, so the device rejects an update signed with a different key.

Android resources use APK assets with a SHA-256 manifest and a versioned runtime directory, while retaining the platform-native binary layout. Generated projects use runtime texts from the top-level `Licenses`, not editor notices.

The NDK's `llvm-strip --strip-unneeded` processes the staged `libludork.so` before Gradle packages it. The original native build output remains unstripped for debugging.

## Failure checklist

If Export, Play or Pack stops, read the first actionable error in its failure dialog, the Console or the pack log. Check plug-in hooks, `Main.proj`, the entry script, JSON syntax, Blueprint validation, generated native modules and missing assets. If the message is that access to a path was denied, close Explorer windows on the output folder and any still-running copy of the packaged game, then retry; a language server or antivirus scan holding generated Lua or binaries can cause the same error. For Android signing, verify the keystore path, alias and passwords, and correct stale saved values in the dialog. Packaging cannot repair invalid project references or substitute for target-platform testing.
