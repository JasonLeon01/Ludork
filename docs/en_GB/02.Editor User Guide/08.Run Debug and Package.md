# Running, Testing and Packaging

## Goal

Run the project with actionable diagnostics, test the native executable, and produce a complete package for a supported target.

## Prerequisites

- A saved project with a valid `Main.proj`, an entry script and a template.
- All changed Blueprints validated and referenced assets present.
- Required platform SDKs, compilers and signing resources for the selected target.
- A target meeting the platform minimum: Windows 10 or newer on x64, macOS 13.3 or newer on Apple Silicon, iOS 15.0 or newer on arm64, or HarmonyOS 6.0.1 / API 21 or newer on arm64-v8a.

## Steps

1. Save and validate the project, then run it with Console visible.
2. Inspect Performance Monitor and test the changed gameplay path.
3. Stop the runtime, open **File → Pack Project**, and review every option.
4. Complete Pack, inspect the first actionable diagnostic if it fails, and test the produced application outside the editor.

## Run modes

The Play control starts the project in the selected development mode. **Individual Window** uses a separate game window. Embedded mode hosts the Windows runtime inside the editor; unsupported platforms use the applicable standalone behaviour. Stop the current process before changing native binaries.

The editor performs the before-run plug-in hooks first, builds the C++ target when needed, starts the runtime with editor launch options, and opens the command channel. A failed hook, build or protocol handshake is reported in the Console.

## Test layers

- Validate modified Blueprints before saving.
- Test maps in the editor with Console output visible.
- Use Performance Monitor for frame and logic timing.
- Run the native executable outside the editor to catch working-directory assumptions.
- Test the packaged result because its writable settings and asset layout differ from editor mode.

## Packaging

Choose **File → Pack Project**, select the target and follow the packaging log. The project must have a valid entry script and a compatible template. Before packaging, replace the Sample's `APP_NAME = "LudorkSample"` in `Scripts/Entry.lua` with a name unique to the game; pack scripts reject the default. Official Locale Tools exports `Locale.xlsx` through the before-pack hook; low-level pack scripts do not perform that export themselves.

![Pack Options window](../../_images/editor/pack-options.png)

*Confirm the target, output and optional deployment choices before starting Pack.*

Desktop packages copy runtime files, `Assets`, `Data` and runtime `Scripts`. The development-only `Scripts/stub` tree is removed before packaging, `.d.lua` is never passed to `luac`, and finalisation rejects any declaration file that remains outside the stub tree. FFmpeg-enabled Windows and macOS packages also carry the applicable shared or dynamic libraries, notices and source offer material. On macOS, signing and notarisation remain the distributor's responsibility.

There is no Standalone iOS template. Selecting the iOS 15.0-or-newer target on macOS requires a C++ Source project, full Xcode and an available Apple Development signing identity. A C++ Source + FFmpeg iOS build uses static `.a` libraries produced through `Sample/cmake/FFmpeg`, rather than the desktop shared-library arrangement. A downstream distributor of the statically linked iOS application must satisfy the applicable LGPL relinking-material requirements and consult `Licenses/FFmpeg/README.md` before release.

By default, iOS packaging only creates `dist/<game-name>.ipa`; no iPhone needs to be connected. Select **Export to iPhone** to also install and launch the app on the device. This mode requires exactly one available iPhone that is unlocked, trusts this Mac, and has Developer Mode enabled.

HarmonyOS Mobile packaging requires a C++ Source project, Apple Silicon macOS and DevEco Studio with the OpenHarmony native SDK. It targets HarmonyOS 6.0.1 / API 21 or newer, produces an arm64-v8a unsigned HAP in `dist`, and does not expose the temporarily unavailable 2in1 target.

## Failure checklist

If Run or Pack stops, read the first actionable error in the Console or pack log. Check plug-in hook results, `Main.proj`, the entry script, JSON syntax, Blueprint validation, generated native modules and missing assets in that order.

## Expected result

The editor run and packaged application start the same entry script with the intended assets and generated Lua data; the package also carries the required notices for its selected capabilities.

## Verification

- Run inside and outside the editor.
- Exercise before-Run and before-Pack plug-ins and inspect their output.
- Test a clean package from its final location, including writable settings.
- Inventory packaged scripts, assets, native libraries, README files, documentation and legal notices; confirm that `Scripts/stub` and `.d.lua` are absent.

## Limitations

macOS signing and notarisation remain the distributor's responsibility. Device export requires a correctly prepared physical iPhone. Packaging cannot repair invalid project references or substitute for target-platform testing.
