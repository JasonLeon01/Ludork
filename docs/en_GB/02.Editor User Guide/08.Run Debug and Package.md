# Running, Testing and Packaging

## Goal

Run the project with actionable diagnostics, test the native executable, and produce a complete package for a supported target.

## Run modes

The Play control starts the project in the selected development mode. **Individual Window** uses a separate game window. Embedded mode hosts the Windows runtime inside the editor; unsupported platforms use the applicable standalone behaviour. Stop the current process before changing native binaries.

The editor performs the before-run plug-in hooks first, builds the C++ target when needed, starts the runtime with editor launch options, and opens the command channel. A failed hook, build or protocol handshake is reported in the Console.

## Test layers

- Validate modified Blueprints before saving.
- Test maps in the editor with Console output visible.
- Use Performance Monitor for frame and logic timing.
- Run the native executable outside the editor to catch working-directory assumptions.
- Test the packaged result because its writable settings and asset layout differ from editor mode.

## Packaging

Choose **File → Pack Project**, select the target and follow the packaging log. The project must have a valid entry script and a compatible template. Before packaging, replace the Sample's `APP_NAME = "LudorkSample"` in `Scripts/Entry.lua` with a name unique to the game; pack scripts reject the default. Official Locale Tools exports `Locale.xlsx` through the before-pack hook; low-level pack scripts do not perform that export themselves.

Desktop packages copy runtime files, `Assets`, `Data` and runtime `Scripts`. **Pack assets (.ldpak)** is clear by default; when selected, each first-level `Assets/<Group>` becomes `Assets/<Group>.ldpak` in staging. Archives are deterministic, uncompressed, unencrypted and seekable. Shader encryption runs first, so logical `.frag` paths resolve packaged `.fragc` entries.

Staging validates UI, applies plug-in exclusions, removes development/editor data, compiles plug-in Lua, encrypts Shader and Data files, rejects remaining `.d.lua`, then optionally builds `.ldpak`. Each archive is verified before its staged source group is removed; the source project is unchanged.

Packing rejects root-level files, symbolic links, case collisions, `.ldpak` group names and output conflicts. Runtime also rejects mixed loose/packed groups. Empty directories are preserved, corrupt archives fail validation, and low-level pack commands use `--pack-assets`.

The development-only `Scripts/stub` tree is removed before packaging, `.d.lua` is never passed to `luac`, and finalisation rejects any declaration file that remains outside the stub tree. FFmpeg-enabled Windows and macOS packages also carry the applicable shared or dynamic libraries, notices and source offer material. On macOS, signing and notarisation remain the distributor's responsibility.

There is no Standalone iOS template. Selecting the iOS 15.0-or-newer target on macOS requires a C++ Source project, full Xcode and an available Apple Development signing identity. A C++ Source + FFmpeg iOS build uses static `.a` libraries produced through `Sample/cmake/FFmpeg`, rather than the desktop shared-library arrangement. A downstream distributor of the statically linked iOS application must satisfy the applicable LGPL relinking-material requirements and consult `Licenses/FFmpeg/README.md` before release.

By default, iOS packaging only creates `dist/<game-name>.ipa`; no iPhone needs to be connected. Select **Export to iPhone** to also install and launch the app on the device. This mode requires exactly one available iPhone that is unlocked, trusts this Mac, and has Developer Mode enabled.

HarmonyOS packaging requires a C++ Source project, Apple Silicon macOS and DevEco Studio with the OpenHarmony native SDK. Every HarmonyOS variant uses HarmonyOS 6.0.2 / API 22. Select **Mobile** for the OpenGL ES phone/tablet host, or **2in1** and then OpenGL (default) or OpenGL ES.

Without device export, the packer produces one arm64-v8a unsigned HAP in `dist`: `<game-name>-harmony-mobile-unsigned.hap`, `<game-name>-harmony-2in1-opengl-unsigned.hap` or `<game-name>-harmony-2in1-opengl-es-unsigned.hap`. Select **Export to matching HarmonyOS device** to instead produce the corresponding `-signed.hap`, install it and launch the game. Mobile export accepts a connected device that reports `default`, `phone` or `tablet`; 2in1 export accepts only `2in1`. Exactly one connected device must match the selected form; devices of the other form may remain connected. The 2in1 OpenGL package requires `libGLv4.so` on the device. Some emulators omit it; the app reports the missing module and does not fall back to OpenGL ES, so use the OpenGL ES package on those images.

A C++ Source + FFmpeg HarmonyOS build statically links an API 22-targeted FFmpeg build and carries the project runtime legal materials; downstream distribution must satisfy the applicable LGPL notice and relinking-material requirements described in `Licenses/FFmpeg/README.md`. `Licenses` and root licence/notice files are not HAP-format prerequisites: the packer includes them when present but does not reject a project when they are absent.

Android packaging is shown only for a C++ Source project on macOS when Android Studio is installed in `/Applications` or the current user's `Applications` directory. It requires SDK Platform 36, Build Tools 36.0.0, a complete stable NDK r27-or-newer toolchain under the locally installed SDK, and host CMake 3.28 or newer. The packer selects the highest qualifying NDK from that SDK's `ndk` directory; a project and editor package never carry an SDK or NDK. It uses host CMake with the selected toolchain, then Android Studio's bundled JBR and Gradle. The APK declares API 24 as its minimum, so it includes Android 12 and 12L. It identifies the application as a game and requests sensor-selected landscape orientation so either landscape rotation is supported. Android packaging never invokes SDK Manager, AVD or `adb`, and neither signed nor unsigned packaging installs or launches the APK.

Selecting Android shows **Sign APK**, which is clear by default. Leave it clear to publish `dist/<game-name>-android-arm64-v8a-unsigned.apk`. Select it and confirm Pack Options to open the signing dialog, then choose an existing, readable JKS or PKCS12 keystore and enter its key alias and keystore password. **Key password is the same as the keystore password** is selected by default; clear it only when the key has a separate password. Cancelling this dialog returns to Pack Options without starting a package. Signing first builds and validates the unsigned APK, then signs and verifies it with Android SDK `apksigner`; a successful signed run publishes only `dist/<game-name>-android-arm64-v8a-signed.apk` and keeps the unsigned APK as build-intermediate data.

The keystore path, alias and passwords exist only for the current Pack operation. Ludork does not save them in the project, editor settings, Gradle files, logs or the system keychain. Do not lose the keystore or its credentials: subsequent versions intended to update the same installed application must use the same signing key.

Android resources are stored as APK assets with a SHA-256 manifest, then copied to a versioned runtime directory. Android and HarmonyOS do not recompress `.ldpak`; Runtime mounts it after extraction. Generated projects use runtime texts from top-level `Licenses`, not editor notices. Static FFmpeg linking still requires `Licenses/FFmpeg/README.md` obligations.

## Failure checklist

If Run or Pack stops, read the first actionable error in the Console or pack log. Check plug-in hook results, `Main.proj`, the entry script, JSON syntax, Blueprint validation, generated native modules and missing assets in that order. For Android signing failures, also check that the keystore path is absolute, the file remains readable, the alias exists and both passwords match the selected key; re-enter the credentials because they are never retained between Pack operations. Packaging cannot repair invalid project references or substitute for target-platform testing.
